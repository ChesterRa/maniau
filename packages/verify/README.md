# 計画の検証

`@maniau/core` の型・時間のデータと、事象の列を入力にする。計画エンジンは読み込まない。JSON から読み直した入力も、入口で型を検査する。

```ts
import { verifyPlan } from '@maniau/verify';

const result = verifyPlan({ household, plan, events });
```

`status` は次の三つで、`issues` の `code`・`subject`・`detail` は個別の理由を示す。

| 状態           | 意味                                                   |
| -------------- | ------------------------------------------------------ |
| `pass`         | この検証で該当した条件を満たし、未確認の条件も無い     |
| `violation`    | 少なくとも一つ、与えられた条件との矛盾がある           |
| `undetermined` | 違反は見つからないが、確認に必要な情報や証明が足りない |

違反があれば未確認の点も `issues` に残し、全体の状態は `violation` とする。`undetermined` を `pass` と同じ意味にはしない。全体の状態だけでなく個々の理由を呼び出し側で扱う。

## 知らせを送る前の検証

```ts
import { verifyNotificationMessage, verifyNotifications } from '@maniau/verify';

const intentions = verifyNotifications({ household, plan, events, intents });
const message = verifyNotificationMessage({ message: payload, language, intents });
```

計画自体は先に `verifyPlan` で確かめる。知らせの意図は基本キーと構造化された根拠を受け取り、
有効な大人、本人に見える作業・依頼・手配・問い、時機と期限、名前の直接混入を照らす。
実際に送る文は、受け手ごとにまとめた後に別の許可表と照合し、固定文と件数以外を送らない。
担当のいない作業については、有効な作業か、誰かが引き受けていないか、案の決め時または作業の締切と
26時間以内の時機を照らす。意図ごとの問題は `subject` に基本キー、特定できない問題は `$all` を付ける。家庭の内容を
`detail` に出さない。呼び出し側は意図の違反を送らず、`$all` の違反は全て送らない。

知らせの回数は、現時点の計画だけでは独立に再現できないため `notification_round_unverified` とする。
この検証は送信先の認証・端末への到着・本人の既読を証明しない。名前の直接一致の検出だけで、
全ての個人情報がキーに含まれないことは保証できない。家庭が入力する ID を内容のない ID に
置き換えることと、外部送信直前の権限確認は別に必要である。

## 確かめること

- 買い物で先に聞く問いが、その要件と手配の「家にあるか」を指し、同じ手配への影響を記しているか。不要な持ち物に問いが残っていないか。期限前の持ち物に手配が無い場合、家にあると答えた可能性を含めて理由を確認できなければ未判定とする。
- 家庭・計画・事象の型と家庭 ID、事象の順序、本命と予備の選択、本人だけの引き受け操作。受けた時の提案の控えと今の作業を照らし、変わった提案に再確認の印があるか。済んだ時の用件の控えが今と異なれば、前の用件の済みを今の作業に当てず、再確認が必要か照らす。控えの無い以前の済みは従来どおり扱う。
- お知らせの文の分類、書かれた曜日と日付、条件の式、回答と変更による元の事項の適用。本文の版、家族による確認・訂正・取り下げ、削除後の出典の扱いも照らす。
- 生きている作業・手配・要件から元の根拠へたどれるか。推定を確認前に必須と扱っていないか。一つの事項に対応する品物・提出物の要件と作業の用件、子の居場所の要件・手配・手順の日を照らす。
- 作業の所要時間、担当の区間、場所、営業時間、移動を含めた人の占有、重なり、先後、家庭の手順と締切。比較中の候補は、本命や予備と同時に実行する作業として数えない。本命の今の依頼が「はい」で確定し、返事待ちや確かめ直しがなければ、不要になった予備の未完了の手順も数えない。済んだ作業と取消しの連絡は数える。
- 同じ案の連続した手順の担当が替わる時、受け渡しの方法はまだ分からない。交接待ちの印なしに二人の手順を確定させていないか、印がある作業に時刻や場所を置いていないかを照らす。一般の作業の前後関係だけから、物の受け渡しがあるとは決めない。既に済んだ手順の実際の受け渡しは未判定とする。
- 帰宅が遅れる寄り道では、別の大人の在宅と同時刻の作業を照らす。到着の時刻を遅らせる確認は、担当本人が最後の提案で見た時刻と、今の作業・到家時刻が一致する場合に限る。
- 依頼ごとの送信・返事・取消しと本命・予備の選択を事象から照合する。送信時の控えがあれば、今の作業ではなく控えの相手・種類・根拠・期間と照らす。子の居場所では、頼んだ日と今の手配の日を家庭の時区で照らし、前の日の返事を今の日の返事にしない。同じ日の時刻の変更も控えと照らす。日が分からない古い控えは、今の日に当たるか未判定とする。依頼の期間が控えと違う時、または送信の控えに期間がないのに計画にある時は違反とする。事象が欠けて控えを確認できない時や、控えの期間を計画に出していない時は未判定とする。確かな一対一の訂正は、元の根拠から置き換え先へたどる。不要と確かめられた依頼の取消し、まだ必要と確かめられた依頼への誤った取消しを調べる。必要性が不明な時は、計画の `live` だけから取消しを要求しない。取消しを送った記録は、相手の受理・既読の証明ではない。
- 決め時を現在時刻と照らし、期限を過ぎた未選択の案を推薦していないか、断られた案の代わりがあるか、取れるか未判定の案を残したまま「不可能」としていないかを確かめる。

## 確かめられないこと

原文からモデルが事項を読み落としたか、文を「関係なし」に誤って分けたか、すべての要件が導かれたかは保証できない。文の分類の検査は、その一部の防線である。入力が正しいか、実際の営業時間・在庫・経路・到着時刻が正しいかは別に確かめる。

駅からの徒歩が目安なら、実際の道のりは未確認とする。地図の詳細な根拠を受け取る型はまだ無いため、`maps` も未確認とする。営業時間に必要な期間や出典が足りない時、事象が欠けた時、昔の作業時点の家庭の条件を確認できない時も未判定にする。

引き受けた時の控えについて、開始・終了・遅れた到家の時刻、用件とその値、店の ID、移動時間、外の相手・種類、条件を現在の作業と照らす。条件は計画が出した値を控えと照らすだけで、その値が元の事項の条件や画面の表示と一致するかまでは確かめない。事象に残った控えの照合であり、実際の画面表示や本人の認証を証明するものではない。本文の書き直し後に読み直しがまだ無い時や、出典の内容が消えて過去の条件・回答をたどれない時は、確かめられない部分を未判定とする。事項と要件の品名・日付の照合は、一つの事項に直接対応する要件に限る。条件の式は共有された子の結果を再利用し、各通知の読み取りが64節点または5000辺を超える場合は、その式を未判定とする。

入口は通常の `DomainEvent` の形を要求する。読み取り結果が削除され、出典の削除事象でそれと分かる場合は、その読み取りを未判定にできる。一方、`noticeReceived` の出典そのものを含まない事象は現在の型を通らず、`invalid_event` になる。実在の家庭向けに内容を分離・削除する置き場所と、その後の検証入力の形はまだ実装していない。

送信前の条件と現在の条件の比較は、一つの未定値と比較する値が変わった場合など、一部しか確かめられない。節点 ID が同じでも意味が同じとは限らず、違っても意味が違うとは限らない。複雑な条件や、送信前の事象が足りない場合は未判定とする。置き換えが競合・循環する場合や、条件付きの回答と取消しが複雑に影響し合う場合も、保守的に未判定を残す。

開始操作を記録する事象はまだ無い。「済んだ」「送った」が無いことは、作業を実際には始めていない証明にならない。決め時を過ぎても進捗の記録がない案は、進捗を確認できないと報告する。

決め時が可能な時刻かどうかの条件は一部照合するが、それが**最も遅い可能な時刻**か、不可能とされた問題に本当に解が無いかは、独立に探索していない。認証済みの本人から操作が来たかはサーバー側の責務であり、ここでは受け取った事象の担当と操作人を照らす。
