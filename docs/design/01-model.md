- 後で変えにくい物（事象の記録、事実の型、引き受けの状態、計算と説明の分担）を先に決める。名前や細部は、作りながら決めてよい。

## 1. 分担と流れ

**Claude が受け持つ**：おたよりを読む。変更の連絡が前のどの事項を変えたかを読む。書かれていない準備を推定する。品物を扱っていそうな店の種類を推定する。家族の一言を答え・条件・好みに直す。計算の結果を説明する。頼み事と取り消しの文を、相手の言葉で下書きする（送るのは家族）。

**コードが受け持つ**：日付・曜日・祝日の検査。条件の適用と、取り消し。決め時。聞くべき問いの判定。案の選択と配置（求解）。場所・道のり・営業時間の照合（地図のデータ）。引き受けの状態。知らせる時機と送り出し。検証。

モデルの出力で、計算で保証する部分を置き換えない。説明の文は、計算の結果に無い事実（日付・人・数）を足していないかをコードで確かめる。

一つの入力ごとの流れ：

1. 入力を事象として記録する（§2）。
2. おたよりなら、Claude が読む。モデルの出力は、どの呼び出しでも、モデル名・プロンプトの版と一緒に記録する（§2）。
3. コードが検査する（型、文IDの範囲、引用が指した文に有るか、指した文に書かれた日付と合うか、日付と曜日、祝日、IDの重なり）。食い違いは問いにする。確かめてほしい文（事項にならなかった文、外した・食い違った事項の文、二通りに読める文）は、読み取りに残して原文の横に示す。合っても、解釈が正しいとまでは言えない。
4. 全ての事象から、事実を組み立て直す（§3）。
5. 要件の適用から、手配・案・作業を導き、前と比べて差分を取る（§4）。
6. 決め時を計算し、聞くべき問いを選ぶ（§5、§6）。
7. 求解で、勧める案・担当・時間帯を求める（§8）。選ぶのは家族である。
8. 検証器が確かめる（§9）。
9. 二人それぞれの「今日」と、知らせを作る。

3〜9は、事象の列（と、それが指す中身）、今の時刻、計算の時に引いた外のデータ（地図）から決まる関数にする。同じ版のコードに、同じ入力を同じ時刻まで流せば、同じ結果になる（求解の再現は§8）。中身を消した時や、地図の結果を保存できない時は、再現できる部分だけを示す（02-foundation §2.3・§6.3・§10）。

## 2. 事象の記録（正本）

家族の事実の正本は、追記だけの事象の列と、それが指す消せる中身である。今の権限は、成員の表の今の値が正本である（02-foundation §2.1）。中身がそろっていれば、今の状態は事象から作り直せる。消した中身に頼る部分は作り直せず、そう示す。

| 事象 | 中身 |
|---|---|
| おたよりが届いた | 原文（文字・画像・PDF）、届いた時刻、送り手、元の版（訂正なら） |
| モデルの出力を記録した | 呼び出しの種類（読み取り・準備の推定・一言の解釈・説明）、出力（型付き）、モデル、プロンプトの版、入力のハッシュ |
| 家族の情報を変えた | ふだんの週、場所と営業時間、取れる手の決まり、分担の決まり |
| 答えた | 問いへの答えと、答えた人 |
| 案を選んだ | 手配と案と、選んだ人 |
| 引き受けを変えた | 引き受ける・断る・済んだ・できなくなった（本人だけ） |
| 外の返事を記録した | 祖母の返事、学童の受理、上長の承認など（はい・いいえ）。記録した家族の人 |
| 知らせた | 誰に、何を、いつ。Push の事業者が受け付けた事だけで、届いた・読んだの証拠ではない（同じ知らせの意図を繰り返さないため、追いかけた回数を数えるため） |
| 時計を進めた | 試験とデモだけ。本番は実際の時刻 |

- 事象の一覧の全体（事項の確認・訂正、取り下げ、削除、書き起こし、記録の誤り等を足した物）と、命令から事象への展開は、02-foundation §7.2 にある。
- 保存の表、敏感な中身の分け方、操作の冪等は、02-foundation §6・§7.3 にある。状態を変える書き込みはトランザクションにし、同じ操作の二重の記録を防ぐ。
- モデルの出力を事象に残すので、再生の時にモデルを呼ばない。試験は API なしで走る。
- 敏感な材料（おたよりの原文・写真、住所、個人の情報を含むモデルの出力）は、事象の本体と分けた保管場所に置き、事象からは ID で指す。作り手の許可の範囲と期限で消せるようにする。消した後に再生できるのは、消した物に頼らない部分だけで、そう示す。
- 地図の外のデータは、条款に従い、place ID と調べた時刻だけを事象に残す。過去の営業時間や道のりは、後から正確には再現できない（架空のデータでの再生とは分けて言う）。
- 実在の家族の事象は、作り手が許した置き場所にだけ置く（リポジトリには入れない）。

## 2.1 家庭と権限

- 家庭を、データを分ける単位にする。家庭・成員（大人・子・頼める人）・ログインの身元の対応を、最初から持つ。事象と作業は、どれも一つの家庭に属する。
- 身元は認証の仕組み（§11）が確かめ、サーバーが成員と照らす。画面やメールから来た「親A」等の名乗りを信じない。
- 権限はサーバーで毎回確かめる：その家庭の成員か、本人だけができる操作（引き受ける・断る・済んだ・できなくなった）か。データベースの行の規則（RLS）は守りの一つだが、サーバーが強い権限でつなぐと効かないので、それだけに頼らない。
- 家庭が一つしかなくても、試験用の二つの家庭で、互いに読めず書けないことを確かめる。
- 家族のデータを読み書きする要求は、毎回、認証のトークン（今週は Cloudflare Access の JWT：署名、決まった発行元と対象、期限）を確かめ、その成員がまだ有効かを見てから、家庭と成員の権限を見る。署名の鍵は入れ替わるので取り直せるようにし、取れない・合わない時は断る。Access の許可から外すだけでは、出したトークンはすぐには消えないので、成員を止める操作をサーバーに持つ。
- 実際の家族の置き場所で認証の設定が欠けていたら、起動しない。デモは別の設定と別のデータで動かし、実際の置き場所と混ぜない。
- 身元の提供元を替える時（Access からパスキーへ等）は、同じ人であることを本人の操作で確かめてから結び付ける。メールが同じというだけで結び付けない。

## 3. 事実の型

型は Zod で一か所に定め、API・保存・モデルの構造化出力の型もそこから作る。

| 型 | 主な中身 |
|---|---|
| 出典 | 出典ID、版、届いた時刻、送り手（学校・園・学童・習い事・勤務先・家族）、届いた形（文か写真）、原文、文の一覧（文ID）。写真なら、文は写真から書き起こした物で、家族が写真と並べて確かめる |
| 事項 | 読み取った一つの事。種類（行事・持ち物・提出物・日課の変更・締切・問い合わせ先・テスト・宿題と家の人のサイン・当番・配られたプリント）、文ID（一つ以上）、書かれた表現と解釈、適用の条件、証拠の状態、前の事項への作用 |
| 未定の値 | 分かれ目になる値と、その取り得る値。例：学習発表会の実施日 ∈ {12/5, 12/8}、白い長袖シャツが家にある ∈ {はい, いいえ} |
| 要件 | 家族が満たす事。何を、いつまでに、性質（必須・任意・好み）、適用の条件、元の事項 |
| 家族の情報 | 人（大人・子・頼める人。大人ごとの画面の言葉）、地域と時区、取れる手の決まり、分担の決まり、代償の上限 |
| 場所 | 種類（家・学校・学童・職場・駅・店）、位置（家は住所か地図の点も入れられる。町や駅の粒度だけなら、道のりは粗い目安と示す。02-foundation §3.3）、営業時間とその出典・調べた時刻、地図の place ID |
| ふだんの週 | 人ごと・曜日ごとの区間（家→駅→職場→駅→学童→家）、出発と到着、手段、お迎えの担当、在宅や不定の印 |
| その日だけの一日 | 大人の、ある日の区間の全部（休む・その時間は外にいる・遅くなる）。その日は、ふだんの曜日の一日の代わりに使う（差分でなく一日の写し。ふだんの週を後で直しても変わらない）。同じ人・同じ日は一つ。外すと、ふだんに戻る。家の情報の直し（見る → 保存）で足し、見るだけなら何も書かない（2026-11-04） |
| 手配 | 要件と家族の情報から出る、手当てが要る事。例：12/7 8:00〜18:15 の子の居場所 |
| 案 | 手配を満たす方法。手順（作業の雛形と待ち時間）、代償、外の返事の要否、決め時（計算） |
| 作業 | 誰が・いつ・どこで・何を。所要時間、最早の開始、締切、先後、元（要件か案） |
| 引き受け | 作業や依頼の状態（§7）と、その履歴 |
| 問い | 未定の値、答えの候補、聞く期限、答えで何が変わるか |

三つの軸を混ぜない（ここが崩れると、§4〜§7 が成り立たない）。

- **証拠の状態**：記載／家族が確認／推定／食い違い。推定と食い違いは、家族が確かめるまで、必須の要件を作らず、前の事実を変える作用（未定の値を決める・置き換える・取り消す）も起こさない。条件が偽か分からない事項の作用も同じ（02-foundation §5.2）。
- **性質**：必須／任意（行けたら見に行く）／好み（夜は作業しない）。分からない締切は「好み」にしない。分からないまま、問いにする。
- **引き受けの状態**：提案／引き受け／条件待ち／確定／済み（§7）。

**日付の書き方**：「あした」「きょう」とだけ書かれた物（連絡帳に多い）は、モデルが日付を作らず、コードが出典の届いた日から決める（あしたは暦の次の日。書かれた曜日と食い違えば「食い違い」として家族に確かめる）。持ち物の期限は、書かれた締切か日付があればそれ、無ければ同じお知らせ（置き換えをたどった元の出典）の行事の最も早い日の朝とし、別のお知らせの行事には結ばない。時刻が書かれていない時の「朝」は、こちらの目安であり、お知らせに書かれた時刻としては見せない（家を出る時刻から決める。今のエンジンの 08:00 決め打ちは、直す差として残す）。

**条件の式**：未定の値の等式を、「かつ・または・でない」で組む小さな式に限る。Claude は、使う未定の値と取り得る値を宣言し、コードは宣言の無い値を使った式を受け付けない。構造化出力は再帰の schema を受けないので、式は平らな節点の一覧（節点の ID、種類、子の節点の ID）で返させ、コードが参照・循環・値を確かめる。

**用語**（文書と画面で、同じ言葉を使う）：

| 言葉 | 意味 |
|---|---|
| 取れる手 | 家族が使える方法の種類と、その決まり（学童の一日利用、祖母に頼む、有休・時間休） |
| 案 | ある手配を、取れる手で満たす具体的な方法。手順・代償・決め時を持つ |
| 代償 | 案を選ぶと払う物：休暇の時間、人に頼む回数、お金、増える作業 |
| 決め時 | その案を取れる最後の時刻（§5） |
| 引き受け待ち | 引き受けの状態「提案」の、画面での言い方 |
| 返事待ち | 引き受けの状態「条件待ち」の、画面での言い方。「祖母の返事待ち」「上長の承認待ち」のように、相手と中身を出す |
| 返事しだい | 計画全体の状態：待っている返事が来れば実行できる（§8） |

## 4. 適用と取り消し

要件・手配・案の選択・作業は、すべて「なぜ要るか」の根拠を持つ。根拠は、元の事項、適用の条件、選んだ案、家族の情報である。

- 事実が変わるたびに、導いた物の集まりを作り直し、前の集まりと比べる。
  - 足す・外す・残す・変える（同じ物で、時刻や担当が変わった）に分ける。
  - 比べられるように、導いた物に安定したキーを付ける。キーは、種類と、置き換えの作用をたどった元の事項の ID（系譜）から作る。時刻や担当など変わり得る値はキーに入れない（同じ物の時刻や担当の変更を「外して足す」と誤り、要らない取り消しを作らないため）。
- 外す物は、引き受けの状態で扱いを変える。

| 外す物の状態 | 扱い |
|---|---|
| 提案 | 一覧から外し、変更のまとめに載せる |
| 引き受け・条件待ち・確定 | 本人に知らせる。外の相手に頼んだ後なら、取り消しの連絡の作業を作る（祖母へ、学童へ） |
| 済み | 記録を残す。済んだ作業そのものは戻さない（買った物など）。その作業で外の相手に出した依頼（届け、頼み事）がまだ効いていれば、取り消しの連絡の作業を作る |

- 取り消しの連絡を作るかは、作業の状態ではなく、外の相手への依頼がまだ効いているかで決める（出した学童の届け、祖母への頼み事）。
- 変更の連絡は、前の事項への作用として読む：未定の値を決める（実施日 = 12/8）、事項を置き換える（時刻の変更）、事項を取り消す。Claude には、関係する出典の今の事項を ID 付きで渡し、作用は ID で返させる。コードは、ID が実在するかを確かめる。
- 外し方は、真理維持（truth maintenance）の考え方に沿う。今週の規模（数十件）では、差分を取るために全体を作り直せば足り、増分の仕組みは要らない。

## 5. 決め時

**案の決め時**：その案を実行するために、最初の作業を始められる最後の時刻。これを過ぎると、その案は取れない。

計算（初版）：

1. 案の手順を、後ろから順にたどる（クリティカルパス法の逆算）。
   - 最後の作業の終わりの期限は、手配が要る時刻と、決まり（学童の届けは前週の月曜のお迎えまで、等）の早い方。
   - 各作業は、担当できる人の空き時間と、場所の開いている時間の中で、期限までに終わる最も遅い枠に置く。買い物などの寄り道は、その人のふだんの週の区間（帰り道の駅など）に差し込み、増える時間と、お迎えに間に合うかを確かめる。電車の道のりは途中に寄る所を一度に問えないので、駅の近くを探し、区間ごとに確かめる。確かめられない所は「要確認」と示す。
   - 帰り道の寄り道（初版の決まり）：
     - 寄れるのは、通勤の区間が家で終わり、店がその道の最後の駅の近くにあり、その駅が家の最寄りの駅である時だけ。
     - 駅に着く時刻は、通勤の区間の終わり（ふだん家に着く時刻）から、家の駅からの徒歩を引いた時刻。店での作業は、そこに店までの徒歩を足した時刻に始まる。
     - 家に着くのは、店への往復の徒歩と作業の分だけ遅れる。作業には、元の到着と遅れた到着を持たせる。駅に着いてから遅れた到着までは、その人の時間がふさがり、他の作業を置かない。
     - 夕方の家の区間は空いた時間として、遅れた分だけ短くしてよい。お迎えと勤務は動かさない。遅れた到着が、続く家の区間の終わりを越える時は寄らない。
     - 遅れる間、他の大人がずっと家にいる時だけ寄る（子を大人のいない家に残さない）。エンジンはこれを、ふだんの週の区間で判断する。他の大人がその時間に別の作業で外にいないかは、検証器が計画の作業と突き合わせる。遅く帰ってよいかは家庭ごとに違うので、計画は寄り道を提案するだけにとどめ、担当の人が引き受けた時に確かめたとする。それまで検証器は「未判定」と示す。
     - 徒歩の時間は家庭の情報の目安で、地図で確かめるまでは目安と示す。地図の根拠（その要求で Google から引いた駅 → 店・店 → 駅の徒歩と営業時間。02-foundation §2.3）が店と駅に結び付く時はそれを使い、行きと戻りを別に足す。
   - 前の作業の終わりの期限は、次の作業の開始から、待ち時間（祖母の返事は最大1日、承認は1営業日、等）を引いた時刻。
   - 最初の作業の開始が、案の決め時である。今日から締切までに、ほかの作業を除いても置ける枠が無い時は、同じ置き方でふだんの予定の二週をさかのぼり、そろった置き方が見つかれば、その始まりを過ぎた決め時とする（過ぎたと言う証拠。作業は過去に置かない）。それでも置き方が無い時は決め時を出さず、決まりの締切が過ぎるまでは取れなくなったとも言わない（見つからないことを、過ぎた証拠にしない）。ふだんの予定にそもそも置ける枠の無い手順（平日の昼だけ開く窓口に、ふだんの予定で行く時が無い等）を持つ案は、「ふだんの予定に置ける時間が無い手順がある」と示して勧めない。決め時を出せない案しか残らない手配は、取れないとは言わず、まだ判断できない（理由 noSlot）とする。家族は選べ、選べば時刻を置かない作業になる（休みを取って行く等は家族が決める）。
2. 逆算は、一つの案の手順だけを見ている。他の作業と時間が重なると、本当の決め時はもっと早い。そこで、その決め時に案を選んだと置いて、計画全体を解き直す（§8）。解けなければ、一つ前の区切り（枠の終わり、店の閉まる時刻、締切）へ戻して試す。確かめ済みの決め時と、目安の決め時を区別して示す。
3. 営業日は、土日・祝日（内閣府のデータ）と、勤務先の休みから作る。
4. 探し切れない・時間切れ・入力が足りない時は「まだ判断できない」とし、「取れない」とは言わない。取れないと言えるのは、確かめた範囲を探し尽くした時だけである。

**画面での見せ方**：手配ごとに、取れる案を決め時の順に並べる。見出しには「安い案が消える時刻」を出す（例：休まずに済む方法は、11/30のお迎えまで）。決め時が過ぎた案は「取れなくなった」として残し、勧めない。

## 6. 聞くべき問い

答えで決め方が変わる事だけを、決め時より前に聞く（情報の価値の考え方の簡単な形）。

1. 候補：未定の値のうち、要件・手配・案に効く物。Claude が「意味が二通りに読める」と示した所も、未定の値として加える。
2. 各候補について、答えごとに計画を解く。比べるのは、次の決め時までに要る作業と、各手配で勧める案である。
3. どの答えでも同じなら、今は聞かない（後で、効く決め時が近づいた時に、もう一度判定する）。違えば聞く。聞く期限は、違いが効く最も早い決め時より前に置き、答えを受け取ってから動ける時間を残す（白い長袖シャツなら、買える最後の機会より前）。
4. 期限までに答えが無ければ、間に合わなくならない側で進め、そう示す（白い長袖シャツは「無い」として買い物を残す）。
5. 一人に同時に出す問いは、少なくする（初期値2件）。聞く期限の順に出す。

## 7. 引き受け

家族の誰が作業を受けたか（引き受け）と、外の相手に頼んだ事がどうなったか（依頼）を、別の物として持つ。引き受けただけでは、まだ頼んでいないことがあるからである。（2026-11-02、検証器の見直しで分けた）

作業の引き受け：

| 状態 | 意味 | 次へ |
|---|---|---|
| 提案（画面では「引き受け待ち」） | 仕組みか、もう一人が提案した | 本人が「引き受ける」か「断る」 |
| 引き受け | 本人が受けた | 本人が「済んだ」を押す。外に頼む作業なら「頼んだ」「出した」を押す |
| 終わり | 済み・断った・できなくなった・取り消し | — |

外への依頼（「頼んだ」「出した」を押した時に始まる）：

| 状態 | 意味 | 次へ |
|---|---|---|
| 返事待ち | 返事・承認・受理を待っている | 「はい」を記録すると確定へ。「いいえ」なら断られた |
| 確定 | 相手が受けた | 前提が消えたら、取り消しの連絡を作る |
| 終わり | 断られた・取り消した（取り消しの連絡を送った） | — |

- 「引き受ける」「断る」「済んだ」「できなくなった」は、本人だけが操作できる。外の返事は、家族の誰でも記録できる。
- 引き受けには、その時に画面で見せた提案の控え（時刻、寄り道で遅れる到着、担当、用件、場所、外の相手）を持たせ、サーバーが今の提案と同じかを確かめる（02-foundation §5.5）。後で解き直して中身が変われば、前の引き受けは新しい中身を確かめたことにならない。（今週の差：エンジンは引き受けた時刻を固定せず、毎回解き直す。引き受けた時刻を保ち、できない時だけ提案し直して確かめ直してもらうのは後に回す。それまで検証器は、見せた時刻と今の時刻が違えば未判定と示す。）
- 手配の状態は、依頼から決まる：選んだ案の依頼が返事待ちなら「返事しだい」、確定なら「決めてよい」。
- 断った・断られた・できなくなった時は、手配を開き直し、残る案で解き直す。前提が消えた時は、§4 の取り消しへ。
- 本命の依頼が断られた時、または本命を決め時を過ぎても始めていない時は、押さえた予備へ移る。予備も無ければ、まだ取れる案から勧める案を出し、家族に選び直してもらう（理由：断られた／決め時を過ぎた）。選んだ記録は消さない。
- 相手の都合が変わった時（確定の後の「いいえ」、断った後の「はい」）は、後の返事に従う。取り消した依頼は変えない。
- 依頼が要らなくなるのは、前提が消えた時、案を取り下げた時、選び替えて外れた時、本命が確定して予備が要らなくなった時である。頼んだ後なら、頼んだ人に取り消しの連絡を作る。何も選んでいない時に家族が出した依頼は、残す。
- 外の相手（祖母、学童、勤務先）は、家族として操作しない。返事は、家族の誰かが記録する。
- **追いかける時機**：条件待ちのまま、次に良い案の決め時が近づいたら、その引き受けの本人に知らせる。予備の案を先に押さえる提案も出す（例：学童の届けを予備に出す。要らなくなれば取り消す）。知らせは担当の本人だけに出し、もう一人は状態を見るだけでよい。
- 知らせは、持続する待ちとして持つ。送る直前に、取り消し・担当・期限を確かめ直す。止まっていた間に来た分は、再開の時に、まだ役に立つ物だけ補う。同じ知らせの意図は一つにする（知らせごとの冪等のキー）が、外の受け付けと記録を一つにできないので、端末に一度だけ出るとは約束しない（02-foundation §5.7）。送り出しが受け付けられたことを、届いた・読んだとは扱わない。知らせの文には子や学校の名前を入れない（ロック画面に出るため）。Service Worker は家族の API の応答を保存しない。ログインが切れた後に知らせから開いた時は、ログインの画面を見せ、裏で失敗した物を届いた・済んだと扱わない。
- 知らせた事、断った事、代わりに引き受けた事は、事象として数える。分担の決まりの点検と、「誰が追いかけ、誰が穴を埋めたか」の実測に使う。家族を採点する表にはしない。

## 8. 計画（求解）

決定的な手から始める：決め時の逆算、ふだんの週の区間への貪欲な配置、範囲を限ったバックトラック。今週の規模は、大人2人・数週間・作業数十件である。時刻は分の精度で扱い、決まった刻みに丸めない。置く時刻の候補は、空いている区間の端（始まりと、終わりから所要を引いた時刻）と期限から作る（10分の作業を17:20〜17:30に置ける）。丸めるのは表示だけで、候補に無かったために置けなかった物を「無理」とは言わない。この規模ではこれで足りると見込むが、正しさや最適さは主張せず、検証器が毎回確かめる。G1 の比較で深い求解が要ると分かったら、下の形を混合整数計画として HiGHS（MIT、WASM）で解く。それでも足りない時だけ、OR-Tools（Python）を別のサービスとして置くことを考える。二つの仕組みを先に作らない。（2026-11-02 夕方、TypeScript にしたので CP-SAT を既定から外した）

**変数**：

- 手配ごとに、勧める案を一つ選ぶ（性質が任意の要件には、「しない」も案に含める）。
- 作業ごとに、担当の候補の人ごとに、置くか置かないかを選べる区間を持ち、選ばれた案の作業だけを置く。担当はちょうど一人。

**硬い条件**：

- 人ごとに作業を重ねない。勤務・移動・既にある予定とも重ねない。
- 場所の開いている時間、最早の開始と締切、先後と待ち時間を守る。
- 確定した引き受けは動かさない。
- 家族が決めた代償の上限を守る（例：この期間の有休は1日まで）。

**目的**（重み付きの和。重みは家族が変えられる初期値）：

- 選んだ案の代償（休暇の時間、頼む回数、お金、増える作業）
- 引き受け済みの作業を動かす数
- 分担の決まりからのずれ
- 大事な作業の、締切までの余裕の少なさ

**二つ目の案**：最良の計画の後、代償の最も大きい手配で選んだ案を禁じて解き直し、中身の違う案を一つ出す。解けなければ、出さない。

**再現**：再生に要るのは決定性である。入力の順を固定し、乱数を使わず、時間の上限は壁時計ではなく探索の手数で置く（壁時計で切ると、機械の負荷で結果が変わる）。解が一意である必要はない。条件が少し変わった時に関係の無い作業まで動かないようにするのは「最小の組み直し」で、前の計画との差を目的に入れて別に扱い、試験で確かめる。（前の版の「目的に小さな順位の項を足して一つに決める」は、一意を保証しないので改めた）

**解の状態と、画面の状態**：

| 画面の状態 | 意味 | 求解の結果 |
|---|---|---|
| 決めてよい | 確定した条件だけで実行できる | OPTIMAL か FEASIBLE（条件待ちを含まない） |
| 返事しだい | 返事・承認・受理が来れば実行できる | 同上（条件待ちを含む） |
| 聞いてから | 答えで決め方が変わる事が、まだ分からない | 問いの判定（§6） |
| このままでは無理 | 今の条件と取れる手では間に合わない | INFEASIBLE |
| まだ判断できない | 時間内に計算が終わらない | UNKNOWN |

- FEASIBLE は「実行できるが、最良とは限らない」。UNKNOWN は「無理」ではない。入力や組み立ての誤りで解けない時は、作りの誤りとして記録して直し、家族には「計算の誤り」と出す。
- 「このままでは無理」の時は、家族が足せる手（担任に相談して日を変えてもらう、有休の上限を一日増やす、祖母に頼む日を増やす等）を一つずつ足して解き直し、解ける物を代償の順に示す。一つで解けなければ二つの組を試す。全部試しても解けない時は、そう示す。

## 9. 検証器

求解のコードに依存しない、別のコードで確かめる。毎回の計算の後と、試験で走らせる。

- 置いた作業が、担当の空き時間・場所の開いている時間・最早の開始と締切の中にある。人ごとに重ならない。先後と待ち時間を守る。
- 生きている作業は、どれも生きている根拠をたどれる（要件が今の事実で適用され、案が選ばれている）。根拠の消えた作業が残っていない（取り消しの連絡と済みを除く）。
- 必須の手配は、選んだ案で満たされるか、「返事しだい」「このままでは無理」として理由付きで示されている。
- 確定の引き受けに、待っている条件がない。「引き受ける」「断る」「済んだ」「できなくなった」は、本人の操作から来ている。
- 決め時の過ぎた案を勧めていない。
- 日付と曜日が合っている。

検証器が確かめるのは、モデルに入れた条件だけである。読み取りで落ちた要件は、ここでは見つからない。それは出典の表示、文の網羅（全ての文が、どれかの事項か「関係なし」に入ったか）、家族の確認で減らす。事項のある文と確かめてほしい文に、計画に入れたか・よていに出すか・読んだだけ（まだ計画にも知らせにもしない）か・確かめてほしいかの印を付け、「何もしない」と「まだできない」を家族が見分けられるようにする。

性質ベースの試験（fast-check）：架空の家族とおたよりの型から、ばらばらの事象の列を作り、毎回、検証器が通ることと、同じ列の再生が同じ状態になることを確かめる。

## 10. Claude の呼び方

| 呼び出し | 入力 | 出力 | モデル（初期値） |
|---|---|---|---|
| 書き起こし | お知らせの写真・PDF | 書かれた文字を、読む順にそのまま行ごとに（読めない字は〓） | Opus 5.5（effort medium・速いモード） |
| 読み取り | 出典の文（写真・PDF は、書き起こして家族が確かめた文）、届いた日、学年度、関係する出典の今の事項（ID付き） | 事項、未定の値、前の事項への作用、二通りに読める所 | Opus 5.5（`claude-opus-5-5`、effort medium・速いモード） |
| 準備の推定 | 要件と、家族の情報の要約 | 書かれていない準備（推定と理由） | Opus 5.5 |
| 一言の解釈 | 家族の一言と、今の作業・頼み事・未定の値・事項 | 記録の種類と対象の ID、問いの参照、仮の話（断られたと仮に置く頼み事）、受け付けられない理由 | Opus 5.5（effort medium・速いモード） |
| やり方の案 | 「すること」の欄と元の文、家族の考えとそれを書いた大人、家の大人・頼める人・場所・やり方（手順の名前を含む）の名前と ID | やり方の案（手順・する大人・頼む相手・場所・見込み）、使える今のやり方、足りないこと。外の事実（値段・返事の早さ・締切の決まり・受け持てる時間）の欄は無い | Opus 5.5（effort medium・速いモード） |
| 説明 | 計算の結果（理由、差分、代償） | 短い日本語 | Sonnet 5.5 |
| もしも | 家族の問い | 今は一言の解釈に含める（どの返事待ちの頼み事が断られたら、かを読む。計算と説明はコード。02-foundation §5.6） | （一言の解釈と同じ） |
| 店の種類 | 品物の名前だけ | 地図で店を探す言葉の案 1〜3 個（推定。家族が確かめて（要れば直して）「探す」を押した時だけ探す。2026-11-04、store-kinds.v1） | Opus 5.5 |
| 頼み事・取り消しの文 | 計算の結果、相手、相手の言葉 | 下書きの文（送るのは家族） | Sonnet 5.5 |

- 出力の型は、構造化出力で固定する。型は §3 の Zod から作る（TypeScript の SDK の `zodOutputFormat` と `messages.parse`）。再帰、数の範囲、文字数の制約は API が受けないので、Zod の検証と業務の検証（日付・文 ID・参照・状態）をコードで行う。拒否（`refusal`）と打ち切り（`max_tokens`）の出力は、有効なデータとして扱わない。
- Opus 5.5 は思考を切れず、effort の初期値が medium なので、呼び出しごとに明示する。
- 今動いている四つの呼び出し（書き起こし・読み取り・一言の解釈・やり方の案）は、どれも Opus 5.5・effort medium・速いモード（`speed: "fast"`。出力が速い。料金は標準の 2 倍）にそろえる（作り手の指示 2026-11-04：家族は画面で答えを待つので、費用より読みの確かさと速さを先にする）。設定は `apps/server/src/reading/model.ts` の一か所。速いモードで答えたかは、応答の usage.speed で分かる。
- 写真・PDF は二段で読む。まず書き起こし（書かれた文字だけを、要約も訂正もせずに）を、家族が写真と並べて確かめ、直してから、文として読み取る。読み取りの文 ID は、確かめた文に付く。写真はサーバーにも記録にも残さず、出典には写真から書き起こした文と示す。
- 家族の情報の住所・名前・ふだんの週は、Claude への入力に足さない。Claude に要るのは、原文と、品物と地域の種類までである。ただし、原文や写真そのものに住所や名前が含まれ得るので、実在の家族の物は、作り手が許した範囲だけを送る（02-foundation §11）。
- 一言の解釈（ひとこと）：モデルは、一言を今の作業・頼み事・未定の値に結び付けた候補を返すだけで、家族に見せる文を書かない。対象があるか、話した人が担当か、今の状態で効くか（返事待ち・まだ送っていない等）はコードが確かめる。前提に入れる作業は「きょう」に出る物（選んだ案の作業と、取り消しを伝える作業）だけで、比べるための候補の作業は入れない。未定の値には、読み取りが宣言した値に加えて、持ち物の「家にあるか」（ある・ない。用意の締切の前か、書かれた使う日が終わるまでは、答えた後も。買い終えた後は今の答えを空にして。買ったことは、家にあることを示さない）を入れる。その答えの候補には、見せた品物をサーバーが控えとして付け、押すまでに品物が直されていれば記録しない（02-foundation §5.3）。家族が押すまで何も書かない。候補ごとに、見せた時の対象（何か・日・相手・状態）の控えをサーバーに置き、押した時に家庭を押さえた中で今と比べ、違えば記録せずに見せ直す。頼み事の日時は、送ったと記録した時の計画の控えを使う（同じ相手への同じ日の頼み事を、時間で見分ける）。これは家族が実際に送った文の中身ではない（送る文は家族が直せ、システムは確かめない）。画面で見分けのつかない候補は選ばせない。一言の一部が別の大人の作業なら、話した人の分だけを黙って記録せず、その人が記録すると示す。仮の話（「おばあちゃんがダメだったら？」）は記録の候補にせず、今返事を待っている要る頼み事だけを候補として返し、家族が押すと「断られたら？」と同じ書かない計算を見せる（02-foundation §5.6）。モデルが、本当の返事か仮の話か決められない、または一つの一言に両方が混ざると読んだ時（replyOrWhatIf）は、ほかの欄に関わらず、どちらの候補も出さず、分けて伝えてもらう（utterance.v2。読み違いはあり得るので、候補は家族が確かめてから押す）。
- やり方の案（W4）：モデルは案の形だけを返し、何も書かない。ID・引用・新しい名前・数の範囲・頼める人に頼む数はコードが確かめ、家族が表に写して直し、変わることを見てから保存する（02-foundation §3.4）。外の事実（値段・相手の返事の早さ・締切の決まり・受け持てる時間）は、出力の形に欄を置かないので、モデルの数を受け取らない（書かれていれば、確かめてほしいことに原文の言葉で書かせる）。家族の考えの「私」がだれかは、頼んだ大人として渡す。家の大人・頼める人・場所・やり方と手順の名前を送る（上の「足さない」の例外。送る物は押す前に画面に出し、欄を送らなくても、送る文と名前に書かれた事は送られると書く）。
  - 一言の前提には、家族・頼める人の名前が入る（上の「足さない」の例外）。そのため、今はデモと、架空の家族だけを入れる試しの家庭で開ける。実在の家族に使う前に、名前を役割に置き換えるか、作り手が送る範囲を決める（02-foundation §11 の門）。
- 日付は二段で扱う。Claude は書かれた表現（「5月30日(土)」「来週の月曜」「令和8年」）と解釈を返し、コードが曜日・学年度・祝日と照らす。
- プロンプトはファイルに置き、版を付ける。版は読み取りの事象に残る。
- 読み取りの版の記録：extract.v1 で架空の二通を読むと、延期の連絡の「衣装は、先日のお知らせのとおり」を、前の「白い長袖シャツ」と結ばず、新しい持ち物にした（要らない買い物の手配ができた）。v2 で「前の事項を指す言い方は、どれを指すか決めて replace を付け、決められなければ ambiguities に入れる」と足し、同じ二通で結ぶことを確かめた。録った応答は `data/demo/recorded/` に置き、試験とデモは API なしで走る。
- モデルは精度と費用を測って選び直す（`eval/` に記録）。

## 11. 技術の選択

2026-11-02 夕方、作り手と相談して改めた。期間の後も作り手のチームが続けて作ることを前提に、後で替えにくい物（言葉、保存、身元、契約）を先に決める。替えやすい物（地図、知らせの経路、求解）は、境界をはっきりさせて後で替えられるようにする。前の版（Python・SQLite）からの変更の理由は各行に書く。

| 物 | 選ぶ物 | 理由 |
|---|---|---|
| 言葉 | TypeScript（画面もサーバーも）、Node 24 | 型を前後で共有できる。作り手のチームが主に使う言葉で、期間の後も保守しやすい。性能は決め手にしない（待ちの多くは Claude と地図の返事）。CP-SAT の主な口が無いのが欠点で、§8 の手順で補う |
| 型と検証 | Zod。一か所に定め、API・保存・Claude の構造化出力に使う | 契約を一つにする |
| 画面 | React、Vite、PWA、react-i18next（日英）、Tailwind と shadcn/Radix | 携帯の幅から。ホーム画面に置ける |
| サーバー | Hono（Node の上）。画面・API・知らせの送り出し・定時の見直しを一つのサービスで。計画の計算はサーバーが正本で、画面ではエンジンを動かさない（デモも同じ道。02-foundation §7.1） | 軽く、型の付いた呼び出しを画面に渡せる。同じ源なので身元の扱いが易しい |
| 保存 | Postgres（Railway）、Drizzle | 家庭ごとの分離と、複数の家庭への広がりに耐える。SQLite から替えた |
| 身元 | 今週：作り手の家族が使う置き場所は、Cloudflare Access を門にする（許した大人のメールに番号を送る）。サーバーは毎回の要求で Access の署名付きトークンを確かめ（署名・対象・発行元・期限）、メールを家族の成員に照らす。トークンの無い要求は断る。期間の後：Better Auth のパスキーを、招待（期限・一回きり・成員に結ぶ・取り消し）と、失った時の取り戻しまでそろえて足す | 今週は、ログインのコードを書かずに、実在の家族のデータの前に確かな門を置く。成員と外の身元（提供元と、その中の ID）を別の表に持つので、提供元を足しても替えても、家族のデータは移さない。Access のログインが iPhone のホーム画面の PWA で崩れたら（別の源へ移る流れのため）、急いで作った認証には替えず、作り手と選び直す（Safari で使い、ホーム画面の知らせは諦める／実際の使用を待つ／確かめた上でパスキーを作る）。手元のデモはログインなし（架空の家族の中で大人を切り替える）。置き場所に出すデモ（作り手の試用）は、Claude の読み取りを呼べるので Access の後ろに置く（家族の家庭とは別の環境と設定。同じサーバーに両方を設定すると起動しない）。サーバーも、`/api/health` を除くデモの API の要求ごとにトークンを確かめる。静的な画面と health はアプリの側では確かめないので、ホスト全体を Access の対象にする。誰でも見られる公開のデモを置くかと、その時の門は G2 で決める |
| 置き場所 | Railway（アプリと Postgres、同じ内部の網。環境ごとに、画面と API を一つのサービスで同じ源から出す）、Cloudflare（ドメイン、Tunnel、Access、写真は R2）。外からの道は Cloudflare Tunnel だけにし、Railway の公開のドメインは作らない（同じ環境に置いたつなぎ手（cloudflared）が Cloudflare へ外向きにつなぎ、内部の網でアプリに渡す） | 作り手が両方の有料会員で、使い慣れている。Tunnel にしたのは、源が公開の入口を持たなければ、Railway に源の側の制限（Cloudflare を通った要求だけを受ける仕組み）があるかに頼らずに、Access を通らない要求を源に届かせずに済むため（2026-11-03、作り手と決めた。前は Full (strict) の前の代理を考えていた）。API はサーバーも確かめる（デモの API は `/api/health` を除く要求ごと、家族の家庭の API は要求ごとに身元と成員）。静的な画面と health、家族の家庭のサーバーにあるデモの口は、アプリの側では確かめないので、ホスト全体を Access の対象にし、源を公開しないことに頼る。実際の環境で、公開の入口が無いことと、トークンの無い要求が断られることを確かめるまで、「直接の要求は届かない」とは言わない。Railway の亜太の地域はシンガポールなので、処理と保存は日本の外になる。そう明記する。各環境の URL は、それぞれ最初に決める（Access と後のパスキーがこれに結び付く）。Railway の Postgres は一台なので、実際の家族のデータを入れる前に volume の控え（Backups）を設定し、合成のデータの別の DB で戻せることを確かめる（本物の DB で戻しを試さない） |
| 知らせ | Web Push（VAPID）。メールの予備は後の候補で、今週は作らない | PWA のまま送れる。iPhone は iOS 16.4 以上で、ホーム画面に置き、本人の操作で許可する |
| 地図 | Google Places（店・営業時間）、Routes（時間）。開くのは Google マップの URL | 保存は place ID と調べた時刻だけ。帰属を示す |
| 試験 | Vitest、fast-check（性質の試験）、Playwright（携帯の幅の通し）。保存は PGlite（速い試験）と、実際の Postgres（並行・移行・家庭の分離） | PGlite は接続が一つなので、並行は実際の Postgres で確かめる |
| 道具 | pnpm（ワークスペース）、Biome、tsconfig は strict | 依存を lock ファイルで固定する |
| 時刻 | 日付だけの物は日付として、時刻は時区付きで持つ（Asia/Tokyo）。Temporal と Intl。時刻は分の精度 | UTC への変換で日がずれないように |
| 祝日 | 内閣府「国民の祝日」のデータ | 出典と利用条件を `THIRD_PARTY.md` に書く |

ハッカソンの提出には、動かしている所も審査員のアカウントも要らない（提出は動画・公開リポジトリ・概要・Claude の使い方の答え）。誰でも、API の鍵なしに、一つのコマンドで手元にデモ（架空の家族、模擬の時計、録った Claude の応答）を動かせるようにする。架空の家族だけの公開のデモを置くかは G2 で決める。作り手の家族が実際に使う物は別に置き、公開しない。

置き場所：

```
package.json, pnpm-workspace.yaml
apps/web/        画面（PWA）
apps/server/     API、身元、知らせの送り出し、Claude と地図の呼び出し、事象の記録
packages/core/   型（Zod）とエンジン（適用・取り消し・決め時・問い・配置）
packages/verify/ 検証器（core の型だけを読み、エンジンを読み込まない）
data/demo/       デモの家族とおたより（架空の人・学校、実在の地理）
eval/            境界の場面・正解・比べる相手・採点（runs/ は Git の外）
spikes/          本体に入れない試し（置き場所・ログイン・知らせ・地図）
```

## 13. 多言語と地域

2026-11-02 夕方、作り手と決めた。

- 画面は日本語と英語。最初の版から全ての画面（設定、許可、日付、誤り、知らせ、空の状態、読み上げのラベル）を両方で持つ。初期は日本語で、大人ごとに切り替えて覚える。文言はキーに出し、日付や数を含む文を連結で組み立てない。ページの `lang` は画面の言葉に合わせ、原文の引用には原文の言葉を示す。
- 次の四つを分ける：画面の言葉、家族の地域と時区、外に出す文の言葉（相手に合わせ、分からなければ家族に聞く）、お知らせの原文の言葉。同じ家族で一人が日本語、もう一人が英語でも、従うのはその家族の日本の暦と学校の決まりである。
- 原文はいつも残す。英語の画面で訳を出すなら訳と示し、日付や条件は訳からではなく、原文から読んだ事実から取る。
- 地域が日本だけのうちは、地域を差し替える仕組みを先に作らない。家族の地域、IANA の時区、祝日・学校・学童の決まりを、データとして分けて持つ。二つ目の地域が要る時に抽象にする。
- 日付だけの物（2026-12-07 等）は、その地の日付として持ち、時刻は時区付きの時刻として持つ。
- 日英の用語は [glossary.md](glossary.md) に揃える。
