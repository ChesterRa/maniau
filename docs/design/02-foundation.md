# 地基の設計 — 正本・概念・生命周期・保存・書き込み

- 状態：初版（2026-11-02 夜）。作り手の指示（機能の細部より先に底層を固める）を受けて、二人が同じ問いに独立に答え、突き合わせて一つにした。
- [01-model.md](01-model.md) は、事実の型・決め時・問い・引き受け・求解・検証の中身を決める。本書は、その下の地基を決める。
  - 何を正本として記録し、何を導くか。
  - 概念の全体と、新しい場面の置き場所。
  - 識別とキー、生命周期、保存の表、書き込みの道。
  - 版、秘密、試験の層、実在の家族のデータの前の門。
- 食い違えば本書に従い、01-model を直す。
- 「確かめた」と書いた物は、今のコードを読むか、架空の材料で動かして確かめた。それ以外は決めた設計で、まだ作っていない。

## 1. 約束（不変条件）

地基の良し悪しは、次を守れるかで測る。機能を足す時も、これを破る形にはしない。

1. **元へ戻れる**：計画のどの物からも、元の文（と写真）へたどれる。
2. **確かでない物で決めない**：
   - 推定・食い違いの事項は、家族が確かめるまで、必須の要件を作らない。
   - 条件が分からない事項は、間に合わなくならない側で「条件しだい」として計画に残すが、確かな事実や、自動で進めてよい物としては見せない。
   - どちらも、条件が偽の事項も、前の事実を変える作用（日付を決める・置き換える・取り消す）を起こさない。
3. **計算はコード**：日付・決め時・条件・配置・検証は、コードで行う。モデルの出力で置き換えない。
4. **変わったら伝わる**：事実が変われば、要らなくなった作業と依頼が分かる。頼んだ後なら、取り消しの連絡の作業ができる。
5. **再現できる**：同じ事象を、同じ版のコードで、同じ時刻まで流せば、同じ計画になる（地図から引いた入力を除く。§2.3）。
6. **人が見た物は残る**：人が判断した時に見ていた物（提案の中身、送った依頼、知らせ）は、その判断と一緒に記録する。後でエンジンが変わっても、「あの時なぜそう言ったか」を示せる。
7. **誰かが持つ**：生きている作業は、どれも担当（提案を含む）があるか、「担当がいない」と示される。
8. **家庭を混ぜない**：どの読み書き・仕事・写真の取り出しも、確かめた身元の家庭の中だけで行う。
9. **消せる**：敏感な中身は消せる。消した後に、消した物に頼る部分を「再現できる」とは言わない。
10. **分からないと無理を分ける**：読めない、探し切れない、データが無い時は「まだ判断できない」「要確認」とし、「無い」「無理」「取り消された」とは言わない。

## 2. 正本と導く物

### 2.1 正本は三つの組

| 正本 | 中身 | 変わり方 |
|---|---|---|
| 事象の列 | 家族がした事と、外から来た物の順。家庭ごとの通し番号 | 追記だけ（例外は §6.4 の削除） |
| 消せる中身 | 原文・書き起こし・写真・読み取りの出力・家族の情報・答えの値・提案の控え・依頼の文 | 事象から ID で指す。消せる |
| 今の権限 | 成員が有効か、ログインの身元とその対応 | 表の今の値が正本。古い事象を流し直しても、止めた成員の権限は戻らない |

- 計画・各自の「きょう」・問い・知らせの予定は、この組と今の時刻から、毎回作る。保存しない（§6.1）。
- 運用の表（操作の記録、知らせの意図と結果、仕事、削除の記録、API の呼び出しと費用、Push の登録）は、家族の事実ではない。
  - ただし、それぞれの運用については、それ自体が正本である。上の三つから作り直せない。
  - 例：操作の記録を失うと、送り直しの冪等が崩れる。結果不明の知らせの記録を失うと、二度送る。
  - 同じ DB に置き、同じ控えに入る（削除の記録だけは、控えの外にも置く。§6.4）。
- 家庭ごとの削除では、運用の表も消す。残すのは次の二つだけで、どちらも家族の中身を持たない。
  - 削除の記録：ID だけ。控えの保持期間が過ぎたら消す。
  - 費用の集計：家庭に結び付かない回数と費用。

### 2.2 記録する物と導く物の決まり

- 人がした事と、外から来た物だけを記録する。
- 時間で決まる状態は、記録せず導く。例：決め時が過ぎた、問いの期限が過ぎた、営業時間の情報が古い、決め時を過ぎても始めていない。
- 人が判断した時に見ていた物は、判断の事象と一緒に記録する（§1 の6）。
- 外への作用（送った・返事があった・取り消しを送った・知らせが受け付けられた）は、作業の状態から逆算せず、それぞれの事象として記録する。

### 2.3 正本に入れない外の入力

- 地図の結果（店の候補、営業時間、道のり）は、条款のため正本に入れない。計算の時にその時に引いた物を入力として使い、計画には place ID と調べた時刻を付ける。
  - 形（2026-11-04）：エンジンの三つ目の入力 `MapInputs`（`computePlan(events, now, maps)`）。店ごとに、家庭の店の ID・Google の place ID・駅の ID・駅の place ID、駅 → 店と店 → 駅の徒歩（別々に照会）、照会の日から7日の営業時間（current。覆う日は [照会の日, +7)）と、ふだんの営業時間（regular）。四つの ID が家庭と合う時だけ使い、合わなければ家庭の目安。計画は使った根拠を `mapInputs` に添えて返し、検証器は家庭の正本（householdSet）と、この根拠を分けて照らす。
  - 要求ごとに引き、同じ要求の画面・命令・予覧・一言の対象選びは同じ根拠を使う。要求をまたいで使い回さない（Google の条件は、緯度経度と place ID のほかの取り置きを認めていない）。
  - 営業時間：current の日は確か（区間が無ければその日は閉まっている）、regular は目安（その日の臨時の休みは確かめていない）。regular か、分からない営業時間でしか置けない買い物は、買える時が過ぎたとも閉まっているとも言わず、まだ判断できない（理由 inputMissing、storeHours）。「きょう」には、店をまだ確かめられないと出す。
  - 店探し（2026-11-04）：家族が押した言葉を、そのまま Google の文の検索に送り、家の最寄りの駅から歩いて 15 分までの店を返すだけで、取っておかない。家族が選んだ店は、place ID・家族の呼び名・扱う品物（その品物の名前）だけを家庭に足す（家の情報の直し。見る → 保存）。品物の名前を持つ店があれば、エンジンは店の種類の対応表より先に、その店で探す（選び直すと、前の店からその品物の名前を外す）。家の情報の見る・保存の要求は、今の家庭と直した後の家庭の両方の店の根拠を引く（新しく選んだ店も、見た時に置ける）。選んだ店の道のりが根拠にも家庭の目安にも無ければ、置けないとは言わず、storeHours で未定にする。
- そのため、過去の計画の地図に頼る部分は、後から正確には再現できない（01-model §2）。§1 の5の「再現」は、地図に頼らない部分と、家族が入れた営業時間・道のりの目安について言う。
- 家族が確かめて入れた物（自分の使う店の営業時間など）は、家族の情報として正本に入る。

### 2.4 外とのつながり（カレンダー・LINE）

- 今週は、確定した事の書き出し（ICS）と、家族が写して送る下書きまで（02-product §5.3）。下書きを、送った事として扱わない。送ったかは、家族の「送った」の記録だけで決める。
- 後で Google カレンダーや LINE とつなぐ時は、それぞれを別のつながりとして足し、家庭・外の ID・許可・重なりの取り除きを持たせる。同期や送り出しの受け取りは、新しい事実として事象に記録する。今は、つなぐための仕組みを先に作らない。

### 2.5 計算の後の検証

- 毎回の計算の後に、検証器を走らせる。
- 違反のある部分は、「決めてよい」と見せず、それに頼る知らせも出さない。画面には「確かめられませんでした」と出し、違反は運用の記録に残して直す。
- 違反が計画全体に及ぶか、どの作業・知らせに響くかを絞れない時は、響き得る物を全部止める。はっきり切り分けられる時だけ、残りを出す。
- 未判定は違反と分けて扱い、未判定であることを画面に出す（隠さない）。未判定の前提に頼る作業と知らせは、確かな事実として見せない。

## 3. 概念の全図

### 3.1 地図

```
家庭
 ├─ 成員：大人・子・頼める人（祖母）  ── 身元（ログイン。大人だけ）
 ├─ 所属【新】：子 × 通う所（学校・園・学童・習い事・塾）、始まりと終わりの日
 ├─ 資源【広げる】：家・駅・職場・店・郵便局・診療所・薬局・通販
 │      営業時間（出典と調べた時刻）、扱う物・できる事、道のりの目安
 ├─ ふだんの週：大人も子も、曜日ごとの区間（在宅・場所が決まらない、も選べる）
 │      その日だけの一日（2026-11-04）：大人のある日の区間の全部。その日はふだんの曜日より先に使う
 ├─ 習い事・塾の決まり【新】：毎週の回（曜日・時刻・場所）と、回ごとの決まり
 │      （試合の日はユニフォーム、月謝は1日まで）。決まりの変更は効く日を持つ
 ├─ 取れる手【広げる】：子の居場所（学童・有休・祖母）、買う（店・通販）、用事（郵便局など）
 └─ 分担の決まり【新】：作業の種類ごとに、誰に提案するか

出典（文字・写真）→ 事項（種類、元の文、条件、証拠の状態、前の事項への作用）
                    │      ↑ 未定の値 ← 答え（家族・後の出典）
                    ↓
                  要件（何を、いつまでに、どの子の）
                    ├─ 選べる方法がある → 手配 → 案（手順・代償・決め時）→ 作業
                    └─ 方法が一つ　　　 → 作業
作業 → 引き受け（本人。提案の控えと一緒に）→ 依頼（送った時の控え）→ 返事
                                              └→ 要らなくなれば、取り消しの連絡の作業
知らせ：担当の本人だけに、もう待てない時だけ
```

流れ（出典→事項→要件→手配・案→作業→引き受け→依頼）は、新しい場面でも変えない。新しい概念は【新】の三つと、資源・取れる手の広げ方だけにする。

### 3.2 新しい場面の置き場所

| 場面 | 入口 | 事項・回 | 要件 → 作業 | 境界 |
|---|---|---|---|---|
| 連絡帳（毎日） | 写真の出典 | 持ち物・宿題とサイン・テスト・当番・プリント。「あした」はコードが日付にする | 持ち物 → 前の晩の用意。家にあるか分からなければ問い、無ければ買う手配。サイン → その晩の作業（出す日が書かれていなければ、締切を作らずに二人へ出す）。テスト → 家族が決めた日数の前に、子へ声をかける作業。当番 → うちの番の物を、書かれた時間の作業に（ずらさない。日だけなら時刻なしで引き受ける）。うちの番か分からない物は、対象を添えて確かめる。「うちの番です」「うちの番ではない」は家族の言明として、言った時の用件と対象に結んで持ち、読んだ中身の確かめ・直し・取り下げとは分ける（直された対象に、前の言明を当てない。言明は事項の確かさも作用も変えない：「うちの番ではない」で、ほかのお知らせの置き換えを戻さない。「うちの番です」で、推定の中身を確かな物にしない。出典の画面から言い直せる） | 「プリント1まい」から中身を作らない。日付だけの締切は日付で持ち、無い時刻を作らない（指した文に見つからない時刻は、コードが落とし、その文を確かめてもらう。時刻の書き方は数え切れないので、見つからないことを「書かれていない」証拠にしない）。午前・午後の無い時刻は、同じ句（読点・句点・日付で区切る）の前に、午前・午後か 24 時制（09:00、15時）の時刻があれば、それに合わせる（つなぎの言葉を見分けられなくても、外れた読みを書かれたとしない。別の日・別の句からは受けない）。前に何も無い「9時」は、どちらの読みも受ける（残る危険）。読んだ時刻を画面から直す入口は、まだ無い（締切はその日の朝8時を目安にして日だけを見せる。始まりを確かめられなかった当番は、時刻に置かず、書かれていないとは言わずに元の文を確かめてもらい、その日の始まりを目安に早めて知らせる）。勉強の仕方は助言しない |
| 習い事・塾 | 所属と決まり（家族が設定）、クラブからの連絡（出典） | 決まりから導く回。連絡は、ある一回への作用（中止・時刻や場所の変更・練習から試合へ） | 回ごとに、決まりから持ち物・送り迎え・月謝の作業。送り迎えが勤務と重なれば子の居場所の手配。**今週の実装**：クラブからの行事（送り手が club）に、家庭の子が一人で、その子に送り迎えの決まり（clubEscort：送り・迎えのどちらが要るか。家族が入れる）がある時、送り・迎えの作業を作る。書かれた始まり（送り）・終わり（迎え）の前後に、片道 30 分の目安の往復で決まった作業にし、書かれた時刻はずらさない（道のりは確かめていないと画面に書く）。終わりが始まり以前か、元の文に「翌日」などとある時は、当番と同じ決まりで 12 時間までは次の日の迎え。それでも迎えの日を決められない時（終わりだけで始まりが無い、次の日でも 12 時間を超える、読み取りが終わりを落とした、終わりが書かれていないのに「翌日」などとある）は、行事の日を迎えの日として見せず、日時の無い作業（行事の日を添える）にして、元の文で確かめてもらう。時刻の無い方はその日の作業（読み取りが落とした始まりは、確かめてと印を付ける）。「今回は要らない」「今回は要る」は家族の言明として、言った時の子・用件・その方の日・時刻・場所に結んで持つ（どれかが変われば当てない）。行事の確かさも作用も変えない。出典の画面から言い直せる | 一回の中止と、以後の決まりの変更を分ける（一回の雨天中止で翌週を消さない）。祝日や振替が分からなければ未判定。子が二人以上の家庭では、決まりのある子が一人でも、どの子の行事か分からないので、送り迎えを作らない（決まりは送り迎えのしかたで、お知らせがその子の物という根拠ではない。所属で子と結ぶのは後）。行事が短く、送りと迎えの往復が重なる時、同じ大人は後の方を置けない（待つ間を作業にしていない）。送り迎えが勤務と重なる時の子の居場所の手配は、まだ作らない。日を決められない迎えは、知らせない（「きょう」に出すだけ） |
| 買い物 | 持ち物の要件 | — | 手配の案：帰り道の店（寄り道）、昼休みの職場の近くの店、通販（家族が入れた「何時までに注文すれば何日に届く」の目安）、祖母に頼む。それぞれ決め時を持つ | 通販のアカウントにつながず、支払いを扱わず、在庫や届く日を言い切らない。目安は目安と示す |
| 用事 | 家族が書いた一言（家族の文字の出典） | 用事（例：金曜までに書留を出す） | 手配の案：家の近くの郵便局（土曜の朝）、職場の近く（昼休み）。営業時間と決め時 | 手で入れる別の道は作らず、出典と同じ道を通す |
| 診療所 | 資源として、家族が自分の使う所を登録 | — | 営業時間・休診日を、予定を組む時の制約に使うだけ | 「どの病気でどこへ」は言わない（医療の助言をしない） |

### 3.3 最初の設定

- 最初に集める：家、学校・園・学童、大人それぞれの職場と通勤。在宅・場所が決まらない、も選べるようにして手間を減らす。
- 家の位置は、住所か地図の点を入れられる（家まわりの店や寄り道の道のりに要る）。駅や町の粒度だけを選んでもよく、その時は道のりを「粗い目安」と示し、家の戸口までの正確さを約束しない。より細かい位置を出すことを強いない。家の位置は消せる中身として持ち、Claude には送らない。
- 後で、使う場面が来た時に聞く：店の好み、細かい決まり、資源の追加。
- 欠けていても、エンジンは止まらない。欠けた所に頼る計画は「入力が足りない」という理由付きの未判定にして、要る時に聞く。
- 寄り道の計算には職場と通勤が要るので、最初の設定を駅と大まかな時間だけに縮めない。
- **今週の実装（うちのこと）**：計算に使う家族と暮らしの情報（人・ふだんの一週間・場所と店・取れる手）を一つの画面で見せ、それぞれ何の計算に使うかを一行で添える。直す時は、保存の前に「この変更で変わること」を見せる：同じ命令（updateHousehold）を書き込まずに展開し（頼み直しを含む）、今の計画と比べた差分（planChanges：増える・無くなる・時刻が動く・時刻を置けなくなる／置けるようになる・担当が替わる・中身が替わる・行く所（店）が替わる・手配の要る時間が変わる／新しく要る／要らなくなる・引き受け直し・要らなくなる引き受け（今の計画に見つからないだけの物は、要らなくなったとは言わず、まだ要るか確かめてもらうと書く。札・知らせと同じ）・取り消しの連絡・頼んだ相手への確かめ（頼んだ時間や根拠が、送った時と変わる依頼）・手の決め時（確かさも渡す。決め時を計算できなくなる手は、もう間に合わないと言い切らず、確かめられないと書く）・重なり）と、直した後の家の情報で確かめた新しい違反と、新しく確かめられなくなった点（「問題なし」とは言わない）。保存は、見た時の計画の番号と、見た物の要約（送った直しを含む）が、押さえた中で今の時刻に作り直した物と同じ時だけ（もう一人の直しや、時が進んで変わった結果を黙って書かない）。直せる範囲はエンジンが正しく扱える物に限る：成員は消さず、ID・種類・有効を替えない（身元の正本は成員の表。止めるのは §5.9 の別の操作）。足せる成員は頼める人（やり方の外の相手。ログインしない）だけで、成員の表にも同じトランザクションで足す。場所は消さず種類も替えない（店・頼める人の家・そのほかの場所は足せる。家は足せない。営業時間は無くてよい）、営業時間は同じ日の中の区間だけ、取れる手は締切の決まりの数と代償だけ（画面で直せるのは、今は締切の決まり）、大人のふだんの一日は前からある曜日を消さず、直した日は区間を切れ目なく続ける（書かれていない時間を作らない。画面は、つながっていた隣の区間を一緒に動かす）。営業時間の調べた所と時刻はサーバーが付ける：区間か休みの日を直した時だけ、家族が確かめた物として今の時刻にし、直していない店は、送られた値によらず今の記録のまま。子の居場所の手配が要る時間は、有効な大人の誰もが「家」以外の区間（通勤・仕事・迎え・外出）にいると書かれている時間の重なり（「家」の区間だけを子を見られる時間として数える。家で仕事をしていて見られない時は「仕事」と書く。画面の「使う所」にも書く。過ごし方と場所は食い違わせない：「家」は家の場所、外出・迎えは家以外。画面は過ごし方を替えると場所も合わせ、サーバーは食い違いを断る。朝だけ家にいて帰らない日や、一日中出かけている日は、その外の区間の全部が手配の要る時間になり、手配は黙って消えない。一日は家で始まり家で終わるとし、最初の区間の前と最後の区間の後は家にいるとする（画面の「使う所」にも書く。起きる時刻を遅らせる・一日の終わりを早めるのは、家にいる時間が延びるという言明になる）。区間の間の空きは、直す操作では作れず、前からある空きは家の外とは決めない。その日の区間が無い大人は、分からないので数えず、ほかの大人だけで決める（初めの設定の限界。直す操作で曜日は消せない。分からない時間をすべて防いだとは言わない）。まだしない：初めの設定の手順、取れる手を足すこと（新しい手は、やり方の表で足す。§3.4）、頼める人を止めること、項目ごとの出典（営業時間のほかは、事象の誰・いつで代える）。

### 3.4 通用の「すること」とやり方（今週の実装）

場面ごとの専用の分岐を足さずに、新しい用事を同じ流れ（出典→事項→要件→手配・案→作業→引き受け→依頼）に載せる入れ物。

- 事項の種類 need：何を（what）、形（shape）、だれのため（forMemberId。家族が選んだ時だけ。家庭の成員に限る）、場所・条件。形は二つで、一つの need は一つの形だけ（直しで形は替えない。替えるなら言い直す）。
  - by（いつまでに済ませる）：締切が要る。日だけの締切は、その日の終わり（23:59）まで。
  - window（ある時間、だれかが要る）：同じ日の始まりと終わりが要る。欠けた窓・日をまたぐ窓は受けない（時刻を作らない）。
- 入口（どちらも同じ need になる）：家族の言明（stateNeed：家族の一言の原文と、家族が画面で確かめた欄。サーバーが、家族の出典と、その出典の事項（evidence stated）に展開する。出典と事項の ID に原文を入れない）と、お知らせの読み取り（extract.v4。下の読み取りの決まり）。言明の直しも、言った時と同じ決まりで確かめる。
- 計画に入っている need（家族の言明か、家族が確かめた・直した読み取り）を直す・要らないにする（correctItem・dismissItem）：「すること」の画面の「中身を直す」「要らないにする」から。保存の前に「この変更で変わること」を見せ、見た計画の番号と見た要約（seen の changes）が、押さえた中で今の時刻に作り直した物と同じ時だけ書く（無ければ seenRequired、番号が古ければ proposalChanged、要約が違えば consequencesChanged）。直すと中身が替わり、選んだやり方は選び直し（前の中身への選び・引き受け・「はい」を今の中身に当てない。送った依頼は相手への確かめにし、取り消しとは決めない）。要らないにすると手配が生きていなくなり、引き受けは要らなくなり、送った依頼には取り消しの連絡が要る（同じお知らせのほかの事項は残る）。お知らせから読んだ物は、理由（もう要らなくなった・うちには関係なかった・読み取りが違っていた）を選べる（家族の言明は聞かない）。まだ確かめていない読み取りは今の決まりのまま（見せた番号だけ）。初めての読み取りなら、計画に無く、作業も依頼も無い。読み直した後で確かめを待つ物には、前の中身で送った依頼や引き受けが残ることがあり、外すと取り消しの連絡が要る（§5.6）が、今はそれを前もって見せない（読み直しを起こす入口〔書き起こしの直し〕が、画面にも命令にもまだ無い。入口を作る時に、見てから書くようにする）。形は直しで替えない（違えば要らないにして、足し直す）。「だれのため」を選ばないにすると、前の物を外す（直しは前の欄に重ねるので、外す時は null を送る。事項の解釈には null を残さない）。言明か読み取りかは、出典に読み取りがあるかで決める（送り手が家族のお知らせでも、モデルが読んだ物は読み取りとして、条件の注意と外す理由を見せる）。見せる口（previewChange）は「すること」の事項だけ受ける（ほかの事項は previewNeedOnly で断る。今の札の確かめのまま）。
- お知らせからの読み取り（extract.v4）：読み取りの構造化出力に形（shape：none・by・window）を足した。need は、家の人に求められている行動で、ほかの種類で作業にならない物（出席・参加・窓口や電話での申し込み・連絡）だけ。提出物・持ち物・家の人の宿題（サイン）・当番と同じ用事は need に重ねない。行事や締切は事実として残し、同じ文が家の人の出席や申し込みを求めていれば、別に need を作る。主催者がする事・問い合わせ先・子の当番は need にしない。だれのためかは推さない（家族が選ぶ）。書かれた対象（各家庭から大人1名）と場所は書かれたまま持つ。条件（希望する家庭は）は、ほかの事項と同じく未定の値と条件で付け、家族が決める値は家族の問いになる。締切は、時刻が書かれていれば時刻つき、日だけなら日付だけで返させる（書かれていない時刻を付けさせない）。変換は、文に書かれていない時刻を落として日だけと印を付け（deadlineDayOnly）、時刻が確かでない時（付けた時刻が文に無い、日だけで読んだのに文に読める時刻か時刻らしい言葉〔朝・放課後・登校前など〕がある）と、形の欄が足りない時（形が無い、窓の日・始まり・終わりが無い、日をまたぐ、締切が無い。問題 needIncomplete）は、その文を家族に確かめてもらう。「あしたまでに」の締切は、コードが決めた日と違えば食い違いにする。v3 までに録った応答は書き換えず、形を none として読む。
- 確かめるまで計画に入れない：モデルが読んだ need（家族の言明でない出典の need。送り手が家族でも同じ）は、家族が確かめる（confirmItem）か直す（correctItem）まで、要件（unconfirmed。日・締切を持たない）だけにし、手配・作業・頼む文を作らない。締切の書き方は数え切れず（候補の日・打ち消した日・「登校前」）、変換では正しい締切と確かめ切れないため（変換の印は、確かめる文を示すだけ）。外す（dismissItem、読み取りが違う）と要件にもしない。食い違う・推定の読み取り（ほかの種類では要件を作らない）も、確かめを待つ要件にして札に出し、直せば計画に入る（黙って捨てない）。確かめる前の作用（置き換え・取り消し・答え）は、効くか分からない物として扱い（先の事項は「しだい」になり、答えは数えない）、確かめれば効き、外せば元に戻る。読み取りの日時が過ぎていても、読み取りの条件で今は要らなくても、確かめるまで要件と札を残す（確かめていない日時や条件で、確かめの入口を隠さない。読み違えた過去の日や、原文に無い条件への答えで、まだ要る物が消えないように）。
  - 確かめ・直し・外しは、その時に拠っていた読み取りに結ぶ：その事項の出典と、条件の式の節点・そこに出る未定の値・答える未定の値・置き換えや取り消しの先の事項を持つ出典の、それぞれ採っている読み取り（と、見つからなかった物）。そのどれかを読み直した後は（同じ中身・同じ版の読み直しでも、替えて戻しても）当てず（前の直しも使わない）、また確かめてもらう。見つからなかった物が後で読まれた時も同じ（見せていない物に効かせない）。関係の無いお知らせの読み直しでは、やり直さない。書き起こしを直しただけ（読み直す前）と取り下げでは結びを替えない（読み直せばやり直す。取り下げた出典の事項は計画から外れる）。
  - 命令は見せた時の番号（seen.throughSeq）を要る。無ければ seenRequired、今より先なら seenAhead、見せた後に家庭の事象が一つでも増えていれば（見せた番号が今と違えば。ほかのお知らせの読み直しで、条件の値の名前が替わることもある）itemChanged、文を直して読み直す前なら rereadPending で断る（見せた読み取りは前の文の物）。確かめで効く物（条件の式・答える値・置き換えや取り消しの先）を、見分けられる形で画面に見せられない読み取り（節点・値の名前・出典が無い。同じ名前の別の問いや、同じ名前と日時の別の事項があり、お知らせ〔題と届いた日〕でも見分けられない）は、確かめ・直しを readingUnshown で断る（外すことはできる。要る物なら、外して「することを足す」で足す）。「合っている」は形のそろった読み取りにだけ（足りなければ needShapeMissing・needWindowMissing ほかで断り、直してもらう）。直しで形を替えない（読み取りに形が無い時だけ入れる。替えるなら needShapeLocked）。
  - 画面：大人の全員の「きょう」に確かめる札（needCheck）を出す。読み取り（何を・いつ。読み取れていない欄は、読み取れていないと書く）、条件（読み取りの式を、連結〔かつ・または〕と否定のまま。答えた後も同じ式を見せる）、ほかの事項への作用（置き換え・取り消しの先〔何を・いつ〕と、どの未定の値に何と答えるか。確かめるまで効かせないこと）。別のお知らせの値や事項には、そのお知らせ（題と届いた日）を添える、元の文（お知らせの全文。指した文を太字にし、指した文と前後の一文にたためる。指す文はモデルが選ぶので、指さなかった文が日時や条件を変えることがある）を見せ（食い違う・推定の読み取りと、確かめてほしい文を指す読み取りには、よく確かめるよう添える）、「合っている」（形のそろった時だけ）・「直す」・「読み取りが違う（外す）」・「うちには要らない（外す。notOurs）」を選んでもらう。読み取りの日時が過ぎた時と、今の答えで要らない時は、そう添える。「直す」の画面は、読み取りで欄を埋め（締切の形の日は締切の日。読み取りに日が無ければ空にし、家族が入れるまで保存させない。きょうの日で埋めない）、同じ全文と条件・答え・作用と並べて直してもらう（条件・答え・作用は直せない。違えば外す）。締切の時刻を空にすると日だけの締切、入れればその時刻（前の日だけの印を外す）。
- やり方（Household.ways）：家族が確かめたデータ。名前、手順、締切の決まり、覆う時間（covers）、代償、取り消せるか。手順は、名前・所要・置ける区間・場所・外の相手と返事の種類・担当・手順ごとの締切を持つ（前の日 21:00 までの予約と、当日 7:30 までの確かめを、両方守る。決まり onTheDay を足した）。受け持ち（cover）の印は、その手順をする人が窓の間を受け持つことを表す。外の相手に頼む手順なら相手が受け持ち（病児保育の予約、祖母に来てもらう。その窓・今の中身への「はい」が証拠。頼むのは前もって）、そうでなければ家族が受け持つ（窓の間その人がほかの作業をしない作業になり、その人のふだんの予定が窓の間ずっと手順の区間（家など）にあり、決まった場所ならその場所の営業時間（書かれていれば）の内にある時だけ置く。書かれた時間の当番と同じ。仕事の時間には置かない）。受け持ちの無い外の相手の手順（休みの承認など）は前提で、「はい」でもだれかが受け持つことにはならない。休みを取って家で見る（承認でその日の予定が変わる）は、まだ表せない。やり方は、家族が「うちのこと」で足す・直す・やめる（下の「家族がやり方を作る」）。Claude は案（推定）を出せるが、家族が表に写して直し、保存するまでやり方にならない（下の「Claude のやり方の案」）。
- 家族がやり方を作る（updateHousehold。保存の前に「この変更で変わること」を見せ、見た物と同じ時だけ書く。§3.3）：
  - 版：やり方の中身（名前・手順・締切・覆う時間・代償とその「分からない」・取り消せるか）の全部。どれかを直せば、選び・引き受け・送った依頼は前の版の物として当てない：選び直しが要る「すること」を見せ（planChanges の rechoose）、引き受けた作業は本人に要らなくなったかを知らせ、送った依頼は返事待ちのまま相手への確かめにする（家族が取り消したいとは決めない）。中身が元に戻れば、前の選びは戻る（選ぶの決まりと同じ）。
  - 消さない（ID は残る。前の選びと控えのため）。使わないやり方は「やめる」：家の情報の stoppedWayIds に入れる（やり方の中身は替えないので、版も今の選び・作業・依頼も替わらない）。やめたやり方は、これからは新しく選べない：選ぶ所に出さず（今の選びに入っている物だけ、印を付けて出す。残せて、外すともう選べない）、setNeedWays はそれを新しく足す選びを断り、本命・予備に選んでいない案を選ぶ命令も断る（wayInactive）。やめた時の「この変更で変わること」と一緒に、そのやり方を選んである「すること」を出し、外すならその「すること」で選び直すと書く（取り消しは、選び直しの「この変更で変わること」で見せる）。使い直すと、また選べる。計画の案には、やめたやり方の印（stopped）を付ける。予備の勧め・決める事の知らせ・断られた時の次の案は、今選べる案（決め時の前で、やめたやり方なら今の本命か予備の物）だけで数える。本命がまだ（か選び直しが要る）のに、今選べる案が無く、やめたやり方の案がある時（ほかの案は決め時を過ぎた時も含む）は、本命を選ばせず、やり方を選び直す所へ案内する（needStep の waysStopped。文は、やめた理由と決め時の過ぎた理由を混ぜず、今選べる案が無いとだけ言う）。
  - 足した・直したやり方の決まり（サーバーが断る）：名前と手順の題がある。ID は画面が作り、形を限る（比べるだけで、区切って読まない）。担当は有効な大人、外の相手は有効な頼める人か家以外の場所、決まった場所は家以外。手順の時間と返事を待つ時間には上限がある。代償の「分からない」は四つの欄の中で重ならず、その欄の値は 0（空の「分からない」は書かない）。成員と場所の名前（NFKC で揃え、前後の空白を除いて比べる。種類をまたいでも）は、新しく重ねない（nameTaken。同じ名前の物があると、画面でどれのことか見分けられず、別の人に頼むことがある）。比べるのは同じ名前の物の組で、前に無かった組ができれば断る（前からある重なりの名前へ、別の物を足す・名前を変えて入れる・一つと入れ替えるのも断る。重なっている名前の集まりや数だけでは、これを見落とす）。前からある重なり（同じ物どうしの組）は、ほかの直しを止めないが、その物をやり方の手順で新しく選ぶのは断る（前から選んであった物は残せる。画面は選べないと書いて選ばせない）。直していないやり方は、初めに入れた版のまま。画面に出さない欄（相手の無い手順の「次の手順まで空ける時間」、店の種類など）は、直す時も元のまま送る。相手を外した手順は、返事までに見込む時間も一緒に外す（画面にそう出してから見せる）。
- Claude のやり方の案（W4。way-ideas.v1、Opus 5.5・effort medium・速さは製品の切り替え〔01-model §10〕。場面の種類を持たず、どの「すること」にも同じ）：計画に入っている「すること」（生きている手配）の画面から、0〜3 件の案と、今のやり方で足りる時はそのやり方（reuse）、案を出す根拠が無い時は足りないこと（missing）を返させる。案は推定で、何も書かない（事象を足さない。デモは画面とサーバーのメモリだけ、家族の家庭は操作の表に要約〔ハッシュ〕だけ）。家族が案を選んで「やり方を足す」の表に写し、直し、この変更で変わることを見てから保存する（updateHousehold。上の決まりと同じ）。どの「すること」に使うかは、保存した後に家族が選ぶ。
  - 送る物：「すること」の欄（何を・形・日時か締切・書かれた場所）と元の文、家族の考え（任意、500 字まで）とそれを書いた大人（考えの「私」がだれか）、家の大人・頼める人・家以外の場所・やめていないやり方の名前と ID（やり方は手順の名前も）。家の情報のほかの欄（ふだんの週・子・場所の営業時間など）は送らない。送る文と名前（元の文・考え・人と場所とやり方と手順の名前）に書かれた事は、名前・住所・予定でも、そのまま送られる（画面の説明も、欄を送らないことと、書かれた事は送られることを分けて書き、文に住所や予定が無いとは言わない）。画面は、押す前にサーバーと同じ関数（wayIdeasContext）で送る物を作り、送る名前を見せる。

  - 検証器が独立に確かめるのは、事象からたどれる前後の版と、書いた人が有効な大人であること。見せた「この変更で変わること」と同じ時だけ書くこと（seen）は、サーバーが守る（検証器は、家族が見たことまでは確かめない）。

- 計算：選んだやり方ごとに案を作り、手順を締切の前に置く。本命・予備・返事・決め時の扱いは子の居場所と同じ。進める本命・予備の前もってする手順は、どれも実際にするので、子の居場所と同じく一つずつ置き、同じ人の時間で重ねない（置く順は、今ある置き方の中で、引き受けた時刻から動く作業が少ない物を選ぶ。前の時刻を保つとは限らない。置けない案には時刻を置かず、手配の理由に timeConflict を出す。選んだまま・引き受け待ちのまま）。本命が「はい」で決まって、もう進めない予備は、進める案に入れない（子の居場所と同じ）。比べるだけの案と、もう進めない予備は、今までどおり、ほかの用事のふさがりだけを避けて置く（進める案の作業も互いもふさがない。選ぶと進める案として置き直すので、選ぶと置けなくなる案は「選んだら」に timeConflict として出る）。ほかの用事へ渡すふさがり（後の「すること」の作業を置く時に避ける時間）は、時刻と担当があり、生きていて、済んでもやめてもいない作業のうち（済んだ作業は渡さない）、時間を使う作業（案の無い作業と取り消しの作業、進める案と勧める案の作業。勧める案は、検証器もほかの用事の進める作業と重ねさせない）と、本人が引き受けた作業（休む予備や、選んでいない案を引き受けた記録も、約束として守る）だけ。比べるだけで、勧めてもおらず、だれも引き受けていない候補は入れない（しない作業で、ほかの用事の決め時を早めない）。子の居場所と買い物から「すること」へ渡すふさがりも同じ。検証器の執行の範囲とは同じでない（引き受けた物を広く守る。2026-11-05）。窓の間の受け持ちは、進める案どうしのふさがりに足さない（今までと同じ。本命と予備の受け持ちが同じ人・同じ窓に重なる時の扱いは、別に決める）。作業の締切は、案の締切と手順ごとの締切の早い方。決まった場所の手順は（前もってする手順も受け持ちも）、その場所の営業時間が書かれていれば、その内だけに置く。書かれた休みの日は、前の日から続く夜の営業があっても置かない。営業時間の書かれていない場所と、地図（Google）から得た営業時間（有効な日・時区・臨時の営業を確かめられない）では、時刻で絞らない（閉まっているとは言わない）。決まった場所にいる区間がふだんの予定に無い手順（平日 9:00〜17:00 の窓口で申し込む等）の案は、決め時を出さず、過ぎたとも言わず、「ふだんの予定に置ける時間が無い手順がある」と示して勧めない（01-model §5）。家族は本命に選べ、その作業は時刻を置かず、いつするかを家族で決めてもらう。例：区への来年度の学童クラブの継続の申し込み（デモの家のやり方「区のホームページで申し込む」「地区センターの窓口で申し込む」。窓口は置けず、ホームページだけを勧める）。
- 覆う（window の need だけ）：今使う案のやり方の約束が全部そろい、受け持つ人が一人でもいる時だけ、覆ったと言う。外の相手に頼む手順はどれも（受け持つ相手も、承認などの前提も）、同じ窓・今の中身への「はい」（取り消していない依頼）があり、家族の受け持ちの作業はどれも、本人が今の中身で引き受けている（引き受け直しを待つ物は数えない）。受け持つ人のいないやり方（承認だけ）は覆わない。場所の書かれた「すること」は、家族の受け持ちでは覆ったと言わない（書かれた場所（原文）と、受け持つ人のいる家庭の場所が同じだと示せない。家族が二つを結ぶ仕組みと行き帰りの確かめは後で）。覆うのは covers があればその内、無ければ窓の全部で、残りの時間を notCovered として出す。病児保育の「はい」でも、預かる時間の外の朝と夕方は覆ったと言わない。
- 引き受けと済みの控え、依頼の控えは、need の中身とやり方の版（about）に結ぶ。違えば前の物を当てない（だれのため・日・やり方が替わっても、題と時刻は同じことがある）。前の物を当てなくなった後に元に戻っても、引き受けは本人にもう一度頼む（§4.2）。
- 見てから書く：言明とやり方の選びも、家の情報の直し（§3.3）と同じく、保存の前に「この変更で変わること」を見せ、見た物と同じ時だけ書く。
- 取り下げ：言明の出典を取り下げると、手配は無くなり、「はい」をくれた相手への取り消しの連絡が要る（お知らせの取り下げと同じ道）。
- 画面（場面の言葉を雛形に入れず、need の欄と、家族が登録したやり方のデータだけで組む）：
  - 足す表：家族の言ったことの原文（必須）と、計算に使う欄（何を・形・日・窓の始まりと終わりか締切の時刻・だれのため）。締切の時刻が空なら、日だけの締切（その日の終わり）。保存の前に「この変更で変わること」を見せ、断る理由（窓の欠け・日をまたぐ窓など）を出す。
  - きょうの札（大人の全員に）：家族が決めることが残る時だけ出す。やり方を選ぶ・選び直す、本命を選ぶ（勧めがある時も）、間に合うやり方が無い、選んだやり方のどれも、ふだんの予定で決め時を出せない（まだ判断できない。取れないとは言わない）、そして窓の need で、今使うやり方の約束を進め終えた後も受け持ちを確かめられない時間が残る時。返事待ち・作業の途中は、その返事と作業の札が出すので、窓の始まりの 26 時間前までは出さない。それより近ければ、返事待ちでも、まだ確かめられない時間を二人に出す（間際まで「決めることは無い」と見せない）。予備の勧めは、子の居場所と同じく、頼んだ本人に出す。札に出ない「すること」も、きょうの下の一覧からいつでも開ける。
  - 「すること」の画面：何を・いつ・だれのため・書かれた場所・家族の言明かお知らせか・元の文。まだ受け持ちを確かめられていない時間（時刻）と、何がそろえば受け持ったと数えるか（場所の書かれた need は、その場所にいるかと行き帰りを確かめていないことも）。本命を選ぶ所は、子の居場所の決める画面と同じ部品。使うやり方は、家庭のやり方を中身（手順と待つ相手・受け持つ人と時間・決め時・代償）つきで並べて選び、見てから保存する（家庭の並びで送る）。
  - 頼む文と取り消しの文：頼む文を作るのは、相手が受け持つ手順だけ。「すること」の何を（家族の言葉）・日・時間（締切の need は締切の日。書かれた時刻があれば時刻も）と、書かれた場所・だれの分（家族が選んだ時）を書く。前提を聞く手順（「鍵を預けてよいか聞く」）は、手順の名前が家族の側から見た言葉で、相手にしてほしい事とは限らないので、文を作らない（家族が書いて送り、送ったと記録する）。取り消しの文は、どのお願いかを送った時の控えで書く。人へは頼んだ時間か締切と何を、所へは頼んだ時間か締切だけ（同じ相手の同じ日の別のお願いを取り消したと読ませない。何をは家族の言葉で、子の名前を含みうるので、所への文には書かない）。控えに中身が無ければ今の事項から推さず、頼んだ時間だけで書き、札で確かめてもらう。文だけでは同じ相手の別のお願いと見分けられない時（同じ所に同じ時間の二つなど）も、推して書き足さず、札でどれかを書き足してもらう。作業の題には、何のための手順か（何を）を添える。
  - 返事を記録する所に、送った時の控え（頼んだ手順・何を・頼んだ時間か締切・場所・だれの分。控えの about から読む）を出し、相手が読んだ文ではないと書く（「はい」が覆う証拠になるので、何への「はい」かを見て記録する）。控えに中身の無い依頼は、今の値で埋めず、確かめられないと書く。
  - 決まった担当：作業の手配の種類で、取れる手かやり方かを決めて引く（ID が二つの集まりで同じでも、別の型の手順の担当を当てない）。
- まだしない：Claude のやり方の提案（ひとことから欄の候補を出すことも）、締切の need の依頼を頼んだ時の中身に結ぶこと、店のほかの場所の営業時間を画面で入れること（足した場所は営業時間が無いまま）、どの場所が時間を確かめる要る所かの見分け、やり方の手順の並べ替えと 4 つ以上の手順、頼める人の連絡先。医療の助言はしない（病児保育は、家族が入れた手立ての一つとして扱うだけ）。

#### 3.4.1 いつにするかの候補（相手の答えで日を決める。段 1）

窓の need の日を一つに決めず、候補を出して答えを集め、家族が一つに決める。場面ごとの種類を足さず、同じ need・同じやり方・同じ手配の流れに載せる（子を見てもらう日も、クラブの練習日も同じ）。

- 候補：窓の need に、日の候補（2〜8。日と始まり・終わり。同じ日の中）を持たせる（stateNeed の candidates か、setNeedCandidates）。候補の ID と代（rev）はサーバーが付ける。時刻を直した候補は代を進め、消した候補の ID は使い回さない。候補のある need の窓は、決めた候補（今の代）の時だけで、決めるまで手配・作業を作らない。
- 答える人（setNeedPeople）：家の大人・頼める人（成員）と、名前だけの相手（guest。ID はサーバーが付ける）。要る人（required。答える人の中から）と、少なくとも何人（minCount。答える人の数まで）。名簿から外した人の答えは数えず、戻しても外す前の答えは当てない。外すと、同じ命令の中でその人のリンクを止める。
- 答え（availabilityRecorded）：はい・たぶん（条件の一言）・むり・取り下げ。出所は三つ：自分の画面（self。本人の大人）、リンクから（link）、家族の記録（family。だれが記録したかを持つ）。出所ごとに最後の記録を見て、取り下げならその出所を未回答に戻す。答えの残った出所どうしで違えば食い違いで、まだとして数える。答えは今の代の候補にだけ当てる。
- 数え（コード。engine/when.ts）：はいの人数 L と、たぶん・食い違い・まだの人が全員はいなら何人か U。要る人に「むり」がいるか U が少なくとも何人に届かなければ満たせない、L が届いて要る人が全員はいなら満たす、ほかはまだ決まらない。答えで変わりうる人（その人の答えしだいで、条件を満たすかが変わりうる人。一人の答えで決まるとは限らない）は閉じた式で出し、0〜5 人の全ての答え・要る人・人数の組み合わせの数え上げと照らす（試験）。
- 候補ごとのやり方：選んだやり方を、候補の日に置いて読む。使えるのは、決め時が過ぎておらず出せる、前もって済ませる事が残っていない、やめたやり方でも使わない資源を使うやり方でもない、受け持ちに穴が無い（要る時）、手順を置ける、営業時間と行き帰りの時間が分かる、の全部の時だけ。やり方の選び（needWaysSet）は need に付けたままで、全部の候補の日に同じ組を使う。
- 勧め（コード）：答えの条件を満たす候補のうち、使えるやり方がある候補が一つだけで、その使えるやり方の代償に分からない物が無い時（onlyUsable）か、どの候補にも同じ一つの使えるやり方があり、はいの人数と決め時の両方で劣らず、どちらかで勝る候補（dominates）。ほかは勧めず、違い（人数・決め時・使えるやり方）を並べて家族が選ぶ。画面は数に合わせて言い（満たす日が一つだけか、そのうち使えるやり方があるのが一つだけか）、ほかにまだ決まらない日があれば添えて、一番良いとは言わない。使えると確かめられないやり方を「使えない」とは言わない。勧めは、やり方の相手と答えた人を結ばない（答えた人が来られない日でも、そのやり方の決め時は出る）。
- 決める（chooseCandidate。見てから書く）：決めた時の根拠（答える人・要る人・人数と、その候補への答えの要約〔たぶんの一言を含む〕）をサーバーが控える。今の根拠と違えば、何が変わったか（答える人・要る人と人数・答え）を出して決め直しを求める。別の候補か別の代に決め直すと、本命と予備を空にする（前の日の選び・引き受けを、新しい日に当てない）。
- 使った後は日を替えない（この版の限り）：その need の手配で、一度でも依頼を送った・作業を引き受けた・済ませた（履歴で見る。選ぶと同時の引き受けも含む）なら、決めた候補の時刻の直しと消し、別の候補への決め直し、候補の無かった前からの need に候補を足すこと、何を・場所などの直しを断る（decisionInUse）。替えるなら、要らないにして作り直す（画面もそう書く）。候補のある need の形・日・時刻の直しは、いつも断る（時刻は候補が持つ）。使う前の中身の直しは、全部の候補の代を進める（前の答えと決めを、古い中身に当てない）。
- 受け持ちが要るか（holdNeeded）：窓の need が、窓の間ずっとだれかの受け持ちを要るか。書かれていなければ要る（既定の値で埋めない。前からの事象の要約は変わらない）。要らない時は、受け持ちの穴を手配の理由に出さず、候補の使えるかにも数えない。
- 一人ずつの答えるリンク（デモの家庭だけ。家族の家庭では linksDemoOnly で断る）：
  - 鍵は 32 バイトのでたらめで、出した命令の応答で一度だけ返す（同じ操作の送り直しには付けない）。事象と表には sha256 だけを置き、計画と View にはリンクがあるかだけを出す。出し直すと前の鍵は効かない。
  - 頁 /answer#鍵：断片の鍵を、そのタブの sessionStorage に移して断片を消し、Authorization: Bearer で読み書きする（Cookie は見ない）。見せるのは、何を・書かれた場所・その人の名前・候補・その人のリンクからの答えと、家族が決めたその人に出す言葉（あれば）だけ（ほかの人の名前と答え・人数・答えで変わりうる人・家族の計画・会話の ID は出さない）。
  - 読むたび・書くたびに、家庭を押さえた中で、need が生きている・その人が名簿にいる・鍵がその人の今の止めていないリンクの物かを確かめ直し、どれかが違えば、どれかを言わずに同じ形で断る（401）。書く時は、今の代か、頁が見た後に同じ人のリンクからの答えが入っていないか（seenSeq）を確かめ、違えば今の物を返して断る（409。二つのタブで、後の方が前の方を黙って上書きしない）。操作 ID は、そのリンクの中の名前にする。一つの鍵で一分に 30 回まで。
  - Origin は別に確かめない：鍵は Bearer で、ブラウザは勝手に付けないので、鍵を持たない別のサイトの頁からは読み書きできない（CORS の許可を返さない）。ブラウザの付ける Sec-Fetch-Site は、same-origin・none・付いていない時だけ受け、ほかの値（別のサイトなど）は断る。書き込みは JSON だけを受ける。鍵を持つ人は、その相手の欄に答えられる（本人かは確かめない）。
  - リンクからの答えは「リンクを持つ人の答え」で、本人の確かめではない（画面・記録で「本人が答えた」と言わず「リンクから」と言う）。
- 画面：「することを足す」で「日は、相手の答えで決める」を選ぶと、候補の欄（2〜8）と「その時間のあいだ、ずっとだれかが受け持つ必要がある」（初めは入っている）を出す。「いつにするか」の画面は、表（行が候補、列が相手。○ はい・△ たぶん・× むり・ー まだ・！ 食い違い、＊ は要る人。日のすぐ右に、はいの人数／たぶん・食い違い・まだの人が全員はいなら何人か。表が枠に収まらない時は、横に送れると書く）、候補ごとの数え・答えで変わりうる人（家族の画面だけ）・たぶんの一言・食い違いの出所・やり方と決め時、勧め、決める（見てから）、家族が聞いた答えの記録、答える人の編集、一人ずつのリンク（出した時に一度だけ URL を見せ、漏れたら出し直すよう書く）。候補のある need の「中身を直す」は、日と時刻の欄を出さず、替えた欄（何を・だれのため）だけを送る。直す前の見通しには、今の答えを数えなくなること・決めた日を使わなくなること・選んだやり方を選び直すことを書く（決める前は計画の差に出ないので、画面が今の状態から言う）。きょうには、決めていない（決めた後に根拠が変わった）物を一行ずつ出す。
- デモ：前の五つの段の事象は変えず、後ろに二つの段を足した。when（12/5）：二人とも出る午後に陽菜を見てもらう日を 12/12 と 12/13 から決める。おばあちゃんの答えは家族の記録、近所の人はリンクから。club（12/6）：クラブの練習日を 12/12 と 12/19 から決める。コーチは要る、6 人以上、受け持ちは要らない。家族が足した会場の予約のやり方を使う。段に焼いたリンクの鍵はだれも持たない（答えて試すには、画面で出し直す）。
- まだしない：候補ごとに別のやり方の組を選ぶこと、使った後に日を替える道（今は要らないにして作り直す）、家族の家庭でのリンク、相手への知らせ（リンクは家族が自分で送る）、答えから日の候補を出すこと。

### 3.5 周りの資源と前もっての前提（今週の実装）

家の周りの施設・サービス（資源）と、使う前に一度だけ済ませておく事（事前の登録など）を、家の情報に持つ。種類はデータで、エンジンと検証器は種類で分けない（作り手の指示：家族と AI が一緒に保つ資源の集まりを核にする。2026-11-04）。

- 資源（resources）：
  - 欄：種類・名前・地域（区や駅の粒度。番地は持たない）・地図の場所への参照・調べて分かった事（家族に見せる文と出典）・家族の扱い（いつも使う・候補・使わない）と、それを決めた時刻。
  - 調べた候補は、家族が入れるまで家の情報に入れない。入れても、登録が済んだ・使える・その日に空いている、とは言わない。
- 出典は三つ：
  - ウェブの頁：URL・題・頁を読んだ時刻、Claude が根拠に挙げた文（引用）が読んだ頁の本文に文字のとおりにあったか（照らした結果。その文がまとめを支えるかは確かめない）。引用の欄は持たない（2026-11-05：引用として抜き出した第三者の頁の文を、画面に出したり残したりしない。まとめは Claude が書いた一文で、頁の言葉や文を含むことがある）。頁が公式かは、コードでは確かめない（画面は「出典の頁」と書き、リンク先で確かめてもらう）。
  - 家族。
  - デモの架空の決まり（画面に、本当の頁ではないと書く）。
- 前もっての前提（preparations）：
  - 名前（家族の言葉）・資源。
  - だれの分：家全体・その人たち・分からない。欄が無いことを家全体とは読まない。
  - 状態：分からない・まだ・手続き中・済んだ。家族が確かめた時刻も持つ。
  - 有効な最後の日。
  - 何日前までに：家族が出典の原文を見て確かめた時だけ持つ。今は「使う日の N 日前（暦の日）」だけで、営業日や時刻つきの締切は持たない。
  - やり方の requires が前提を指す。いくつのやり方が同じ前提を指しても、前提は家に一つ。
- やり方の resourceIds が、そのやり方の使う資源を指す（前提からは、使う資源を推し量らない。前提の資源を使うとは限らない）。
- 計算：
  - 通用の「すること」の案で、やり方の前提がその「すること」の使う日・だれのために満たされていなければ、印（needsPreparation）を付ける。印には、前提・訳・家族が確かめた日数からの目安の日を持たせる。
  - 印のある案がある手配では勧めない（止めたやり方・営業時間の分からない場所と同じ）。家族は選べる。
  - 訳は七つ：分からない・まだ・手続き中・有効な期間が切れた・だれの分か分からない・だれのための「すること」か分からない・ほかの人の分。
  - 家族が「使わない」とした資源を使うやり方の案には、印（unusedResources）を付け、勧める候補にしない。
    - ほかの案は、比べて勧める。家族が外した所は比べる理由にならない。済んだか分からない前提の案とは違う（そちらは、比べられないので、手配の全部で勧めない）。
    - 案が全部その印なら勧めないが、選べる手は残る（できないとは言わない）。家族は選べる。
  - 窓の「すること」の案で、約束が全部そろっても今の情報と計算では受け持てると示せない時間があれば、印（coverGaps）を付け、勧める候補にしない（2026-11-05）。
    - 印の時間は、覆ったかの計算と同じ決まりで前もって求める：受け持つ手順が無い・場所の書かれた「すること」に家族の受け持ちがある（家族のいる所と書かれた場所を結べない）なら窓の全部、受け持てる時間（covers）が窓より狭ければ、はみ出た時間。受け持つ人の決まった家族の受け持ちを、今の計算では窓に置けない（ふだんの予定やほかの作業との重なりなど）時も窓の全部（予定を直すと変わることがある）。だれもいないと分かったのではない。
    - まだ引き受けていない・返事の無いこと・受け持つ人がまだ決まっていないことは入れない。締切の形の「すること」には付けない。
    - ほかの案は比べて勧める（「使わない」の印と同じ）。案が全部その印なら勧めず、その訳を書く（訳が混ざる時は、手ごとの印の行だけ）。家族は選べる。
- 直し：
  - 前からある資源と前提で替えられるのは、資源の扱いと、前提のだれの分・状態・有効な最後の日だけ。だれの分の人は家の成員だけ。直した時刻はサーバーが付ける（だれの分だけの直しでは、状態を確かめた時刻を付けない）。消す・ほかの欄の直しは断る。
  - 新しく入れられるのは、そのデモで調べて見せた候補と同じ中身の資源と、その資源の登録の案だけ（扱い・だれの分・状態・有効な最後の日は家族が選ぶ）。
  - やり方の requires と resourceIds は、家にある前提・資源を指す時だけ直せる。
- 「この変更で変わること」に、手の前もっての印・「使わない」の印の変化と、勧める手の変化（出る・無くなる・替わる）を書く（見た物の要約にも入る）。
- 検証器：家の情報と事象から独立に確かめる。
  - 違反にする物：印の漏れ、余計な印、食い違う訳と日、満たされていない前提のある案を勧めたこと、「使わない」とした資源を使う案を勧めたこと、受け持てると示せない時間の印（coverGaps）の漏れ・余計・食い違いと、その印のある案を勧めたこと。
  - coverGaps は、根拠を独立に確かめられる範囲で違反にする。決まった受け持つ人のふだんの予定が窓に合わない時は、窓の全部と独立に分かる。予定は合うのに受け持ちに時刻が無い時は、ほかの作業や行ける時間のためかもしれず、置けない訳そのものは未判定にする（印と勧めの食い違いは見る）。
  - 事項や履歴が足りなければ未判定にする。
  - 家族が確かめた印は、記録があることしか示さず、頁の事実を証さない。
- 画面：
  - 「うち」の「周りの資源」：資源と出典、前提の状態・だれの分・使うやり方。直す時は「この変更で変わること」を見てから保存する。
  - やり方の表：使う前に済ませておく前提を、家の前提から選べる（前提を選んでも、頼む先・行く所は替わらない）。
  - 案の札：「前もって：…」と、お勧めを出さない訳、「使わないとしています」。
- 周りを調べる（survey.v1）：
  - Claude がウェブ検索で頁を探し、頁を読み（ウェブ検索と頁の読み取りの道具を、コードの実行を通さず直に呼ぶ）、候補を JSON で返す。送るのは、家の場所の地域と最寄りの駅（区や駅の粒度）、頼む種類（病児保育・一時保育・ファミリー・サポート。データ）、今日の日付だけ。家族の名前や予定は送らない。医療機関は調べない。
  - ウェブ検索は引用（citations）がいつも付くので、構造化出力とは一緒に使えない。最後の文の JSON を型で読む。
  - コードの確かめ：候補にするのは、同じ応答で本文を読んだ頁に、候補の引用が文字のとおりにある物だけ（全角・半角と空白をそろえ、8 字以上）。読んでいない・PDF・読めなかった頁、引用を本文で照らせない物（本文に無い・そろえて 8 字に満たない）、頼んでいない種類の物は外し、訳ごとの数を画面に出す。頁を読んだ時刻は、応答の時刻を家の時区の形にする。
  - 引用が本文にあることは、その文が頁にあることしか示さない。引用は照らすためにだけ使い、照らした後の候補（API の答え・記録した調べ・家に入る資源と前提）には残さない。まとめが頁の本文にそのままある物（頁の文の写し）と、根拠に挙げた文（まとめ・登録・日数の引用）を含む物は、その文がそろえて 8 字以上なら候補にしない（まとめが頁のほかの言葉や文を含むことまでは止めず、止めたとは言わない）。事前の登録が要るかは Claude の読みとして見せ、家族が出典の頁で確かめる。日数（何日前までか）は候補に入れない（頁の文を見せないので、数字だけでは何の数か確かめられない）。
  - 家族が候補ごとに選ぶ：扱い、事前の登録（要る・もう入れてある登録と同じ・要らない・まだ分からない）、要るならだれの分、その登録を前提にするやり方。前提にするのは前提を足すだけで、やり方の使う資源・頼む先・行く所は替えない。登録を「要る」か「同じ登録」にするまで、前提にできない（登録の前提の無いやり方に見せないため）。どれも Claude の読みによらず、家族が決める。
  - 資源は場所に結んで入れる（やり方の手順は場所に頼む・行くので、資源を手順に結ぶ手がかり）。家に同じ名前の場所があれば、家族が「同じ所」と確かめた時だけその場所に結び、確かめなければ場所に結ばずに入れる（名前が同じだけでは同じ所と決めない）。無ければ新しい場所（施設。名前と地域だけ）を足す。サーバーは、新しい資源の場所を、名前が同じで家ではない場所の時だけ受ける。
  - 家族が「この家の候補にする」を押すと、保存の前に「この変更で変わること」を見せる（何も書かない）。
  - この所に頼む・行くやり方は、入れた後に、今のやり方を写して作る（家族が、どのやり方のどの資源の代わりかを選ぶ。前のやり方は替えない）。写した表は、代わりにする資源の場所に頼む・行く手順だけをこの所にし（家族が表で直せる。ほかの手順・資源・前提はそのまま）、前の所の時間・費用・期限・返事までの時間をこの所の事実にしない：受け持つ時間と、替えた手順の期限・返事までの時間は選ぶまで保存せず、費用の円は分からないにする。前提は、代わりにする資源の前提を外し、この所の前提（家にあれば）を足した案で、家族が選ぶ。この所の事前の登録は、表で選び直す（要る・要らない。選ぶまで、「まだ分からない」でも保存しない。要るなら前提を一つは選ぶ）。使う資源は、手順が今頼む・行く所で決める（この所に頼む手順を元に戻せば、この所を使うとは書かない）。保存した後、そのやり方を選んだ「すること」の頼む作業は、この所に頼む（計画は家の情報の手順から作り、検証器は作業の頼む先が手順と同じかを確かめる）。
  - デモの既定は、記録した調べ（デモの家の地域を一度だけ本物で調べ、確かめた結果を data/demo/recorded/survey.json に持つ。頁の本文も引用も持たず、照らした結果と出典と読んだ時刻だけ）。数えない。Claude にいま調べ直してもらうのは、一つのデモで 3 回、サーバー全体で一日 30 回まで（作り手の決定 2026-11-05）。
  - 家族の家庭では、まだ開けない（今週は、実在の家の住所をサーバーに入れない）。
- 家族の好み（いつもの店）：
  - 好みの正本は、資源の扱い（use）だけ。店も資源にし、店の場所（Place）を指す。店の場所に第二の好みの欄や、品物ごとの順位を作らない。一つの店に、資源は一つ。調べ直しや候補の足し算で、家族の扱いを替えない（AI は候補を出すだけ）。
  - 計算（品物によらず同じ決まり。engine/purchase.ts の purchaseStores と、plan.ts の買い物）：
    1. 家族がその品物のために選んだ店（「ほかの店を探す」で選んだ店。店の扱う物に品物の名前そのものがある）が先。その店が「使わない」なら、どちらも採らず決めない（訳 storeNotUsed）。
    2. 無ければ、品物の種類を扱う店から「使わない」の店を外し、「いつも使う」の店があれば、その店の機会だけから置く（ほかの店が先に寄れても、ほかの店にしない）。いつもの店が二つ以上なら、その中でいちばん早い機会。
    3. いつもの店に、これから寄れる時が無い時は、ほかの店に黙って移さず、決めない（訳 usualStoreUnavailable。家にあるかが分からなければ、今のとおり聞く）。ほかの使える店にまだ寄れる（または営業時間を確かめていない）か、いつもの店にさかのぼっても寄れる時が無い時は、過ぎたとも無理とも言わない。どの店にももう寄れる時が無く、いつもの店の機会が過ぎただけなら、今までどおり過ぎた（過ぎた最後の機会を決め時として示す）。
    4. いつもの店が無ければ、今のまま（「使わない」を除いた店の、いちばん早い機会）。品物を扱う店が「使わない」の店だけなら、決めない（storeNotUsed）。
  - 決め時（最後の機会）と、過ぎた機会のさかのぼりは、置いたのと同じ店の集まりから求める（いつもの店にしか行かないのに、ほかの店の最後の機会を決め時にしない）。
  - 引き受けた買い物の店が、扱いの直しで替わる時は、今までどおり、保存の前に「変わること」に行く所（店）の変化と引き受け直しを出す（担当は替えない）。
  - 境：品物の名前が、店の扱う種類の名前（clothing・kidsClothing・groceries）と同じ字なら、その種類として扱う。店の扱う物（goods）は、店の扱う種類と、品物のために選んだ店の印を同じ欄に持つので、この時は品物のための店を選べない（画面は「ここでは選べません」と書く）。
  - 直し：資源の無い店に家族が扱いを選ぶと、店の資源を作る。サーバーは、ID が店から決めた物（res-store-店の ID）、名前が店の名前、分かった事が無く、その店を指す資源がほかに無い時だけ受ける。扱いを決めた時刻はサーバーが付ける。
  - 画面：「うち」の「周りの資源」で、店ごとに扱いを選ぶ（保存の前に「この変更で変わること」：行く所（店）・決め時の変化）。買い物の札に「いつもの店です」。いつもの店に寄れない・扱う店が「使わない」の店だけの時は、「このままでは無理」の札に訳と店の名前を書き、「周りの資源」で扱いを替える道を示す（ほかの店を自動では選ばない）。
  - 検証器：計画の goods によらず、事項と、家族の店の扱い（資源 → 場所）から独立に照らす。違反にする物：「使わない」の店に置いた、品物のために選んだ店を外して置いた、品物のための選びが無いのに、いつもの店を外して置いた。食い違う資源・品物の種類を確かめられない時は未判定。決め時がその店の集まりの最後の機会であることは、検証器では独立に証していない（core の試験で確かめる）。
  - デモ：子ども服を扱う店を二つにし（駅から近く先に寄れる架空の店を足した）、地図に結んだ豊洲駅の近くの衣料品店を「いつも使う」にしてある。いつもの店に置き、「使わない」にすると、もう一つの店に替わる。
- まだしない：
  - いつもの店の好みを、やり方の勧め（いつもの病児保育室を使うやり方を先に勧める等）に当てること。
  - 前提の締切を「すること」の作業にすること。
  - 自動の見直し（今週は手で押す調べ直しだけ。作り手の決定 2026-11-05）。

| 物 | ID | 変わらないための決まり |
|---|---|---|
| 操作 | 画面が作る操作 ID（UUID） | 同じ ID の二度目は、中身の要約が同じなら今の状態を返し、違えば衝突として断る（§7.3） |
| 事象 | サーバーが作る ID と、家庭ごとの通し番号 | 画面は通し番号を付けない |
| 出典 | サーバーが作る | 訂正は版を上げる。古い版への遅れた読み取りで、新しい版を上書きしない |
| 事項・未定の値 | サーバーが作る、中身を含まない ID | モデルの局所 ID は、その呼び出しの中で対応を取るためだけに使い、保存しない（モデルや原文の言葉が ID に入らないように）。読み直しの決まりは §4.1 |
| エンジンが作る未定の値 | 系譜から（`u-atHome:元の事項ID`） | 今のまま |
| 要件・手配・案・作業 | 種類＋系譜（置き換えをたどった元の事項）＋雛形・手順の ID（＋子の ID・回の ID）＋世代 | 時刻・担当・店・通販の別をキーに入れない。キーの形は、保存した事象が指す契約である。形を変える時は、古い事象のキーを写す読み替えの関数を一緒に作る |
| 習い事の回 | 所属 ID＋決まりで予定されていた日 | 人が操作した回は、実際の日や決まりが変わっても同じ ID を保つ。決まりの変更で予定が動いた回に操作があれば「要確認」 |
| 家族の情報の中の物 | 家族が作る時に、サーバーが付ける（中身を含まない） | 使い回さない。消した物を指していた作業は「前提が消えた」として扱う |
| 依頼 | 送った時に画面が作る UUID | 送った時の相手・種類・根拠・文の控えを持ち、後の作業から逆算しない |

### 4.1 読み直しで、事項の同じを保つ

- 読み直すのは、書き起こしを直した時と、使い始める前のプロンプトの更新の時だけ。家族の訂正（読み違い、うちの子に関係ない、推定の確認）は、読み直さずに事項への事象で記録する（§5.2）。
- 読み直しでは、前の事項と未定の値を ID 付きでモデルに渡し、対応の候補を返させる。モデルの対応は候補であり、決めるのはコードと家族である。
- コードが自動で同じと認めるのは、同じ出典の中で一対一に決まり、元の文の部分と事項の意味（種類・解釈・条件の式）がすべて同じ時だけ。
  - 条件の式は、節点の ID ではなく形で比べる（ID はモデルの付けた物で、読み直しで別の式に使い回されることがある）。
  - 字が直った、一つが二つに分かれた、二つが一つになった、候補が複数ある時は、家族に「同じ物ですか」と聞く。
- 対応の決まらない前の事項は、消さない。
  - 「今回の読み取りで見つからなかった・要確認」として残し、間に合わなくならない側で計画に残す。
  - 家族が「もう関係ない」と確かめた時だけ外す。読み直しの読み落としで、明日の持ち物が黙って消えないようにする。
- 要確認の間：
  - 送った依頼と引き受けの事実は残す。
  - 取り消されたとも、続けてよいとも決めない。
  - その事項について、新しい決定を勧めない。

### 4.2 世代（取り消した物が、また要るようになった時）

- 世代は、手配全体ではなく、作業と依頼ごとに持つ。
- 世代が上がるのは、その作業か依頼について、取り消しがはっきり起きた後に、また要るようになった時だけ。
  - はっきりした取り消しの例：その依頼に取り消しの連絡を送った。本人に「要らなくなった」と知らせた。
  - 世代が上がると、前の引き受けは引き継がず、本人にもう一度聞く。
  - **今週の実装**：引き受けた作業が、後のお知らせの取り消し・条件が外れた・事項を外した・家の決まりの変更などで、今の計画から無くなるか生きていなくなった時と、家族が別の案を選んだ・本命が決まった等で、その案の作業をもう進めない時（isActiveTask）は、計画の released に入れ（理由 gone・notLive・inactive・unconfirmed）、選ぶ前の「選んだら」にも、選ぶと要らなくなる引き受けを並べ（見せた物の要約に入る）、持った本人の「きょう」の一番上に「もう要りません」を出す（用件と時間は、引き受けた時の控え。控えの無い古い引き受けは中身が分からないと書く）。知らせは、動き始める時（控えの始まり）の 26 時間前から終わりまで（始まった後に中止が届いても知らせる。時刻の無い物は出た時に）。本人の「分かりました」で引き受けを取り下げる（計画に無い作業でも、本人だけ）。家族の操作やデモのお知らせで、要らなくなった引き受けが戻った時は、本人が「きょう」で見たかもしれないので、もう一度引き受けるかを聞き直す（assignmentProposed。選ぶ前の「選んだら」と、見せた物の作り直しも、同じ頼み直しを含めて計算する）。ほかの道で戻った時も、「もう要らない」と知らせた後なら確かめ直しにする（世代の代わり）。「分かりました」は、見た計画の通し番号が今と同じ時だけ受ける（古い札の遅れた押しで、戻った引き受けを外さない）。外への取り消しの連絡とは別。引き受けには根拠の事項とお知らせの ID を控える（commitmentChanged の basisItemIds・basisSourceIds）。要らなくなったと言う（gone）のは、根拠のお知らせを取り下げた時か、根拠の事項がどれも、関係ないとされたか取り消された時だけ。引き受けた後に根拠のお知らせを読み直した物（同じ ID は同じ事項の証拠ではないので、その後の取り消し・関係ない・条件の外れも当てない。出典ごとの取り下げは当てる）、根拠の事項が今も残るのに作業が無くなった物（家の決まりや子の数が変わった等）、根拠のお知らせを消した物、読み直しで根拠の事項が見つからない物、控えの無い古い引き受けは、要らなくなったとは言わずに「まだ要るか確かめて」（unconfirmed）にする（§5.1 の「根拠を消したので要確認」。消したお知らせの中身と時刻は出さない。控えの無い古い引き受けは、家庭のお知らせを一つでもまるごと消していれば中身を出さない）。
- 一つの依頼の取り消しで、同じ手配の他の作業は変わらない。例：学童の予備を取り消しても、祖母の本命とその引き受けはそのまま。
- 条件が行き来しただけで、取り消しを誰にも伝えておらず、提案の中身も変わらない時は、世代を上げず、引き受けを保つ。
- キーには、世代が2以上の時だけ後ろに付ける。今のキーは変わらない。

## 5. 生命周期

どれも「状態・入る物（事象か時間）・記録か導出か・次に響く物」で書く。時間で入る状態は、すべて導出である。

### 5.1 出典

| 状態 | 入る物 | 記録か | 次に響く物 |
|---|---|---|---|
| 届いた | noticeReceived（文字なら文、写真なら写真の参照） | 記録 | 読み取りの仕事 |
| 書き起こした（写真） | modelOutputRecorded（transcribe） | 記録 | 文ができる。読み取りへ |
| 書き起こしを直した | transcriptionCorrected【新】 | 記録 | 読み直し（§4.1） |
| 読んだ | modelOutputRecorded（extract）、コードの検査を通った物 | 記録 | 事項・未定の値。計画を作り直す |
| 読めなかった | 拒否・打ち切り・型の誤り・API の誤り | 運用の表 | 画面に「読めませんでした」と、もう一度・手で書く。空の正常な計画にしない |
| 訂正された | 後の出典の correctsSourceId、後の事項の作用 | 導出 | 事項の今の形が変わる |
| 取り下げた | sourceWithdrawn【新】：家族が「このお知らせはもう当てはまらない」と言った | 記録 | 事項が全部生きていない → 頼んだ後なら取り消しの連絡（§1 の4） |
| 写真を消した | 削除の仕事 → sourceContentPurged【新】（写真だけ） | 記録 | 計画は変わらない。元の文の画面に「写真は消しました」 |
| お知らせごと消した | 削除の仕事 → sourceContentPurged（全部） | 記録 | 事項は使えなくなる。取り消しは推し量らず、それに頼っていた依頼と引き受けは「根拠を消したので要確認」 |

- 今のデモ（11/3）では、写真を残さない：書き起こしを家族が写真と見比べて直した文を、出典の文として受け（届いた形は写真）、写真の参照・書き起こしの記録・写真の削除は持たない。家族の家庭で写真を受ける時に、上の表のとおり作る。
- 読み取りの記録の出典、読み取りの出典、各事項の出典は一つに揃う。揃わない読み取りと、届いていない出典の読み取りは使わない（非同期の読み取りの取り違えで、別の出典を汚さない）。
- お知らせごと消した出典は、たたんだ状態からも原文を外し、見せる物に出さない。同じ ID のお知らせは、もう受け付けない。事象の列に残る中身を消すのは、置き場所の仕事（§6.4）。

取り下げと削除を分ける。取り下げは「当てはまらない」という家族の言明で、取り消しの流れを起こす。削除はプライバシーの求めで、学校の行事が中止になったとは推し量らない。

### 5.2 事項と作用

| 状態 | 入る物 | 記録か | 次に響く物 |
|---|---|---|---|
| 記載・推定・食い違い | 読み取り | 記録 | 推定・食い違いは家族への確認にし、必須の要件も作用も起こさない |
| 確かめた | itemConfirmed【新】 | 記録 | 「家族が確認」。要件と作用が効く。お知らせから読んだ「すること」は、確かめるまで計画に入らない（§3.4）。その時の読み取りに結び、読み直しの後は当てない |
| 直した | itemCorrected【新】：解釈の一部を家族が直す | 記録 | 解釈を置き換え、「家族が確認」。ID は変わらない |
| 関係ない | itemDismissed【新】：うちの子に関係ない等 | 記録 | 要件を作らない。itemConfirmed で戻せる |
| うちの番か | turnStated【新】：家の人の当番が、うちの番か（言った時の用件と対象を持つ） | 記録 | 当番を作業にするかを決める。用件か対象が直されたら当てない。確かさ・作用は変えない（関係ない・確かめたとは別） |
| 送り迎えが今回要るか | escortStated【新】：習い事・クラブの行事の送りか迎えが、今回要るか（言った時の子・用件・その方の日・時刻・場所を持つ） | 記録 | 家の決まりより先に、その方の作業を作るかを決める。どれかが変われば当てない。確かさ・作用は変えない |
| 要確認（読み直しで見つからない） | 読み直し | 導出 | §4.1 |
| 置き換えられた・取り消された | 後の事項の作用 | 導出 | 置き換えは系譜で同じキーを保つ。取り消しは外す |
| 条件が偽 | 未定の値の答え | 導出 | 生きていない |
| 過ぎた | 日付が過ぎた | 導出 | 画面から下げる |

**作用は三つの値で効く**：

- 作用（未定の値を決める・置き換える・取り消す）は、その事項が確かで（記載か家族の確認）、条件が真で、置き換え・取り消しを受けていない時だけ効く。
  - 後で置き換え・取り消しを受けた事項の作用は外れ、その作用で決まっていた値も決まっていない側に戻る。受けるか分からなければ、作用も分からないとする。
- 同じお知らせの中で、効く作用が同じ未定の値に違う値を言う時は、先後の証拠が無いので、どちらとも決めない（未定のまま。後の確かな連絡か家族の答えで決まる）。モデルの出力の並びの順で決めない。
- 一つの事項を、効く（効くかもしれない）置き換えが二つ以上言う時も同じで、どれが続きかを決めない。系譜は継がせず、前の事項も、言い合う後の事項も「条件しだい」として残し（どれも確かな必需品としない）、頼んだ依頼は要確認にする。
- 条件が偽なら効かない。分からない時は、作用も分からないとし、前の事項を消さない。
  - 前と後の両方を「条件しだい」として、間に合わなくならない側で計画に残すか、問いにする。
  - 確定した事実や、自動で進めてよい物としては見せない（§1 の2）。
- 条件と作用が互いを頼って回る時は、未判定にする。たたみ直しを限りなく繰り返さない。
- 作用の真偽は、出典が届いた時に一度だけ決めない。たたむ度に、その時の答えで決め直す（後で家族が答えれば、前の作用も効き方が変わる）。
- 確かめた（直す前）：作用を、事項の証拠の状態と条件の真偽を見ずに当てていた。
  - 架空の材料で、条件が偽の延期の連絡が日付を12/8に決め、前の事項を置き換えた。
  - 食い違いの事項でも同じだった。
- 直した（§13 の1）：上の決まりで効くようにし、戻りの試験を足した。

### 5.3 未定の値と問い

- 未定の値：
  - 宣言は、読み取りかエンジンが行う。
  - 答えは、家族の answered か、後の出典の作用（効く物だけ）。順の後の物が勝つ。
  - 答え直しは、新しい answered。
  - 買い物の「家にあるか」の値（エンジンが宣言する）への答えは、画面が見せた品物の名前を控えに持つ（about）。今の品物と違う答えは使わず、家にあるかはまだ分からないものとして扱う（品物が直されたり、別のお知らせに置き換えられたりした時、古い答えで別の品物を「ある」にしないため）。もう一度聞くかは、ほかの決まり（扱える品物か、期限、買い終えたか）による。控えの無い前の答えは、今まで通り使う。要らなくなった持ち物（条件が外れた等）には聞かず（問いの札も知らせも出さない）、その間の答えも受けない（条件が戻った時に、要らない間の答えを使わないため）。
  - 出典が取り下げ・削除されたら、その出典の未定の値と作用は使わない。その値への家族の答えも使わない（他の出典の事項がその値を条件にしていれば、条件しだいに残る）。
    - その事項を確かめても（itemConfirmed）、条件は解けない（読み取りが正しい事と、条件が満たされた事は別）。今は、家族が「関係ない」とするしかない。「この回は要る」と言う手段は、実在の家族のデータの門（§13.1）の前に要否を決める。
- 問い（全部導出）：
  - 答えで計画が変わり、聞く期限の前の時だけ出る。
  - 知らせた → 答えた → 期限が過ぎた。期限が過ぎたら、間に合わなくならない側で進め、画面にそう出す。
  - **今週の実装（家族が決める値）**：お知らせが家族に決めさせる値（読み取りの未定の値で kind が family。「参加される方は」「出席の場合は」）で、まだ答えが無く、今も確かな読み取り（取り下げ・消したお知らせの物でなく、文を直した後なら読み直した物）にある時、値ごとに代入して、その値を条件に使う事項（条件の節点をたどる）の条件を三値で求める。どの値でも同じ確かな結果（全部 true か全部 false）の事項には効かないとし、効くかもしれない事項（結果が違うか、ほかの未定の値のために分からない）の要件のうち、まだ期限の過ぎていない物があれば聞く（Question の family：お知らせの言葉の名前と、値ごとに要る要件。そのうち、その値でもほかの条件しだいの物は conditionalKeys に分け、画面は「ほかの条件しだいで」と書く。効くか分からない作用の先にある事項も、しだいに入れる）。答えが要る最後の時（until）は、その要件の最も早い期限（画面で時刻を見せるかは、その期限を作った要件に時刻が書かれているかで決める）。安全な既定の答えは無いので、fallbackValue を付けない。答えるまで、その要件の作業は「だれがやるか」に出さず、その要件の持ち物の「家にあるか」も聞かない（先に決める方を聞く）。もう持った人がいる作業は出す。要る物の無い値の行は「この答えで要る作業はありません」とだけ言う（同じお知らせの条件の無い作業は、問いに関わらず出ている）。知らせは until の 26 時間前から（until の無い問いは札だけ）。
  - **答えと、答えた後の変化**：問いの札からの答えは、見せた問い（key・until・affects）を付け、今の時刻で作った問いと同じ時だけ受ける（事象が無くても、時が進めば要件が期限で外れて問いが変わる）。文を直して読み直す前は、答えを受けない（問いも出さない）。受けた答えには、答えた時の問いの形（名前・値・その値を条件に使う事項の中身（家族の直しを重ねた物）と条件の式の形）を about に控え、今の形と同じ時だけ使う。読み直しで同じ ID が別の問いになった（参加→欠席）、条件の式が替わった（参加なら→参加しないなら）、行事の日や締切が直された等で替われば、前の答えは使わず、前の答えを添えて聞き直す。時が進んだだけ・確かめただけ・ほかの事項が取り消しただけでは替わらない。
  - まだしない事（境）：作用（ほかの事項の取り消し・未定の値の答え）を通じてだけ要件を変える家族の値は、問いにしない。その作業は隠さず、条件しだいのまま見せる。札でない答え（一言、元の文の画面）は、決める期限の後も受け、そのまま使う（期限を過ぎた事を、間に合わなかったとは言わない）。

### 5.4 要件・手配・案

- 要件と手配は、全部導出。生きている事項（決まりから導いた回を含む）から出て、事項が生きていなければ消える。
- 案の状態：
  - 開いている・決め時が過ぎた：導出。
  - 本命・予備に選んだ：optionChosen で記録。
  - 取り下げた：optionDropped で記録。
  - 断られた：依頼の返事から導出。
  - 決め時を過ぎても始めていない：導出。始めたかは、今の手配の日の分で見る：今の日を頼んだ依頼（控えの頼んだ日が同じ。日の無い古い控えは当たる）か、今の用件（その日）に当たる本人の「済んだ」。日が直されて前の日の分になった依頼・済みでは、始めたことにしない。断られた・返事待ちは、頼んだ日によらず数える（前の日の分でも、頼み直すまで決まったことにしない）。
- 手配の状態（決めてよい・返事しだい・聞いてから・無理・まだ判断できない）は、導出（01-model §8）。

### 5.5 作業と引き受け

- 作業があるか：導出。要件が生きていて、案が選ばれているか勧められている時。
- 引き受けの状態：

| 状態 | 入る物 | 記録か |
|---|---|---|
| 提案 | 分担の決まりかエンジンの配置。もう一人の assignmentProposed | 導出、または記録 |
| 引き受け | commitmentChanged accept（本人だけ）。提案の控え（時刻・遅れる帰宅・担当・用件・場所・外の相手・根拠の条件）を持つ。サーバーが今の提案と同じかを確かめ、違えば断って見せ直す。置けていない作業（時刻の無い提案）は控えが作れないので、置けてから引き受ける | 記録 |
| 確かめ直しが要る | 解き直して、提案の中身が控えと違う。世代が上がった（§4.2） | 導出 |
| 担当を替えた | assignmentProposed。前の担当の引き受けの控えは捨てる（前の人の同意を、次の人に引き継がない） | 記録 |
| 済み・断った・できなくなった | commitmentChanged（本人だけ）。済んだは、札で見せた用件（文言のキーと値）を控えに持つ。サーバーが今の用件と同じかを確かめ、違えば断って見せ直す | 記録 |
| 取り消し | 根拠が消え、済んでいない | 導出 |
| 担当がいない | 担当の成員を止めた | 導出 |

- まだ引き受けていない提案は、提案を受けた人には「おねがい」の札で、もう一人の大人には、きょうの下の「待っていること・やること」に静かに一行で出す（「健太さんが、まだ引き受けていません」と作業・時刻）。だれが頼んだかは言わない（仕組みの提案もある）。引き受けた後に中身が替わった確かめ直しは、まだ引き受けていないとは言わないので出さない。引き受ければ相手の作業になり、断れば「だれがやるか」の札になって、この行は消える。知らせは替えない（2026-11-05）。
- 済みの控えの用件が今の作業の用件と違えば（直し・置き換えで、作業のキーは同じまま白い長袖シャツが赤い帽子になった）、その済みは今の作業に当てない。引き受けた所に戻し、確かめ直しを出す（前の物を済ませた記録で、別の物を済んだことにしない）。用件が戻れば、また済みになる。控えの無い前の済みは、今まで通り当てる。
  - 手配の手順（学童の申込書を書く等）の用件には、その手配の日を入れ、画面の行にも「12/7（月）の分」と書く。預ける日が直されたら別の用件になり、前の日の済みや引き受けを新しい日に当てない。買い物と提出物の用件は品物だけで、日が動いても同じ物を用意すれば足りるので、済みは残す。
  - 家の人の当番の用件には、書かれた日・始まり・終わり・場所を入れる（別の日の当番は別の用件。直されたら、前の済みや引き受けを当てず、前の内容を見た画面からの記録も断る）。家の人がすること（音読カードのサイン）は、同じ紙への用事なので、提出物と同じく用件は物だけ。
- 条件しだいの作業は、画面が条件を添えて見せる（「12/5なら要ります」）ので、控えにも根拠の条件を入れる：式の形（§5.6 の condition と同じ）、式が使う未定の値の名前、根拠が今確かでないか。
  - どれかが替われば、見せ直す（引き受けの前なら断り、後なら確かめ直し）。未定の値に答えが出ただけなら、替わらない。
  - 名前は、画面と同じく今も確かな読み取りからだけ取る。名前を出した出典を取り下げた時や、文を直して読み直す前は、名前が確かでないので、替わったとみなす。
  - 作業の元の文を直してまだ読み直していない時や、取り消されるかもしれない時は、画面は「条件しだい」とだけ添える。控えでも確かでない印を付け、替わったとみなす（同じ中身に読み直せば元に戻る）。
- 提案の控えに残す地図由来の欄（place ID 以外）は、Google の条款を確かめてから決める。家族が選んだからといって、事業者のデータを自由に保存してよいとはみなさない。
  - こちらが計算した時刻でも、Google の道のりや所要の時間に頼って出した物は、こちらの計算だというだけで保存してよいとは言えない。
  - 控えは、本人が実際に見た物と同じでなければならない。見せた時刻と別の時刻を控えに書くと、本人が確かめた中身を偽ることになる。
  - 2026-11-04 に改めた（作り手が「画面の中の地図・本物の店・寄り道の時間」を選び、二人で合わせた）：デモでは、要求ごとに引いた地図の値で提案の時刻を作り、それを見せて引き受けられる。控えには、見せた時刻・徒歩の分・店の place ID が入る。デモの事象はサーバーのメモリにだけあり、デモの期限で消える。家族の家庭（DB に保存する形）では、地図の値を計画に入れない（家族の情報の目安だけ）。Google の条件を満たしたとは、まだ言わない。

### 5.6 外への依頼

- 送った（externalRequestSent）：相手・種類・根拠（手配・案・作業のキーと事項の ID）・文の控えを持つ。
  - 控え（snapshot）には、送った時の計画で見えていた物を写す：条件しだいだったか（conditional）、根拠の条件の形（condition。節点の ID を除いた式）、頼んだ時間（window。子の居場所の手配の区間）、子の居場所ならどの子の分か（childId）。控えは requestSnapshot で作る。取り消しの文は控えの子の名前で書き、控えに子の無い古い依頼は今の手配の子を使う。どの子か分からなければ名前を書かず、札で確かめてもらう（今の家の子を当てない。子が一人でも、頼んだ時の子だという証拠にはならない）。
- 送った後に、頼んだ時の前提と今が違えば、要るかを頼んだ本人に確かめる（needsCheck）。取り消したとも、続けてよいとも決めない。
  - 根拠の事項のどれかが、読み直しで見つからない・確かでない・取り消された（他の根拠で手配が残っていても）。
  - 根拠が、効くか分からない置き換え・取り消しの先にある。
  - 送った時は確かだったのに、今は条件しだい。
  - 条件の形が違う（読み直しで式が替わった）。後でその新しい条件に答えが出ても、相手が新しい前提で引き受けたことにはならないので、確かめは残る。
  - 頼んだ時間が違う（置き換えで日が変わった、家族の予定が変わった）。
  - 条件に答えが出ただけなら疑いではない：真なら続け、偽なら取り消しの連絡を作る。条件しだいの未定の値に、それを決める新しい作用が届いただけでも疑いにしない（頼んだ文の前提は替わらず、決まれば同じ道で取り消しまで進む）。
  - 控えに条件や時間の無い古い事象では、それらからは決めない（検証器は、事象から当時を作り直せなければ未判定とする）。
- 返事待ち → 確定・断られた（externalReplyRecorded。後の返事に従う）→ 取り消した（cancellationSent）。
  - 取り消しを伝えた依頼を理由に頼む手順を開き直す（引き受けた所に戻し、頼み直す）のは、手配がまだ要る時だけ。要らなくなった手配では、取り消しを理由には開き直さない（頼んだことも取り消しを伝えたことも済んだ事。開き直して引き受けに戻すと、もう要らない作業を引き受けた物として見せ、検証器の記録と食い違って、知らせの門が全部を止めた。2026-11-05）。日が直されて前の日の分になった依頼を今の日に当てない決まり（引き受けた所に戻す）は別で、変えていない。
- 断られたら（仮の計算。今週の実装）：返事待ちの依頼について、送った本人に「断られたら？」を出す。見せる口（previewChange）に仮の「断られた」（recordReply の no）を渡し、本当の記録と同じ計算の結果を見せる。書かない・送らない・知らせない（「選んだら」と違い、見た後に保存へ進む口を置かない。型でも、見てから保存する命令 SaveablePreview から外す）。
  - 見せる物：使う案がどうなるか（そのまま・予備へ進む・ほかの案へ・選び直し。選び直しなら勧める案と、いつまでに返事が要るか）と、残る案それぞれが消えるまでの時間。断られた案が予備だった時は、予備が無くなると書く。
  - 通用の「すること」の仮定では、返事の期限（「…までに返事をもらえれば、断られても…に間に合います」）を書かない。頼む文にも、ほかの手の決め時から出した返事の期限を書かない（返事待ちの行と同じ。受け持ちの置き方・前提・使わない資源・行ける時間を別に確かめるため。「すること」に書かれた日時は書く。2026-11-05）。
  - 仮の計算も、計画のエンジンと別の検証器で確かめる（仮の事象と組めば違反なし、本当の事象だけと組めば違反として見つかる。`apps/server/test/what-if-verify.test.ts`）。
- 確保できた予備（子の居場所の手配だけ。2026-11-05）：予備に押さえた案の手順（当日の準備を除く）が一つ以上あって全部済み、外の相手の受け付けが要る手順は、その依頼が今も生きていて、今の日の分として受け付けられている（確かめ待ちでない）時。決め時（申し込みの締切）が過ぎていても、その前に済ませて受け付けられた物は確保できている。引き受けただけ・返事待ち・取り消し・別の日の受け付けは、確保と言わない。
  - 確保できていれば、次の予備は勧めない（札も知らせも出さない）。返事待ちの行に「断られても、予備の『…』に進めます」と書く。受け付けたと書くのは、外の受け付けが要る手順がある時だけ。当日の準備は確保に含めないので、別にあると書く。
  - 確保できていなければ、返事待ちの行に、断られても間に合う返事の期限を書く（頼む文・決める画面と同じ。時計が進めば、次の手に替わる）。
  - 通用の「すること」は判定せず、返事待ちの行には返事の期限も書かない。承認が済んでも、だれかが窓を受け持つとは限らない。将来の受け持ちは引き受けで約束になる。家族が使わないとした資源や、済んでいない前提もある。これらを確かめる正の根拠を作るまでは、確保とも、間に合うとも言わない（次の予備の勧めは、今までどおり出す）。
- その日だけの一日（仮の計算と記録。2026-11-04）：一言（「12/7 は休めたら？」）か「うちのこと」の「この日だけ変える」から、大人のある日の前提（だれ・日・変え方・時刻）を前提の画面に直せる欄で出し、家の情報の直しと同じ見る口（書かない計算）で、何が変わるかをすぐ見せる。言われていない前提（「家」の区間は子を見られる時間、前後はふだんどおり等）は「仮に置いた前提」と分けて書く。記録は別の「この日を記録する」だけで、見た計算の控え（seen）を付け、家庭を押さえた中で計算し直して、違えば記録せずに見せ直す。
  - 区間はモデルでなくコード（core の draftDay）が、その日の今の一日から作る。一日休みは一日を家に、その時間は家・外出はその時間を置き替え、仕事の終わりは帰りの通勤を同じ長さでずらす。
  - 日は、モデルの読んだ日を、モデルの写した言い方（dateText）でなく家族の原文で確かめる（core の datesSaid）。原文の言い方（今日・本日・今夜・今晩、明日・あした、明後日・あさって、M/D・M月D日・年つきの日、日を言わない時の（今週・来週・再来週の）○曜、英語の today・tonight・tomorrow・the day after tomorrow・December 7・7 December・this／next Monday・Monday next week）から、指しうる日を全部求め、一つに決まってモデルの日と同じ時だけ受ける。週の始まり（月曜か日曜か）や「next」の取り方で変わる、今日がその曜日の「金曜」、二つの日を言った、読まない言い方、食い違いは、黙って直さず、日を空けて聞く。年の無い月日は去年・今年・来年のうち今日に一番近い日とし、年を書いた月日はその年で読む（読めない年や「来年」のような言葉があれば、年を落として読まない）。日に添えた曜日（「12/7（月）」）は、日と合うかだけ確かめる。家の人の名前のうち日の言い方を含む物（「明日香」）は、日として読まない（文字のとおり、長い名前から消す）。文字列から、その言葉が本当に日を言っているかまでは確かめられないので、この確かめは受けるための要る条件で、十分な条件ではない（家の外の名前などの中の「今日」「明日」は見分けられず、モデルが同じ読み違いをすれば通る）。そのため前提の画面は、家族の原文（読みに送った文）を読んだ前提と並べて出し、家族が確かめる。
  - 作らない一日（計算せずに訳を示す）：仕事や通勤の途中で家に移る（行き来の時間が分からない）、お迎えのある日に仕事の終わりを変える（お迎えをどうするか言われていない）、日をまたぐ、その日の区間とつながらない。人・日・時刻が決まらない時も計算せずに聞く。
  - 検証器は、その日だけの一日が新しく作った区切りで、前後の場所が違う・分からない所を未判定にする（ふだんの週と同じ区切りは、言わない）。未判定は画面の「この変更で変わること」に数で出る。
- 取り消しの連絡が要るか：送った時の控えと、根拠が今も生きているかから導く。今の作業の一覧からは逆算しない。
  - 確かめた（直す前）：読み直しで事項が消えると、送った依頼が計画の出力から消え、取り消しの作業もできなかった（依頼を今の作業から引いていたため）。
  - 直した：控え（snapshot）のある事象は、作業が消えても控えから依頼を作り、根拠が分からなければ要確認にする。
  - 残る穴：控えの無い古い形の事象で、今の作業も消えた時は、依頼が計画の出力から消える（相手も根拠も分からないため）。検証器は active_request_missing として見つけるが、デモの API はまだ検証器を通していない。実在の家族のデータを入れる前（門②）に、送ったの記録は控えを必須にし、控えの無い事象は受け付けない。
- 根拠が要確認や削除で分からない時は、取り消しの連絡を作らず、「要るか確かめてください」と出す。ただし、送った後に家族がすでに外した依頼（§3.4 の選び直し）は、根拠が分からなくなっても要らないまま（取り消しの連絡を残す）。家族の決めごとは、計算が事象の順で読み直す（送った位置〔事象の通し番号〕と、その後の家族の選び・外し・選び直し）。事象は、サーバーが命令の権限と前提を確かめてから書いた物として信じる（計算は事象を書き直さず、命令の前提と権限の全てを独立には確かめ直さない）。事象が正しいかを独立に確かめるのは検証器（当時の家の情報と中身から作り直せなければ未判定）。
- 記録の誤り：requestRecordCorrected【新】。
  - 「送った」を押し間違え、実際には何も送っていない時だけ使う。押した本人が使い、返事がまだ無い事が条件。
  - 引き受けは、直した「送った」を除いて、その作業の変遷（担当の提案・本人の操作・送った）をたどり直す。送る前に引き受けていなければ提案に戻り（引き受けていない人の作業を「引き受けた」にしない）、後の担当替え・本人の「済んだ」・同じ作業の別の依頼は残る。検証器も同じ意味で、事象から独立にたどり直す。
  - 依頼の ID は、直して消した物も含めて、二度使わない。同じ作業の依頼は一通だけ（命令が二通目を断る）。
  - 引き受けていない担当も「送った」を記録できる（実際に送った事実を、引き受けの有無で捨てない）。
  - 元の事象は消さない。取り消しを送ったことにもならない。
  - 実際に送った後なら、取り消しの連絡を送るしかない。
  - 返事があるか、送ったか分からない時は使えない。

### 5.7 知らせ

| 状態 | 入る物 | 記録か |
|---|---|---|
| 出すべき | 今の計画から、知らせの決まり（core の純粋な関数） | 導出 |
| 送る待ち | 知らせの意図の表に、冪等のキーで入れる | 運用の表 |
| 送っている | 期限付きで引き受けた送り出し | 運用の表 |
| 受け付けられた | Push の事業者が受け付けた | 記録（notified：経路・結果・種類・中身の控え・アプリの版） |
| 失敗・結果不明 | 誤りが返った。引き受けの期限が切れた | 運用の表。限られた回数だけ試し直す |
| 要らなくなった | 送る直前に作り直したら、もう出すべきでない | 運用の表（送らずに閉じる） |

- notified は、事業者が受け付けたという意味だけで、本人に届いた・読んだ証拠にしない。
- 受け付けの後、記録の前に止まると、二度届くことがある。意図は一つに保つが、端末に一度だけ出るとは約束しない。
- デモには送り手が無い。デモの見せる物には、その時刻の「知らせの候補」を添える（apps/server/src/notify-preview.ts）：今の計画から同じ決まりで意図を作り、送る前の門（検証器）に今の意図を全部かけ、夜の待ちを分け、大人ごとにまとめた文を文の門にかける。送らず、notified も書かない。送った記録・何回目か・登録した端末・送る直前の作り直しは見ないので、画面は「まだ送っていないとした時の候補」と言い、「きょう」の画面だけに出す（試しの計算の画面には出さない）。

### 5.8 資源

| 状態 | 入る物 | 記録か |
|---|---|---|
| 候補 | 地図の検索や推定から出した物 | 計算の時の入力（§2.3）。出どころ・調べた時刻・確かでない事を付けて、案として見せてよい。店ごとに先に登録してもらうことは求めない。家族が選んだのは「この店で」という決定であり、営業時間・道のり・在庫を本人が確かめたことにはしない。これらは出どころ・調べた時刻・確かでない事を持ち続ける。在庫は約束しない |
| 使う | 家族が足した・確かめた（家族の情報の変更） | 記録 |
| 古い | 調べた時刻から決めた日数が過ぎた。家族が「違った」と言った | 導出（計画では「要確認」） |
| 調べ直した | 家族の情報の変更（調べた時刻を新しく） | 記録 |
| やめた | 家族の情報から外す | 記録 |
| 引っ越し | 家の場所を変えた | 記録。前の版は消さずに残し、新しい版から先の計画を変える。家を起点にした道のりの目安は「要確認」（導出）。家のまわりの資源を選び直す画面へ |

### 5.9 成員と家庭

- 成員：
  - 招いた → 使う（身元を結んだ）→ 止めた。
  - 止める時は、成員の表（権限の正本）と家族の情報（名前・言葉などの中身）を、一つのトランザクションで変える。
  - 止めた後の要求は、トークンが期限内でも毎回断る。止めた大人の作業は「担当がいない」になる。
- 子：
  - 所属を足す・外す（入学・進級・学童をやめる）は、効く日付きの変更。
  - 進級しても子の ID は変えない。4月の切り替えの仕組みは、今週は作らない。
- 家庭：
  - 作る（最初の設定）→ 使う → 引っ越し → 止める・消す。
  - 止めたら、すぐに読み書きと送り出しを止める。消す時は全部消す（§6.4）。

## 6. 保存（Postgres）

### 6.1 表

家庭をまたぐ参照を作らないため、家庭に属する表には household_id を持たせ、参照は (household_id, id) の組で結ぶ（ログインの身元 identities だけは家庭に属さない）。

| 表 | 主な列 | 決まり |
|---|---|---|
| households | id、種類（real・test）、状態、地域、時区、次の通し番号 | 書き込みを一列に並べる所（§7.3）。demo の家庭は本番の置き場所に置かず、メモリだけに置く。test は合成のデータの家庭（控えから戻す確かめ等） |
| identities | id、発行元、発行元の中の ID、作った・外した時刻 | ログインの身元。一意（発行元, 中の ID）。家庭を持たない。メールが同じというだけで、別の発行元の身元と結ばない |
| members | household_id、id、種類、active、identity_id（大人だけ） | 権限の正本。名前などの中身は持たない。一意（household_id, identity_id）。同じ人が、後で二つの家庭に入れる形にしておく（今週はその流れを作らない） |
| events | household_id、seq、id、type、version、occurred_at、recorded_at、actor_id、op_id、body（jsonb。§6.2 の許した欄と中身の ID だけ） | 主キー（household_id, seq）、一意（household_id, id） |
| operations | household_id、op_id、actor_id、中身の要約、結果（事象の通し番号の範囲。何も起きなかった操作も一行） | 一意（household_id, op_id）。要約は敏感な付随情報として扱う |
| payloads | household_id、id、種類、sha256、本体（jsonb）、消した時刻と理由 | 敏感な中身はここだけ。sha256 は、ここに置き、事象には置かない |
| blobs | household_id、id、R2 の無作為なキー、mime、大きさ、sha256、状態（仮・確定・消した） | 写真の本体は R2。DB と R2 は一つのトランザクションにできないので、仮で置き、DB の記録で確定し、仮のまま残った物は後で消す |
| model_calls | household_id、id、呼び出しの種類、モデル、プロンプトの版、入力の参照、始め・終わり、終わり方（ok・拒否・打ち切り・型の誤り・誤り・不明）、入出力の tokens、推定の費用、アプリの版 | 呼ぶ前に一行入れ、後で埋める。使用量が分からなければ費用も不明とし、0 にしない |
| jobs | household_id、id、種類（読み取り・削除）、状態、試した回数、次に試す時刻、引き受けの期限、誤りの種類 | 落ちても続きから。引き受けは期限付き |
| notification_intents | household_id、id、member_id、知らせのキー、種類、送る時刻、状態、試した回数、引き受けの期限 | 一意（household_id, member_id, キー） |
| push_subscriptions | household_id、id、member_id、endpoint、鍵、作った・外した時刻、最後の成功と誤り | 鍵は秘密に準じて扱う。410 が返れば外す |
| deletions | household_id、id、範囲、対象の ID、求めた人・時刻、状態、終えた時刻 | 中身を持たない。同じ記録を DB の控えの外にも書き、控えから戻した時に削除をやり直すために使う（§6.4） |

- 導いた計画の控えの表は作らない。数十〜数百の事象なら、読む度にたたみ直す。計画には、計算に使った最後の通し番号、アプリの版、計算した時刻を付けて返す。測って遅いと分かった時だけ、家庭・通し番号・家族の情報の版・アプリの版・時刻を含むキーで控えを足す。
- RLS（行の決まり）は、今週は使わない。全ての表に household_id を持たせ、使える形にしておく。使う時は、サーバーのつなぐ役に、決まりを迂回できる権限を与えない。

### 6.2 敏感な中身を、事象と分ける

01-model §2 の「分けた保管場所」を、保存の層で行う。

- 書く時に、保存の層が事象から敏感な欄を取り出して payloads に置き、事象には中身の ID だけを残す（乾かす）。読む時に戻す（戻す）。
- core のエンジンと試験は、今と同じ「中身の入った事象」を扱う。保存の分け方を、エンジンは知らない。
- 事象に残してよい欄を、事象の種類ごとに決める（許す一覧）。一覧に無い欄は、すべて payloads に置く。

| 事象 | 事象に残す欄 | payloads に置く物 |
|---|---|---|
| householdSet | なし | 家族の情報の全体 |
| noticeReceived | 出典の ID・版・届いた時刻・送り手の種類・送り手の場所の ID・言葉・届いた形・訂正元 | 題・文・写真の参照 |
| modelOutputRecorded | 呼び出しの種類・モデル・プロンプトの版・出典の ID と版 | 出力・入力のハッシュ |
| transcriptionCorrected | 出典の ID | 直した行 |
| answered | 未定の値の ID | 値・見せた品物の名前（家にあるかの答え） |
| itemConfirmed・itemDismissed | 事項の ID・理由の種類 | — |
| itemCorrected | 事項の ID | 直した解釈 |
| turnStated | 事項の ID | うちの番か・言った時の用件と対象 |
| escortStated | 事項の ID・送りか迎えか | 要るか・言った時の子・用件・日・時刻・場所 |
| itemsStated | 出典の ID | 家族の言明の事項（原文と解釈） |
| needWaysSet | 事項の ID・やり方の ID | 選んだ時の中身とやり方の版の要約 |
| optionChosen・optionDropped・assignmentProposed | キーと成員の ID・役割 | — |
| commitmentChanged | 作業のキー・成員の ID・操作 | 提案の控え・済んだ時の用件（「すること」の作業は、中身とやり方の版の要約も） |
| externalRequestSent | 作業のキー・依頼の ID・相手の ID・種類・根拠のキーと事項の ID | 文の控え |
| externalReplyRecorded・cancellationSent・requestRecordCorrected | 依頼の ID・返事 | — |
| notified | 知らせのキー・成員の ID・経路・結果・種類 | 中身の控え |
| sourceWithdrawn・sourceContentPurged | 出典の ID・範囲 | — |
| clockAdvanced | 時刻（デモだけ） | — |

- 事象に残す ID は、どれもサーバーが作る中身を含まない ID と、決まった種類の符号だけにする（§4）。許す一覧だけでは、ID に名前が紛れ込むのを防げないため。
- それでも、ID・時刻・相手の ID は結び付けられる付随情報である。出典ごとに消した後も、事象の骨（種類・ID・時刻）は残り、中身は無い。家庭ごとに消す時は、骨も消す。
- 捨てた案：
  - 事象の中に置いたまま、消す時に書き換える。分ける欄を数える手間は同じで、追記だけの決まりを日常的に破る。
  - 鍵を捨てて読めなくする（暗号の消去）。今週の規模に重く、確かめていない方法で完全な削除を約束できない。

### 6.3 消された中身をたたむ

- 戻す時に中身が消えていたら、事象は「消した」印付きで core に渡る。
- 写真だけ消した：書き起こしと事項は残るので、計画は変わらない。
- お知らせごと消した：その出典の事項・未定の値・作用は使えない。それに頼っていた依頼と引き受けは「根拠を消したので要確認」（§5.1）。
- 家族の情報の古い版を消した：今の版があれば計画は作れる。古い時点の説明は「再現できない」と示す。

### 6.4 消す

| 求め | すること |
|---|---|
| 写真だけ | R2 と blobs を消し、sourceContentPurged（写真）を記録 |
| お知らせごと | その出典の payloads（文・書き起こし・読み取りの出力・依頼の文の控え）と写真を消し、sourceContentPurged（全部）を記録 |
| 家庭ごと | 止めて、全部の表から消す。事象そのものも消す |
| 写真の保持の期限 | 決めた日数で写真だけを消す（日数は作り手が決める。§15） |

- 消すことは、削除の仕事にして、状態を持たせ、段ごとに試し直せるようにする。終えるまで「消しました」と言わない。
- 出典を消す求めが来たら、その時点で「消している」の印を付け、その出典の読み取り・モデルへの送り出し・知らせ・新しい取り出しを止める。
  - 途中の読み取りの結果は、書く前に、消していないことと出典の版が変わっていないことを確かめ直す。消した後に、遅れて届いた結果で中身が戻らないようにする。
  - 外の事業者に既に送った物は、こちらで取り消せない。
- 中身から作った物（文の題、要約、ハッシュ、ログ、仕事の記録）も、個人の情報を含み得る物として一緒に消す。
- 控え（Railway の Backups）には、控えが入れ替わるまで残る。控えの中の削除の記録は、控えを取った時より後の削除を含まない。そこで：
  - 削除の記録を、DB の控えの外（R2 の別の置き場）にも書く。中身は ID だけで、権限を絞り、控えの保持期間より長く残してから消す。
  - 順番：削除の求めを受け付けたと答える前に、外の記録を書き、読めることを確かめる。書けなければ「消している」のままにし、終えたとは言わない。DB だけ処理して外の記録が無いまま止まると、古い控えから戻した時に、その削除が分からなくなるため。
  - 控えから戻す時は、隔離した所で、この外の記録に従って消し直してから、外に出す。外の記録がそろっていると確かめられない時は、戻すのをやめる。
  - これを隔離した合成のデータで確かめるまで、「全ての写しを消した」と言わない。
- 控えから戻すと、控えを取った時より後の事（家族の操作、送った依頼、知らせ、操作の記録）は失われる。
  - 戻した時は、戻した時点を家族に示し、自動の送り出しを止める。
  - その時点より後の依頼・引き受けを、家族に確かめてもらってから再開する。
  - 戻した控えより後の操作について、送り直しの冪等は保てない。そう言う。
- 外の事業者（Claude の API、地図）に送った物の保持は、それぞれの条件に従う。使う人には、実際に送る先と保持を説明する。

## 7. 書き込みの道

### 7.1 計算する場所

**サーバーを正本にする。画面ではエンジンを動かさない。**

- 画面は、サーバーが作った見せる物（その大人の「きょう」、よてい、手配の詳細、元の文）を受け取って出す。
- 理由：
  - 知らせと書き込みの検査には、どのみちサーバーで計算が要る。
  - 画面とサーバーで版がずれると、見えた物と記録した物が食い違う。
- 「もしも」：サーバーの試算の口で答える。仮の事象を足して計算し、保存しない。
- デモも同じ道を通す。サーバーの中に、メモリに保存するデモの家庭を作り、時計はデモの時計にする。
- 電波が無い時は、確定したか分からない操作を成功と見せない。同じ操作 ID で、状態を問い合わせるか送り直す。
- 捨てた案：画面でも同じ core で計算して先に見せる。速く見えるが、二か所の版の管理と、ずれた時の扱いが要る。電波の無い所で使う要望が出たら、「下書き」と示した手元の試算として考える。

### 7.2 命令

画面は事象を直接書かない。命令を送り、サーバーが権限と前提を確かめて、事象に展開する。

| 命令 | 書ける人 | 出る事象 |
|---|---|---|
| 家族の情報を変える | 有効な大人。見た版の後に家族の情報が変わっていたら断る | householdSet（成員を止める時は members の表も） |
| お知らせを入れる（文字・写真・家族の一言） | 有効な大人 | noticeReceived（と読み取りの仕事） |
| 書き起こしを直す | 有効な大人 | transcriptionCorrected（と読み直しの仕事） |
| 事項を確かめる・直す・関係ないとする | 有効な大人。今の読み取りにあり、取り下げていない出典の事項だけ。お知らせから読んだ「すること」は、見せた時の番号が要り、見せた後に出典が変わっていたら・今より先の番号なら・文を直して読み直す前なら断る。計画に入っている「すること」（家族の言明か、家族が確かめた読み取り）の直し・外しは、見た計画の番号と見た「この変更で変わること」の要約が今と同じ時だけ。「合っている」は形のそろった物だけ。直しで形を替えない（§3.4） | itemConfirmed・itemCorrected・itemDismissed |
| 当番がうちの番かを言う | 有効な大人。今の読み取りにあり、取り下げていない出典の、家の人の当番だけ。見た画面の後に、その出典の文・事項・答え・言明が替わっていたら断る。「うちの番ではない」で無くなる作業を、ほかの大人が引き受けた・済ませていたら断る（持った人が言う） | turnStated（言った本人が引き受けていた作業は、引き受けの取り下げ commitmentChanged も） |
| 要らなくなった引き受けを分かったと言う | 担当の本人だけ。計画の released にある作業（今の計画に無くても）。見た計画の通し番号が今と同じ時だけ受ける | commitmentChanged（取り下げ） |
| 送り迎えが今回要るかを言う | 有効な大人。今の計画で生きている、確かな習い事・クラブの行事の、送り迎えの子が決まる物だけ。見た計画の通し番号が今と同じ時だけ受ける（後に記録が進んだ画面も、今より先の番号も断る。ほかのお知らせの取り消しと、その取り下げで元に戻った時も、出典ごとの番号では見えない）。「今回は要らない」で無くなる作業を、ほかの大人が引き受けた・済ませていたら断る | escortStated（言った本人が引き受けていた作業は、引き受けの取り下げ commitmentChanged も） |
| 読み直しの対応に答える | 有効な大人 | 同じ物か、どれとも違うかの事象（§4.1） |
| お知らせを取り下げる | 有効な大人。届いていて消していない出典（取り下げ済みなら何も足さない） | sourceWithdrawn |
| 写真だけ・お知らせごと消す | 有効な大人 | 削除の仕事（終えた時に sourceContentPurged） |
| 答える | 有効な大人。今の読み取りにある未定の値（宣言した値の中から）か、計画の問いの値だけ。持ち物の「家にあるか」の値は、要件が生きていて、用意の締切の前か、書かれた使う日が終わるまで（使う日が書かれていなければ締切の前）だけ（はい・いいえ。問いが消えた後の「用意できた」「やっぱり無かった」を含む。締切の後の答えでは買う手配を作らず、無いことを大人に示す。条件が外れて要らない間は、古い札からでも断る）。家にあるかの値には、画面が見せた品物の名前と、見せた計画の事象の位置の控えを必ず付け、今の品物と違うか、見せた後にその値への答えが入っていれば断る（もう一人の新しい答えを、古い札や一言の候補で上書きしない）。取り下げた・消した出典の未定の値は断る。家族が決める値（kind が family）には、見せた計画の通し番号を必ず付け、今と同じ時だけ受ける（問いの中身・もう一人の答え・読み直しが替わった後の古い札と、先の番号を断る。一言の候補も同じ）。問いの札からの答えは、見せた問い（key・until・affects）が今の時刻の問いと同じ時だけ受ける。文を直して読み直す前は断る。受けた答えには問いの形を控える（§5.3） | answered |

- 新しく決める命令（案を選ぶ・担当を提案する・引き受ける）は、今も要る（生きている）手配・作業にだけ受け付ける。古い画面からの操作で、要らなくなった計画の意図を書かないため。起きた事の記録（済んだ・送った・返事・取り消しを送った）は、要らなくなった後でも受け付ける。
- 今のたたみ方は、本人でない引き受けの操作と、有効な大人でない人の家族の言明（事項の確かめ・直し・関係ない、取り下げ、書き起こしの直し、「送った」の直し）を、記録した上で無視している。書き込みの時点で断る方を正にし、たたみ方の無視は守りの二重として残す。
- 押し間違いの取り消しには、全ての事象に効く「取り消し」を作らない。
  - 過去の事象を飛ばすと、その後の済み・返事・知らせの事実と食い違うからである。
  - 意味のある後の操作で直す：答え直す、案をやめる・選び替える、できなくなった、記録の誤り（§5.6）。
  - 最初は、何でも戻すボタンを置かない。

### 7.3 一つの命令の処理

一つのトランザクションで行う。

1. 身元を確かめる（トランザクションの前）。
   - Cloudflare Access の署名付きトークン（署名・発行元・対象・期限）を確かめる。
   - 全ての入口で確かめ、トークンが無いか正しくない要求は、Railway に直接来た物も含めて断る。
   - Cloudflare を通った要求だけを源に届かせるため、Railway の公開のドメインを作らず、外からの道を Cloudflare Tunnel だけにする（01-model §11 の置き場所）。実際の環境で確かめるまで「直接の要求は全部届かない」とは言わない。
   - Cookie で書き込む要求は、Origin を確かめる。
2. households の行を、書き込みのために押さえる。同じ家庭の書き込みは、一列に並ぶ。
3. 押さえた後に、その身元の成員が今も有効か、その家庭の権限があるかを、トランザクションの中で確かめ直す（押さえる前に止められた時のため）。
   - 確かめるのは、成員が有効な大人であること、確かめた身元が今もその成員に結ばれていること、身元を外していないこと。読むだけの要求（見せる物）も、押さえた中で同じく確かめ、通らなければ家庭の物を何も返さない。
   - これが撤権と互いに排他になるのは、撤権（成員を止める・身元を外す・結びを外す）の書き込みも、先に同じ家庭の行を押さえる時だけである。撤権の操作を作る時は、同じ順で押さえる（関わる家庭を全て押さえてから表を変える）。本物の Postgres での並びの試験と合わせて、門②の条件にする。
4. operations で操作 ID を引く。
   - あって、元の操作をした人が同じで、要約も同じなら、何も足さずに今の見せる物を返す。
   - 人か要約が違えば、衝突として断る。
5. 事象を読み、たたみ、今の計画を作る。
6. 権限（§7.2）と前提を確かめる。
   - 例：引き受けは、その作業が今あり、本人に提案されていて、提案の控えが今の提案と同じ時だけ。
   - 押した人が見た版の後に、対象が消えたか、提案・決め時が変わっていたら、409 と新しい見せる物を返し、本人に見直してもらう。
7. 事象に通し番号を付けて足し、operations に一行足す。何も起きなかった操作も一行足す。
   - 理由：「A を選ぶ」が既に A で何も起きず、後で別の人が B にした後、同じ操作の送り直しで A に戻すのを防ぐ。
8. 終える。新しい計画から見せる物を返す。知らせの判定をすぐ一度する（§9）。

- モデル・地図・Push への通信の間は、DB の押さえを持たない。地図の結果が古ければ、押さえの外で引き直し、押さえた後に版と調べた時刻を確かめてから使う。

## 8. 読み取りの道

1. 受け取る。
   - 文字か写真。出典の ID を作り、写真は R2 へ仮に置く。
   - noticeReceived を記録し、読み取りの仕事を待ちに入れる。
   - 写真の大きさ、文の数、条件の節点の数（今は64）に上限を置く。
   - 「あした」「きょう」の基準の日は、お知らせが書かれた日（連絡帳の日付）であり、写真を撮った・入れた時刻ではない。前の日の連絡帳を後で撮った時や、夜中を越えて入れた時に、入れた日を基準にしない。書かれた日が分からなければ、家族に確かめる。モデルが返した日付と、コードが「あした」から決めた日付が違えば、食い違いにする。
     - 今のコードは、受け取った時（receivedAt）の家庭の時区の暦日を基準にしている。これで合うのは、受け取った日が元の文の書かれた日と同じ時だけである。前の日の連絡帳を後で撮った写真、LINE の古い連絡を次の日に転送した物、連絡帳の文を後で打ち込んだ物では合わない。取り込みを作る時に、書かれた日を出典の欄に持たせ、分からなければ家族に確かめる（写真も文も同じ決まり。それまでは設計）。食い違いの検査は実装済み。
   - 写真は、置く前にサーバーで付随情報（EXIF の撮った場所・時刻など）を外す。置く物と Claude に送る物は、外した後の同じ画像にする。外れたことを試験で確かめ、使う人への説明も実際の処理に合わせる。確かめるまで「外した」と言わない。
2. 写真なら書き起こす：modelOutputRecorded（transcribe）。
   - 行ごとの読みにくさを持たせ、画面で写真と並べて、読みにくい行を目立たせる。
   - 全行の確認は求めない。
   - モデルが言う確かさは危うさの目印にすぎず、確かさが高くても正しいとは限らない。
3. 読む。
   - 関係する出典の今の事項を ID 付きで渡す。
   - 出力をコードで検査する：型、文 ID、日付と曜日、条件、作用の ID、出典の版。
   - 通れば modelOutputRecorded（extract）。読んでいる間に出典の版が上がっていたら、その出力は当てない。
4. 失敗する。
   - 拒否・打ち切り・型の誤りは、有効なデータとして扱わない。
   - 試し直しは回数と待ちに上限を置き、試しごとに model_calls を分ける。
   - TypeScript の SDK は既定で自分で2回試し直すので、`maxRetries: 0` にして、試し直しはこちらで行い、一回ずつ記録する（SDK の中の試し直しで、記録に出ない呼び出しを作らない）。
   - だめなら仕事を失敗にし、画面に「読めませんでした」と、もう一度・手で書くを出す。
   - デモの録った応答で、本番の失敗を埋めない。
5. 代償の大きい作業の前に見せる。
   - 買い物・休み・人に頼むの前には、要の日付・対象と、元の文（写真のその所）を家族に見せる。
   - 確かさの高さにかかわらず、決める画面で見せる。
   - 自動で進めてよい境界は、実際の写真で測ってから決める。
6. 費用：呼び出しごとに model_calls（§6.1）。
7. 家族の家庭の入口（試しの家庭だけ）。
   - お知らせの文と一言を Claude で読むのは、試しの家庭（データベースで test と印を付けた、架空の家族の家庭）で、読み取りの鍵があるサーバーだけ（/api/me の canRead・canHear）。印は、中身が架空だという証明ではない。実在の家族の材料は、今週はサーバーに入れない（§11）。写真の書き起こしは、家族の家庭ではまだ開けない。
   - 本文に、画面が見ている大人（as）と操作 ID を付ける。操作する人はサーバーが身元で決め、as は替わった時の検出だけに使う（identityChanged）。モデルへ送る前と、結果を足す前に、身元と家庭を確かめ直す。
   - 上限：家庭ごとに一日の回数（お知らせと一言を合わせて。UTC の日付で数え、日本時間の朝 9 時に戻る）と、同時に一件。長すぎる文も同じ断り（readingLimit）なので、画面は「文が長すぎるか、回数の上限」と書く。失敗も一回と数える。
   - 操作の表には、操作の種類・大人・中身の要約（ハッシュ）・番号だけを置き、文は置かない。同じ操作 ID で中身が違えば断る（operationReused）。前の操作の結果がサーバーにも分からない時（呼び出しの途中で止まった等）は readingUncertain を返し、同じ操作では外へ送り直さない。画面は、予定を確かめてから、新しい操作で入れ直してもらう。
   - 一言の候補は、言った本人が確かめた時だけ記録する（/api/proposals/:pid）。見せた後に対象が変わっていれば記録しない（proposalChanged）。記録してよいかは、サーバーが core の recordBlock で決める：同じ種類の相手（計画の生きている作業〔比べるための案の作業も〕、記録の先になりうる頼み事、一言で答えられる未定の値〔家にあるかとほかの値を分けない〕）がほかに一つも無い時だけ記録できる。題・名前・品名・控えの文・日付の表示は、家族やお知らせの文で真似でき、同じに見えて違う物（空白・見えない文字・形の似た字）を見分けられないので、どれも比べない。試しの家庭では、「すること」の頼み事の返事と取り消しを伝えたことは、いつも札で記録する。候補を出す時に訳（blocked）を付け、画面は記録の手を出さない。押された時も、家庭を押さえた中で今の事象と時刻から同じ判断をし直し、記録しない（proposalChanged）。
   - やり方の案（§3.4）も同じ入口の決まり（canRead・as と身元・操作 ID・一日の回数と同時に一件。回数はお知らせ・一言と合わせて数える）。事象は足さず、案はサーバーのメモリに少しの間だけ置く（操作の表には要約だけ）。前の結果がメモリから消えていれば readingUncertain を返し、画面は新しい操作で出し直してもらう。
   - 画面には「架空の文だけ」と、Claude に送る物を書く（お知らせ：入れた文と、この家庭ですでに記録した事項〔家族が言ったことを含む〕と未定の問い。一言：一言と、家族・頼める人の名前、今の事項・作業・頼み事〔相手や場所を含む〕。やり方の案：§3.4 の送る物と、送る文と名前に書かれた事はそのまま送られること）。

## 9. 時間と定時の仕事、知らせ

- 時計：
  - 本番はサーバーの時計。試験とデモだけ時計を差し込む。
  - 日付だけの物はその地の日付、時刻のある物は時区付きで持つ。
- 繰り返し：
  - サーバーのプロセスの中で、5分ごとと起動の時に回す。外の cron や別のキューは足さない。
  - 仕事と知らせの意図は DB にあるので、落ちても続きから再開する。
- 知らせの判定：
  - 書き込みの後にすぐ一度と、繰り返しの度に行う。
  - 本番の家庭ごとに今の計画を作り、知らせの決まり（core の純粋な関数）で、出すべき知らせを出す。
- 送り出し：
  - 意図を冪等のキーで入れ、期限付きで引き受けてから送る。
  - 送る直前に、もう一度作り直し、取り消し・担当・期限を確かめる。
  - 事業者が受け付けたら notified を記録する。
  - 失敗や結果不明は運用の表に置き、限られた回数だけ試し直す。
  - 送り出しは、一つのプロセスから始める。増やす時は、仕事の引き受けにだけ `SKIP LOCKED` を使う。
- 止まっていた間の分：
  - 起動の時に、まだ役に立つ物（決め時・問いの期限の前）だけ送る。
  - 役に立たなくなった物は送らず、画面に「過ぎた決め時」として出す。
- 時機：
  - 決め時の知らせには、5分の間隔より十分前の余裕を持たせる。
  - 新しく出た物で残りが5分も無い時は「すぐ扱う」とだけ言い、時刻ちょうどを約束しない。
- 文：
  - ロック画面の文には、子・学校・人の名前を入れない。
  - Service Worker は家族の API の応答を保存しない。
  - iPhone のホーム画面の PWA と Access と知らせの組み合わせは、実機で確かめる。成り立たない間は画面の中の表示を使い、送れたと装わない。
  - 一台の iPhone で二人の大人を切り替える時（デモと、作り手の確かめ方）：同じ Push の登録先で使う人が替わったら、前の人との結び付きを外す。知らせから開いた時は、今の身元で権限を確かめる。実機で確かめるまで、本人に届いたとは言わない。デモの画面の中の切り替えは、Access の身元の切り替えや、本人ごとの知らせの証明にならない。
  - 一人が複数の端末を使う時は、一つの意図について、登録先ごとに試しを記録する。今週は複数の端末の流れを作らない。

#### 9.1 知らせの決まりと送り出し（2026-11-02 に作った形）

- 出すべき物（core の `notificationIntents`。有効な大人ごとの「きょう」の上の札から）：
  - 取り消し・要確認：札が出たら。頼んだ時間の終わりまで（始まった後も残りがある）。夜に待つかは、頼んだ時間の始まりで決める。
  - 予備：札が出たら（札は次の案の決め時の26時間前から出る。予備がもう確保できていれば出さない：§5.6）。
  - 決める事：最初に選べなくなる案（選んだが使えなくなった案を除く）の決め時の26時間前から。札を見る大人の全員に。
  - 頼まれた事：もう一人の大人が頼んだ物は、すぐ。自分で自分に頼んだ物は出さない。仕組みの提案（提案の事象が無いか、system が書いた物）は、決め時の26時間前から。引き受けた後に中身が変わった物は、誰が頼んだ物でも出す。
  - 問い：聞く期限の26時間前から。家族が決める値の問いは、答えが要る最後の時（until）の26時間前から（until の無い問いは知らせない）。
  - 「すること」の手配の札（大人の全員に）：本命を選ぶ時は、決める事と同じく、最初に選べなくなる案の決め時の26時間前から（決め時のある案が無ければ知らせず、札だけ）。やり方をまだ選んでいない（選び直す）時は、確かめた日時（窓の形は窓の始まり、締切の形は締切。締切の形の手配の始まりは計算した時刻〔締切を過ぎた後は締切〕なので使わない）の26時間前から、その終わりまで、中身を言わずに（選ぶ前は、やり方の前もっての手順〔前の日の予約など〕が分からないので、その時ではもう遅いこともある）。窓の受け持ちを確かめられない時間は、窓の始まりの26時間前から終わりまで（夜に待つかは始まりで決める）。間に合う進め方が無い時と、選んだやり方のどれも決め時を出せない時は、札だけ（できないとは言い切らない）。
  - 読み取りを確かめる札：お知らせから読んだ「すること」を、読み取りの事象から1時間たっても確かめていなければ、そのお知らせを入れた大人にだけ一度（中身は入れない。同じ読み取りの事項は一つにまとめ、キーは出典と読み取りの事象の番号。仕組みが入れたお知らせには出さない。読み取りの日時は確かめていないので期限にせず、夜は朝まで待つ。締切に間に合うとは言わない）。全部を確かめる・外す・取り下げると消え、読み直せば新しい読み取りから数え直す。ほかの知らせと同じく、札が消えてまた出れば次の回として知らせる（拠る別のお知らせの読み直しで確かめが外れ、札が戻った時も）。もう一人の大人に知らせるかは、まだ決めていない。
  - 期限を過ぎた物は出さない（止まっていた間の分も）。
- キーは「何についての知らせか」（計画の ID と決まった符号と成員の ID）だけで、時刻・品物などの中身を入れない。検証器が照らせるよう、意図は元の物（作業・依頼・手配と案・問い）を構造で持つ。
- 回（何回目か）：
  - 書き込みのまとまり（一度の家庭の押さえの中で足した事象。events の batch に最初の通し番号）ごとに、前に見た所から事象を再生し、無かったキーが出たら回を一つ進める。同じキーが出ている間は一回で、消えてまた出れば次の回（見回りの合間でも、同じ分の書き込みでも落とさない）。
  - 最後に今の時刻で作り直す（時刻だけで出る・消える物は、5分ごとの見回りで拾う）。初めて見る家庭は、再生せず今の形を一回目とする。
  - 見た位置（households の notified_through_seq）・意図の表の読み・再生・書き戻しは、家庭の行を押さえた一つのトランザクションで行う（命令とも、別のプロセスとも重ならない）。
  - notified には「キー#回」を残す。
- 夜（家庭の時区で22時〜7時）は、朝まで待てる物を7時まで待つ。7時に送ると、本人が動く時（無ければ期限）まで2時間の余裕が無い物は、夜でも送る。
- 同じ大人に同時にいくつも出れば、件数の文で一通にまとめ、意図ごとに notified を残す。
- 送る前の確かめ：
  - 家庭を押さえて作り直し、まだ出すべきか・身元が今も結ばれているかを見る。回を数えた後に家族の書き込みがあれば（その間に消えてまた出て、次の回になったかもしれない）、今は送らず、次のまわしで数え直してから送る。
  - 検証器：計画の違反があれば、その家庭の知らせを全部止める（どれに響くか絞れない）。知らせの検証の違反は、そのキーだけ止める（$all なら全部）。実際に送る文も、決まった文かを確かめる。未判定は止めない（文は事実を言い切らず、開いて確かめてもらうだけ）。回の数え方は検証器では未判定で、サーバーの試験で確かめる。記録には違反の種類だけを残す。
  - 事業者に持たせる時間（TTL）は、期限までの残り（最長24時間）。残りが無ければ送らない。
  - 引き受けるごとに札（乱数）を付け、送った後の状態は自分の札の行だけを替える（期限の切れた古い引き受けが、後から引き受けた物の結果を上書きしない）。送る前に、その回が notified に記録済みなら送らない（記録の後・状態の更新の前に止まった時に、送り直さない）。事業者が受け付けた後・記録の前に止まった時の二度送りは、防げない。
- 登録先：
  - 大人ごとに一つ。知っている Push の事業者（Apple・Google・Mozilla・Microsoft）の https の宛先だけを受ける（サーバーから任意の住所へ送らない）。
  - 同じ宛先で別の大人が登録すれば、前の人との結び付きを外す。登録ごとの版（乱数）を持ち、送る直前に同じ大人・身元・版かを確かめる。無くなった（404・410）宛先と、結びの外れた身元の登録は、読んだ時と同じ版の物だけを消す（その間に登録し直された物は消さない）。
  - 登録する・外すは、家庭の行を押さえた中で結びを確かめ直し、同じ取引の中で書く（命令と同じ。撤権と互いに排他になる条件も同じで、§7.3 の 3）。
  - 登録には、端末が頼んだ時（その端末の時計）を添える。同じ登録先で、後から頼まれた登録が先に済んでいれば、遅れて届いた前の登録は断る（一台の端末で使う人が替わった時）。同じ時なら、別の人の登録は先に済んだ方を残す。違う端末の時計とは比べない。
  - 残る隙：新しい人が知らせを止めて登録を消した後に、前の人の遅れた登録が届くと、比べる時刻が無いので受けてしまう。止めた時は端末の購読も外すので、その宛先には、ふつう事業者が「無い」と返し、最初に送る時に消える（実機では未確認。購読を外せなかった時は、前の人の知らせがその端末に出得る。文に名前は無く、開けば今の身元で確かめる）。実際の家族が一台の端末を分けて使うなら、消した後も時刻を残す形にする（門②で見直す）。
  - 送る事と記録は一つにできないので、確かめた後・送る前の替わりまでは防げない。ロック画面の文に名前を入れず、開いた時に今の身元で確かめる。
- 画面：家族の家庭だけ。iPhone はホーム画面に追加した時だけ受け取れる（追加を案内する）。許可は押した時だけ求める。Service Worker は知らせを出すだけで、API の応答を控えない。
  - 止める時は、サーバーが外したと答えた時だけ、端末の購読を外す。使う人が替わった・画面を閉じた後は、前の人の操作の続き（購読を作る・外す）をしない（端末の購読は、次の人の物かもしれない）。
  - 知らせを押して、前から開いていた画面に戻った時も、身元を確かめ直す（確かめる間、前の人の画面は出さない）。
- まだ確かめていない：iPhone の実機でのホーム画面の PWA・Access・知らせの組み合わせ（11/4）、大人ごとの静かな時間、複数の端末。

## 10. 版と「なぜそう言ったか」

| 物 | 決まり |
|---|---|
| 事象の形 | 事象の種類ごとに版を持つ。古い版を今の形に読み替える関数を core に置き、互換の試験を付ける。保存した事象は書き換えない（例外は §6.4 の削除）。知らない新しい版は、無理に読まずに止める |
| 計画のキーの形 | 事象が指す契約。変える時は、読み替えの関数で古い事象のキーも写す |
| プロンプト | 版を modelOutputRecorded に残す。新しい版は新しい出典にだけ使う。古い出典は、明示して読み直す時だけ（§4.1） |
| 家族の情報 | householdSet ごとの版。計画は、その時の最新の版で、先の事を計算する |
| エンジン | 計画は保存しないので、版が変われば計画も変わり得る（それでよい） |
| 説明 | 「あの時なぜ」は、人が見た物（提案の控え、依頼の控え、知らせの中身）で示す。notified と model_calls にアプリの版（Git のコミット）を残す |

- 保存した事象が一つも無い間（門②の前）は、事象の形を版を上げずに変えてよい。デモと試験の事象はコードから作り直す。実在の家族の事象を最初に保存した時に v1 を固め、以後の変更は版を上げて読み替える。
  - 2026-11-02：提案の控え（shown）を全部の欄に広げ、notified に経路・結果・種類・中身の控え・アプリの版を足した。この規則による変更で、前の形は読まない。
- 完全に再現できるのは、要る中身、その時のコードと依存、時間のデータ、許された外のデータがそろう時だけである。
- 消した原文、保存できない地図の結果、失われた古い版があれば「再現できない」と示す。今の地図や新しいモデルで埋めない。

## 11. 秘密と個人情報

- 鍵：手元は `.env`、本番は置き場所の秘密の設定。ブラウザ・Git・ふだんのログに出さない。
- 家庭の分離：
  - 全ての API・DB の検索・仕事・写真の取り出しを、確かめた身元から引いた household_id で絞る。
  - 二つの試験用の家庭で、互いに読めず書けないことを、実際の Postgres で確かめる。
- Claude に送る物：
  - 出典（文字・写真）と、関係する出典の今の事項だけ。家族の情報の名前・住所・ふだんの週は送らない。例外：一言とやり方の案は、家族・頼める人・場所などの名前を送る（何を送るかは §8・§3.4。押す前に画面に出す。今はデモと試しの家庭だけ）。
  - 原文・家族の考え・家族が付けた名前そのものに個人の情報が含まれ得る（連絡帳の写真の名前、考えに書いた住所など）。欄を送らないことを、文に書かれた事を送らないことと言わない。どの文字・写真を送るかは、作り手が許した範囲に限る（§15）。
- ログ：
  - ID・数・時間・終わり方だけ。本文・文・名前・入力の要約を出さない。
  - 送ってよい項目の一覧で、送り出しとログを絞る。
- 写真の URL・R2 のキー・Push の登録・文の要約も、漏れ得る物として扱う。
- 公開のデモは架空の家族だけで、本番と読み書きの先を分ける。
- 処理と保存の場所：
  - Railway はシンガポール（作り手が了承）。
  - R2 の場所の指定は、保存の国の保証ではない。
  - Claude と地図の処理・保持の条件は別に確かめ、使う人に説明する。
  - 地図のデータは条款に従い、place ID 以外の営業時間・道のり・写真を、自由に保存してよいとはみなさない。

## 13. 段階と、今のコードから直す順

### 13.1 段階

1. **架空のデモ**：今の純粋なエンジンで通す。サーバーの道（メモリの保存）に載せ替える。
2. **実在の家族のデータの前の門**：次をそろえ、架空のデータで実際の環境（Railway・Cloudflare・iPhone）で確かめる。
   - 身元
   - members と identities
   - 家庭の分離
   - 事象と payloads の分け方（許す一覧）
   - 命令と operations
   - 家庭の行の押さえと 409。撤権（成員を止める・身元や結びを外す）の書き込みも同じ家庭の行を先に押さえ、読む・書くと互いに排他になることを、本物の Postgres の並びの試験で確かめる（§7.3 の 3）
   - 書き込みの Origin と JSON の確かめ、家族の家庭の返事を控えに残さない（no-store）
   - 送った依頼の控え（必須にし、控えの無い送ったの事象は受け付けない。§5.6 の残る穴）
   - 引き受けの提案の控え（accept の命令に必須。控えの無い引き受けは、今の作業を確かめたことにしない）
   - 読み取りの仕事は、実際に読んだ出典の文の版（sourceVersion）を必ず記録し、書く前に今の版と照らす
   - 消す（家庭ごと・取り下げ・写真・お知らせごと）、消している間の止め方、DB の控えの外の削除の記録（先に書いて読めることを確かめる）と、控えからの戻し（戻した後は送り出しを止め、家族が確かめてから再開）
   - 写真の付随情報を外す
   - 知らせの意図と結果
   - model_calls（SDK の試し直しを止める）と上限
   - 源が公開の入口を持たないこと（Railway の公開のドメインが無く、外からの道が Tunnel だけであること）を、実際の環境で確かめる
   - 一台の iPhone で二人の大人を切り替えた時の、Push の登録と身元の結び付き（§9）。登録の順は端末の時刻で決めるが、新しい人が止めて登録を消した後の、前の人の遅れた登録は断れない（§9.1 の残る隙）。実際の家族が一台を分けて使うなら、消した後も時刻を残す形に直すか、一台を一人で使う決まりにして、実機で確かめる
   - 家族の情報の ID を、中身を含まない ID にそろえる（家族が書いた成員・場所・取れる手・手順の ID は、事象の actorId・taskKey・知らせのキーにそのまま残るため。入口で付け替え、配列の参照・組み合わせた ID・控えも含めて試験する。§5.8）
   - 読み取りの事項の ID も、中身を含まない ID に付け替える（今はモデルが付けた出典の中の ID を、出典の ID につないでいる。事象の itemId・作業のキーに残るため。turnStated などの言明も含めて試験する）
   - **この門を通るまで、実在の家族のデータを入れない。**
3. **後で**：繰り返しの決まりの広げ方、地図、性能の手当て、パスキー。要る時に足す。

## 14. 捨てた案

| 案 | 捨てた理由 |
|---|---|
| 正本を事象の列だけにする | 個別の削除と、今の権限の即時の遮断ができない |
| 全部を今の値の表だけにする | 「誰がいつ何に同意したか」と、取り消しの根拠が残らない |
| 画面でもエンジンを動かして先に見せる | 二か所の版の管理と、ずれた時の扱いが要る。§7.1 |
| モデルに事項の同じを決めさせる | 読み落としや分割で、引き受けを別の物に付け替える。§4.1 |
| 読み直しで見つからない事項を消す | 読み落としで、明日の持ち物が黙って消える。§4.1 |
| 全ての事象に効く「取り消し」 | 後の済み・返事・知らせと食い違う。§7.2 |
| 操作の記録を事象だけで済ませる | 何も起きなかった操作の送り直しが、後の他の人の選択を戻す。§7.3 |
| 外の cron・別のキュー・複数の送り手 | 今の規模に要らない。DB の意図と期限付きの引き受けで、後で移せる |
| 端末に一度だけ届くことの約束 | 外の受け付けと DB の記録を一つにできない。§5.7 |
| 中身を事象に置いたまま、消す時に書き換える | §6.2 |

## 15. 作り手が決める点
