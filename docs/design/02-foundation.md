# 地基の設計 — 正本・概念・生命周期・保存・書き込み

- 状態：初版（2026-11-02 夜）。作り手の指示（機能の細部より先に底層を固める）を受けて、二人が同じ問いに独立に答え、突き合わせて一つにした。
- [01-model.md](01-model.md) は、事実の型・決め時・問い・引き受け・求解・検証の中身を決める。本書は、その下の地基を決める。
  - 何を正本として記録し、何を導くか。
  - 概念の全体と、新しい場面の置き場所。
  - 識別とキー、生命周期、保存の表、書き込みの道。
  - 版、秘密、試験の層、実在の家族のデータの前の門。
- 食い違えば本書に従い、01-model を直す。
- 「確かめた」と書いた物は、今のコードを読むか、架空の材料で動かして確かめた。それ以外は決めた設計で、まだ作っていない。

## 1. 約束（不変条件）

地基の良し悪しは、次を守れるかで測る。機能を足す時も、これを破る形にはしない。

1. **元へ戻れる**：計画のどの物からも、元の文（と写真）へたどれる。
2. **確かでない物で決めない**：
   - 推定・食い違いの事項は、家族が確かめるまで、必須の要件を作らない。
   - 条件が分からない事項は、間に合わなくならない側で「条件しだい」として計画に残すが、確かな事実や、自動で進めてよい物としては見せない。
   - どちらも、条件が偽の事項も、前の事実を変える作用（日付を決める・置き換える・取り消す）を起こさない。
3. **計算はコード**：日付・決め時・条件・配置・検証は、コードで行う。モデルの出力で置き換えない。
4. **変わったら伝わる**：事実が変われば、要らなくなった作業と依頼が分かる。頼んだ後なら、取り消しの連絡の作業ができる。
5. **再現できる**：同じ事象を、同じ版のコードで、同じ時刻まで流せば、同じ計画になる（地図から引いた入力を除く。§2.3）。
6. **人が見た物は残る**：人が判断した時に見ていた物（提案の中身、送った依頼、知らせ）は、その判断と一緒に記録する。後でエンジンが変わっても、「あの時なぜそう言ったか」を示せる。
7. **誰かが持つ**：生きている作業は、どれも担当（提案を含む）があるか、「担当がいない」と示される。
8. **家庭を混ぜない**：どの読み書き・仕事・写真の取り出しも、確かめた身元の家庭の中だけで行う。
9. **消せる**：敏感な中身は消せる。消した後に、消した物に頼る部分を「再現できる」とは言わない。
10. **分からないと無理を分ける**：読めない、探し切れない、データが無い時は「まだ判断できない」「要確認」とし、「無い」「無理」「取り消された」とは言わない。

## 2. 正本と導く物

### 2.1 正本は三つの組

| 正本 | 中身 | 変わり方 |
|---|---|---|
| 事象の列 | 家族がした事と、外から来た物の順。家庭ごとの通し番号 | 追記だけ（例外は §6.4 の削除） |
| 消せる中身 | 原文・書き起こし・写真・読み取りの出力・家族の情報・答えの値・提案の控え・依頼の文 | 事象から ID で指す。消せる |
| 今の権限 | 成員が有効か、ログインの身元とその対応 | 表の今の値が正本。古い事象を流し直しても、止めた成員の権限は戻らない |

- 計画・各自の「きょう」・問い・知らせの予定は、この組と今の時刻から、毎回作る。保存しない（§6.1）。
- 運用の表（操作の記録、知らせの意図と結果、仕事、削除の記録、API の呼び出しと費用、Push の登録）は、家族の事実ではない。
  - ただし、それぞれの運用については、それ自体が正本である。上の三つから作り直せない。
  - 例：操作の記録を失うと、送り直しの冪等が崩れる。結果不明の知らせの記録を失うと、二度送る。
  - 同じ DB に置き、同じ控えに入る（削除の記録だけは、控えの外にも置く。§6.4）。
- 家庭ごとの削除では、運用の表も消す。残すのは次の二つだけで、どちらも家族の中身を持たない。
  - 削除の記録：ID だけ。控えの保持期間が過ぎたら消す。
  - 費用の集計：家庭に結び付かない回数と費用。

### 2.2 記録する物と導く物の決まり

- 人がした事と、外から来た物だけを記録する。
- 時間で決まる状態は、記録せず導く。例：決め時が過ぎた、問いの期限が過ぎた、営業時間の情報が古い、決め時を過ぎても始めていない。
- 人が判断した時に見ていた物は、判断の事象と一緒に記録する（§1 の6）。
- 外への作用（送った・返事があった・取り消しを送った・知らせが受け付けられた）は、作業の状態から逆算せず、それぞれの事象として記録する。

### 2.3 正本に入れない外の入力

- 地図の結果（店の候補、営業時間、道のり）は、条款のため正本に入れない。計算の時にその時に引いた物を入力として使い、計画には place ID と調べた時刻を付ける。
- そのため、過去の計画の地図に頼る部分は、後から正確には再現できない（01-model §2）。§1 の5の「再現」は、地図に頼らない部分と、家族が入れた営業時間・道のりの目安について言う。
- 家族が確かめて入れた物（自分の使う店の営業時間など）は、家族の情報として正本に入る。

### 2.4 外とのつながり（カレンダー・LINE）

- 今週は、確定した事の書き出し（ICS）と、家族が写して送る下書きまで（02-product §5.3）。下書きを、送った事として扱わない。送ったかは、家族の「送った」の記録だけで決める。
- 後で Google カレンダーや LINE とつなぐ時は、それぞれを別のつながりとして足し、家庭・外の ID・許可・重なりの取り除きを持たせる。同期や送り出しの受け取りは、新しい事実として事象に記録する。今は、つなぐための仕組みを先に作らない。

### 2.5 計算の後の検証

- 毎回の計算の後に、検証器を走らせる。
- 違反のある部分は、「決めてよい」と見せず、それに頼る知らせも出さない。画面には「確かめられませんでした」と出し、違反は運用の記録に残して直す。
- 違反が計画全体に及ぶか、どの作業・知らせに響くかを絞れない時は、響き得る物を全部止める。はっきり切り分けられる時だけ、残りを出す。
- 未判定は違反と分けて扱い、未判定であることを画面に出す（隠さない）。未判定の前提に頼る作業と知らせは、確かな事実として見せない。

## 3. 概念の全図

### 3.1 地図

```
家庭
 ├─ 成員：大人・子・頼める人（祖母）  ── 身元（ログイン。大人だけ）
 ├─ 所属【新】：子 × 通う所（学校・園・学童・習い事・塾）、始まりと終わりの日
 ├─ 資源【広げる】：家・駅・職場・店・郵便局・診療所・薬局・通販
 │      営業時間（出典と調べた時刻）、扱う物・できる事、道のりの目安
 ├─ ふだんの週：大人も子も、曜日ごとの区間（在宅・場所が決まらない、も選べる）
 ├─ 習い事・塾の決まり【新】：毎週の回（曜日・時刻・場所）と、回ごとの決まり
 │      （試合の日はユニフォーム、月謝は1日まで）。決まりの変更は効く日を持つ
 ├─ 取れる手【広げる】：子の居場所（学童・有休・祖母）、買う（店・通販）、用事（郵便局など）
 └─ 分担の決まり【新】：作業の種類ごとに、誰に提案するか

出典（文字・写真）→ 事項（種類、元の文、条件、証拠の状態、前の事項への作用）
                    │      ↑ 未定の値 ← 答え（家族・後の出典）
                    ↓
                  要件（何を、いつまでに、どの子の）
                    ├─ 選べる方法がある → 手配 → 案（手順・代償・決め時）→ 作業
                    └─ 方法が一つ　　　 → 作業
作業 → 引き受け（本人。提案の控えと一緒に）→ 依頼（送った時の控え）→ 返事
                                              └→ 要らなくなれば、取り消しの連絡の作業
知らせ：担当の本人だけに、もう待てない時だけ
```

流れ（出典→事項→要件→手配・案→作業→引き受け→依頼）は、新しい場面でも変えない。新しい概念は【新】の三つと、資源・取れる手の広げ方だけにする。

### 3.2 新しい場面の置き場所

| 場面 | 入口 | 事項・回 | 要件 → 作業 | 境界 |
|---|---|---|---|---|
| 連絡帳（毎日） | 写真の出典 | 持ち物・宿題とサイン・テスト・当番・プリント。「あした」はコードが日付にする | 持ち物 → 前の晩の用意。家にあるか分からなければ問い、無ければ買う手配。サイン → その晩の作業。テスト → 家族が決めた日数の前に、子へ声をかける作業。当番 → その日の作業 | 「プリント1まい」から中身を作らない。日付だけの締切は日付で持ち、無い時刻を作らない。勉強の仕方は助言しない |
| 習い事・塾 | 所属と決まり（家族が設定）、クラブからの連絡（出典） | 決まりから導く回。連絡は、ある一回への作用（中止・時刻や場所の変更・練習から試合へ） | 回ごとに、決まりから持ち物・送り迎え・月謝の作業。送り迎えが勤務と重なれば子の居場所の手配 | 一回の中止と、以後の決まりの変更を分ける（一回の雨天中止で翌週を消さない）。祝日や振替が分からなければ未判定 |
| 買い物 | 持ち物の要件 | — | 手配の案：帰り道の店（寄り道）、昼休みの職場の近くの店、通販（家族が入れた「何時までに注文すれば何日に届く」の目安）、祖母に頼む。それぞれ決め時を持つ | 通販のアカウントにつながず、支払いを扱わず、在庫や届く日を言い切らない。目安は目安と示す |
| 用事 | 家族が書いた一言（家族の文字の出典） | 用事（例：金曜までに書留を出す） | 手配の案：家の近くの郵便局（土曜の朝）、職場の近く（昼休み）。営業時間と決め時 | 手で入れる別の道は作らず、出典と同じ道を通す |
| 診療所 | 資源として、家族が自分の使う所を登録 | — | 営業時間・休診日を、予定を組む時の制約に使うだけ | 「どの病気でどこへ」は言わない（医療の助言をしない） |

### 3.3 最初の設定

- 最初に集める：家、学校・園・学童、大人それぞれの職場と通勤。在宅・場所が決まらない、も選べるようにして手間を減らす。
- 家の位置は、住所か地図の点を入れられる（家まわりの店や寄り道の道のりに要る）。駅や町の粒度だけを選んでもよく、その時は道のりを「粗い目安」と示し、家の戸口までの正確さを約束しない。より細かい位置を出すことを強いない。家の位置は消せる中身として持ち、Claude には送らない。
- 後で、使う場面が来た時に聞く：店の好み、細かい決まり、資源の追加。
- 欠けていても、エンジンは止まらない。欠けた所に頼る計画は「入力が足りない」という理由付きの未判定にして、要る時に聞く。
- 寄り道の計算には職場と通勤が要るので、最初の設定を駅と大まかな時間だけに縮めない。

## 4. 識別と安定キー

| 物 | ID | 変わらないための決まり |
|---|---|---|
| 操作 | 画面が作る操作 ID（UUID） | 同じ ID の二度目は、中身の要約が同じなら今の状態を返し、違えば衝突として断る（§7.3） |
| 事象 | サーバーが作る ID と、家庭ごとの通し番号 | 画面は通し番号を付けない |
| 出典 | サーバーが作る | 訂正は版を上げる。古い版への遅れた読み取りで、新しい版を上書きしない |
| 事項・未定の値 | サーバーが作る、中身を含まない ID | モデルの局所 ID は、その呼び出しの中で対応を取るためだけに使い、保存しない（モデルや原文の言葉が ID に入らないように）。読み直しの決まりは §4.1 |
| エンジンが作る未定の値 | 系譜から（`u-atHome:元の事項ID`） | 今のまま |
| 要件・手配・案・作業 | 種類＋系譜（置き換えをたどった元の事項）＋雛形・手順の ID（＋子の ID・回の ID）＋世代 | 時刻・担当・店・通販の別をキーに入れない。キーの形は、保存した事象が指す契約である。形を変える時は、古い事象のキーを写す読み替えの関数を一緒に作る |
| 習い事の回 | 所属 ID＋決まりで予定されていた日 | 人が操作した回は、実際の日や決まりが変わっても同じ ID を保つ。決まりの変更で予定が動いた回に操作があれば「要確認」 |
| 家族の情報の中の物 | 家族が作る時に、サーバーが付ける（中身を含まない） | 使い回さない。消した物を指していた作業は「前提が消えた」として扱う |
| 依頼 | 送った時に画面が作る UUID | 送った時の相手・種類・根拠・文の控えを持ち、後の作業から逆算しない |

### 4.1 読み直しで、事項の同じを保つ

- 読み直すのは、書き起こしを直した時と、使い始める前のプロンプトの更新の時だけ。家族の訂正（読み違い、うちの子に関係ない、推定の確認）は、読み直さずに事項への事象で記録する（§5.2）。
- 読み直しでは、前の事項と未定の値を ID 付きでモデルに渡し、対応の候補を返させる。モデルの対応は候補であり、決めるのはコードと家族である。
- コードが自動で同じと認めるのは、同じ出典の中で一対一に決まり、元の文の部分と事項の意味（種類・解釈・条件の式）がすべて同じ時だけ。
  - 条件の式は、節点の ID ではなく形で比べる（ID はモデルの付けた物で、読み直しで別の式に使い回されることがある）。
  - 字が直った、一つが二つに分かれた、二つが一つになった、候補が複数ある時は、家族に「同じ物ですか」と聞く。
- 対応の決まらない前の事項は、消さない。
  - 「今回の読み取りで見つからなかった・要確認」として残し、間に合わなくならない側で計画に残す。
  - 家族が「もう関係ない」と確かめた時だけ外す。読み直しの読み落としで、明日の持ち物が黙って消えないようにする。
- 要確認の間：
  - 送った依頼と引き受けの事実は残す。
  - 取り消されたとも、続けてよいとも決めない。
  - その事項について、新しい決定を勧めない。

### 4.2 世代（取り消した物が、また要るようになった時）

- 世代は、手配全体ではなく、作業と依頼ごとに持つ。
- 世代が上がるのは、その作業か依頼について、取り消しがはっきり起きた後に、また要るようになった時だけ。
  - はっきりした取り消しの例：その依頼に取り消しの連絡を送った。本人に「要らなくなった」と知らせた。
  - 世代が上がると、前の引き受けは引き継がず、本人にもう一度聞く。
- 一つの依頼の取り消しで、同じ手配の他の作業は変わらない。例：学童の予備を取り消しても、祖母の本命とその引き受けはそのまま。
- 条件が行き来しただけで、取り消しを誰にも伝えておらず、提案の中身も変わらない時は、世代を上げず、引き受けを保つ。
- キーには、世代が2以上の時だけ後ろに付ける。今のキーは変わらない。

## 5. 生命周期

どれも「状態・入る物（事象か時間）・記録か導出か・次に響く物」で書く。時間で入る状態は、すべて導出である。

### 5.1 出典

| 状態 | 入る物 | 記録か | 次に響く物 |
|---|---|---|---|
| 届いた | noticeReceived（文字なら文、写真なら写真の参照） | 記録 | 読み取りの仕事 |
| 書き起こした（写真） | modelOutputRecorded（transcribe） | 記録 | 文ができる。読み取りへ |
| 書き起こしを直した | transcriptionCorrected【新】 | 記録 | 読み直し（§4.1） |
| 読んだ | modelOutputRecorded（extract）、コードの検査を通った物 | 記録 | 事項・未定の値。計画を作り直す |
| 読めなかった | 拒否・打ち切り・型の誤り・API の誤り | 運用の表 | 画面に「読めませんでした」と、もう一度・手で書く。空の正常な計画にしない |
| 訂正された | 後の出典の correctsSourceId、後の事項の作用 | 導出 | 事項の今の形が変わる |
| 取り下げた | sourceWithdrawn【新】：家族が「このお知らせはもう当てはまらない」と言った | 記録 | 事項が全部生きていない → 頼んだ後なら取り消しの連絡（§1 の4） |
| 写真を消した | 削除の仕事 → sourceContentPurged【新】（写真だけ） | 記録 | 計画は変わらない。元の文の画面に「写真は消しました」 |
| お知らせごと消した | 削除の仕事 → sourceContentPurged（全部） | 記録 | 事項は使えなくなる。取り消しは推し量らず、それに頼っていた依頼と引き受けは「根拠を消したので要確認」 |

- 読み取りの記録の出典、読み取りの出典、各事項の出典は一つに揃う。揃わない読み取りと、届いていない出典の読み取りは使わない（非同期の読み取りの取り違えで、別の出典を汚さない）。
- お知らせごと消した出典は、たたんだ状態からも原文を外し、見せる物に出さない。同じ ID のお知らせは、もう受け付けない。事象の列に残る中身を消すのは、置き場所の仕事（§6.4）。

取り下げと削除を分ける。取り下げは「当てはまらない」という家族の言明で、取り消しの流れを起こす。削除はプライバシーの求めで、学校の行事が中止になったとは推し量らない。

### 5.2 事項と作用

| 状態 | 入る物 | 記録か | 次に響く物 |
|---|---|---|---|
| 記載・推定・食い違い | 読み取り | 記録 | 推定・食い違いは家族への確認にし、必須の要件も作用も起こさない |
| 確かめた | itemConfirmed【新】 | 記録 | 「家族が確認」。要件と作用が効く |
| 直した | itemCorrected【新】：解釈の一部を家族が直す | 記録 | 解釈を置き換え、「家族が確認」。ID は変わらない |
| 関係ない | itemDismissed【新】：うちの子に関係ない等 | 記録 | 要件を作らない。itemConfirmed で戻せる |
| 要確認（読み直しで見つからない） | 読み直し | 導出 | §4.1 |
| 置き換えられた・取り消された | 後の事項の作用 | 導出 | 置き換えは系譜で同じキーを保つ。取り消しは外す |
| 条件が偽 | 未定の値の答え | 導出 | 生きていない |
| 過ぎた | 日付が過ぎた | 導出 | 画面から下げる |

**作用は三つの値で効く**：

- 作用（未定の値を決める・置き換える・取り消す）は、その事項が確かで（記載か家族の確認）、条件が真で、置き換え・取り消しを受けていない時だけ効く。
  - 後で置き換え・取り消しを受けた事項の作用は外れ、その作用で決まっていた値も決まっていない側に戻る。受けるか分からなければ、作用も分からないとする。
- 同じお知らせの中で、効く作用が同じ未定の値に違う値を言う時は、先後の証拠が無いので、どちらとも決めない（未定のまま。後の確かな連絡か家族の答えで決まる）。モデルの出力の並びの順で決めない。
- 一つの事項を、効く（効くかもしれない）置き換えが二つ以上言う時も同じで、どれが続きかを決めない。系譜は継がせず、前の事項も、言い合う後の事項も「条件しだい」として残し（どれも確かな必需品としない）、頼んだ依頼は要確認にする。
- 条件が偽なら効かない。分からない時は、作用も分からないとし、前の事項を消さない。
  - 前と後の両方を「条件しだい」として、間に合わなくならない側で計画に残すか、問いにする。
  - 確定した事実や、自動で進めてよい物としては見せない（§1 の2）。
- 条件と作用が互いを頼って回る時は、未判定にする。たたみ直しを限りなく繰り返さない。
- 作用の真偽は、出典が届いた時に一度だけ決めない。たたむ度に、その時の答えで決め直す（後で家族が答えれば、前の作用も効き方が変わる）。
- 確かめた（直す前）：作用を、事項の証拠の状態と条件の真偽を見ずに当てていた。
  - 架空の材料で、条件が偽の延期の連絡が日付を12/8に決め、前の事項を置き換えた。
  - 食い違いの事項でも同じだった。
- 直した（§13 の1）：上の決まりで効くようにし、戻りの試験を足した。

### 5.3 未定の値と問い

- 未定の値：
  - 宣言は、読み取りかエンジンが行う。
  - 答えは、家族の answered か、後の出典の作用（効く物だけ）。順の後の物が勝つ。
  - 答え直しは、新しい answered。
  - 出典が取り下げ・削除されたら、その出典の未定の値と作用は使わない。その値への家族の答えも使わない（他の出典の事項がその値を条件にしていれば、条件しだいに残る）。
    - その事項を確かめても（itemConfirmed）、条件は解けない（読み取りが正しい事と、条件が満たされた事は別）。今は、家族が「関係ない」とするしかない。「この回は要る」と言う手段は、実在の家族のデータの門（§13.1）の前に要否を決める。
- 問い（全部導出）：
  - 答えで計画が変わり、聞く期限の前の時だけ出る。
  - 知らせた → 答えた → 期限が過ぎた。期限が過ぎたら、間に合わなくならない側で進め、画面にそう出す。

### 5.4 要件・手配・案

- 要件と手配は、全部導出。生きている事項（決まりから導いた回を含む）から出て、事項が生きていなければ消える。
- 案の状態：
  - 開いている・決め時が過ぎた：導出。
  - 本命・予備に選んだ：optionChosen で記録。
  - 取り下げた：optionDropped で記録。
  - 断られた：依頼の返事から導出。
  - 決め時を過ぎても始めていない：導出。
- 手配の状態（決めてよい・返事しだい・聞いてから・無理・まだ判断できない）は、導出（01-model §8）。

### 5.5 作業と引き受け

- 作業があるか：導出。要件が生きていて、案が選ばれているか勧められている時。
- 引き受けの状態：

| 状態 | 入る物 | 記録か |
|---|---|---|
| 提案 | 分担の決まりかエンジンの配置。もう一人の assignmentProposed | 導出、または記録 |
| 引き受け | commitmentChanged accept（本人だけ）。提案の控え（時刻・遅れる帰宅・担当・用件・場所・外の相手）を持つ。サーバーが今の提案と同じかを確かめ、違えば断って見せ直す。置けていない作業（時刻の無い提案）は控えが作れないので、置けてから引き受ける | 記録 |
| 確かめ直しが要る | 解き直して、提案の中身が控えと違う。世代が上がった（§4.2） | 導出 |
| 担当を替えた | assignmentProposed。前の担当の引き受けの控えは捨てる（前の人の同意を、次の人に引き継がない） | 記録 |
| 済み・断った・できなくなった | commitmentChanged（本人だけ） | 記録 |
| 取り消し | 根拠が消え、済んでいない | 導出 |
| 担当がいない | 担当の成員を止めた | 導出 |

- 提案の控えに残す地図由来の欄（place ID 以外）は、Google の条款を確かめてから決める。家族が選んだからといって、事業者のデータを自由に保存してよいとはみなさない。
  - こちらが計算した時刻でも、Google の道のりや所要の時間に頼って出した物は、こちらの計算だというだけで保存してよいとは言えない。
  - 控えは、本人が実際に見た物と同じでなければならない。見せた時刻と別の時刻を控えに書くと、本人が確かめた中身を偽ることになる。
  - そこで、条款を確かめるまでは、引き受けられる正式な提案の時刻は、保存してよい物（家族の情報の目安）だけから作り、それを見せて控えに残す。地図から出した値は、出どころを付けた参考として見せるだけにし、引き受けの中身にしない。参考の値でしか組めない提案は、引き受けを止める。
  - 今のデモは家族の情報の目安だけを使うので、これに当たらない。

### 5.6 外への依頼

- 送った（externalRequestSent）：相手・種類・根拠（手配・案・作業のキーと事項の ID）・文の控えを持つ。
  - 控え（snapshot）には、送った時の計画で見えていた物を写す：条件しだいだったか（conditional）、根拠の条件の形（condition。節点の ID を除いた式）、頼んだ時間（window。子の居場所の手配の区間）。控えは requestSnapshot で作る。
- 送った後に、頼んだ時の前提と今が違えば、要るかを頼んだ本人に確かめる（needsCheck）。取り消したとも、続けてよいとも決めない。
  - 根拠の事項のどれかが、読み直しで見つからない・確かでない・取り消された（他の根拠で手配が残っていても）。
  - 根拠が、効くか分からない置き換え・取り消しの先にある。
  - 送った時は確かだったのに、今は条件しだい。
  - 条件の形が違う（読み直しで式が替わった）。後でその新しい条件に答えが出ても、相手が新しい前提で引き受けたことにはならないので、確かめは残る。
  - 頼んだ時間が違う（置き換えで日が変わった、家族の予定が変わった）。
  - 条件に答えが出ただけなら疑いではない：真なら続け、偽なら取り消しの連絡を作る。条件しだいの未定の値に、それを決める新しい作用が届いただけでも疑いにしない（頼んだ文の前提は替わらず、決まれば同じ道で取り消しまで進む）。
  - 控えに条件や時間の無い古い事象では、それらからは決めない（検証器は、事象から当時を作り直せなければ未判定とする）。
- 返事待ち → 確定・断られた（externalReplyRecorded。後の返事に従う）→ 取り消した（cancellationSent）。
- 取り消しの連絡が要るか：送った時の控えと、根拠が今も生きているかから導く。今の作業の一覧からは逆算しない。
  - 確かめた（直す前）：読み直しで事項が消えると、送った依頼が計画の出力から消え、取り消しの作業もできなかった（依頼を今の作業から引いていたため）。
  - 直した：控え（snapshot）のある事象は、作業が消えても控えから依頼を作り、根拠が分からなければ要確認にする。
  - 残る穴：控えの無い古い形の事象で、今の作業も消えた時は、依頼が計画の出力から消える（相手も根拠も分からないため）。検証器は active_request_missing として見つけるが、デモの API はまだ検証器を通していない。実在の家族のデータを入れる前（門②）に、送ったの記録は控えを必須にし、控えの無い事象は受け付けない。
- 根拠が要確認や削除で分からない時は、取り消しの連絡を作らず、「要るか確かめてください」と出す。
- 記録の誤り：requestRecordCorrected【新】。
  - 「送った」を押し間違え、実際には何も送っていない時だけ使う。押した本人が使い、返事がまだ無い事が条件。
  - 引き受けは、直した「送った」を除いて、その作業の変遷（担当の提案・本人の操作・送った）をたどり直す。送る前に引き受けていなければ提案に戻り（引き受けていない人の作業を「引き受けた」にしない）、後の担当替え・本人の「済んだ」・同じ作業の別の依頼は残る。検証器も同じ意味で、事象から独立にたどり直す。
  - 依頼の ID は、直して消した物も含めて、二度使わない。同じ作業の依頼は一通だけ（命令が二通目を断る）。
  - 引き受けていない担当も「送った」を記録できる（実際に送った事実を、引き受けの有無で捨てない）。
  - 元の事象は消さない。取り消しを送ったことにもならない。
  - 実際に送った後なら、取り消しの連絡を送るしかない。
  - 返事があるか、送ったか分からない時は使えない。

### 5.7 知らせ

| 状態 | 入る物 | 記録か |
|---|---|---|
| 出すべき | 今の計画から、知らせの決まり（core の純粋な関数） | 導出 |
| 送る待ち | 知らせの意図の表に、冪等のキーで入れる | 運用の表 |
| 送っている | 期限付きで引き受けた送り出し | 運用の表 |
| 受け付けられた | Push の事業者が受け付けた | 記録（notified：経路・結果・種類・中身の控え・アプリの版） |
| 失敗・結果不明 | 誤りが返った。引き受けの期限が切れた | 運用の表。限られた回数だけ試し直す |
| 要らなくなった | 送る直前に作り直したら、もう出すべきでない | 運用の表（送らずに閉じる） |

- notified は、事業者が受け付けたという意味だけで、本人に届いた・読んだ証拠にしない。
- 受け付けの後、記録の前に止まると、二度届くことがある。意図は一つに保つが、端末に一度だけ出るとは約束しない。

### 5.8 資源

| 状態 | 入る物 | 記録か |
|---|---|---|
| 候補 | 地図の検索や推定から出した物 | 計算の時の入力（§2.3）。出どころ・調べた時刻・確かでない事を付けて、案として見せてよい。店ごとに先に登録してもらうことは求めない。家族が選んだのは「この店で」という決定であり、営業時間・道のり・在庫を本人が確かめたことにはしない。これらは出どころ・調べた時刻・確かでない事を持ち続ける。在庫は約束しない |
| 使う | 家族が足した・確かめた（家族の情報の変更） | 記録 |
| 古い | 調べた時刻から決めた日数が過ぎた。家族が「違った」と言った | 導出（計画では「要確認」） |
| 調べ直した | 家族の情報の変更（調べた時刻を新しく） | 記録 |
| やめた | 家族の情報から外す | 記録 |
| 引っ越し | 家の場所を変えた | 記録。前の版は消さずに残し、新しい版から先の計画を変える。家を起点にした道のりの目安は「要確認」（導出）。家のまわりの資源を選び直す画面へ |

### 5.9 成員と家庭

- 成員：
  - 招いた → 使う（身元を結んだ）→ 止めた。
  - 止める時は、成員の表（権限の正本）と家族の情報（名前・言葉などの中身）を、一つのトランザクションで変える。
  - 止めた後の要求は、トークンが期限内でも毎回断る。止めた大人の作業は「担当がいない」になる。
- 子：
  - 所属を足す・外す（入学・進級・学童をやめる）は、効く日付きの変更。
  - 進級しても子の ID は変えない。4月の切り替えの仕組みは、今週は作らない。
- 家庭：
  - 作る（最初の設定）→ 使う → 引っ越し → 止める・消す。
  - 止めたら、すぐに読み書きと送り出しを止める。消す時は全部消す（§6.4）。

## 6. 保存（Postgres）

### 6.1 表

家庭をまたぐ参照を作らないため、家庭に属する表には household_id を持たせ、参照は (household_id, id) の組で結ぶ（ログインの身元 identities だけは家庭に属さない）。

| 表 | 主な列 | 決まり |
|---|---|---|
| households | id、種類（real・test）、状態、地域、時区、次の通し番号 | 書き込みを一列に並べる所（§7.3）。demo の家庭は本番の置き場所に置かず、メモリだけに置く。test は合成のデータの家庭（控えから戻す確かめ等） |
| identities | id、発行元、発行元の中の ID、作った・外した時刻 | ログインの身元。一意（発行元, 中の ID）。家庭を持たない。メールが同じというだけで、別の発行元の身元と結ばない |
| members | household_id、id、種類、active、identity_id（大人だけ） | 権限の正本。名前などの中身は持たない。一意（household_id, identity_id）。同じ人が、後で二つの家庭に入れる形にしておく（今週はその流れを作らない） |
| events | household_id、seq、id、type、version、occurred_at、recorded_at、actor_id、op_id、body（jsonb。§6.2 の許した欄と中身の ID だけ） | 主キー（household_id, seq）、一意（household_id, id） |
| operations | household_id、op_id、actor_id、中身の要約、結果（事象の通し番号の範囲。何も起きなかった操作も一行） | 一意（household_id, op_id）。要約は敏感な付随情報として扱う |
| payloads | household_id、id、種類、sha256、本体（jsonb）、消した時刻と理由 | 敏感な中身はここだけ。sha256 は、ここに置き、事象には置かない |
| blobs | household_id、id、R2 の無作為なキー、mime、大きさ、sha256、状態（仮・確定・消した） | 写真の本体は R2。DB と R2 は一つのトランザクションにできないので、仮で置き、DB の記録で確定し、仮のまま残った物は後で消す |
| model_calls | household_id、id、呼び出しの種類、モデル、プロンプトの版、入力の参照、始め・終わり、終わり方（ok・拒否・打ち切り・型の誤り・誤り・不明）、入出力の tokens、推定の費用、アプリの版 | 呼ぶ前に一行入れ、後で埋める。使用量が分からなければ費用も不明とし、0 にしない |
| jobs | household_id、id、種類（読み取り・削除）、状態、試した回数、次に試す時刻、引き受けの期限、誤りの種類 | 落ちても続きから。引き受けは期限付き |
| notification_intents | household_id、id、member_id、知らせのキー、種類、送る時刻、状態、試した回数、引き受けの期限 | 一意（household_id, member_id, キー） |
| push_subscriptions | household_id、id、member_id、endpoint、鍵、作った・外した時刻、最後の成功と誤り | 鍵は秘密に準じて扱う。410 が返れば外す |
| deletions | household_id、id、範囲、対象の ID、求めた人・時刻、状態、終えた時刻 | 中身を持たない。同じ記録を DB の控えの外にも書き、控えから戻した時に削除をやり直すために使う（§6.4） |

- 導いた計画の控えの表は作らない。数十〜数百の事象なら、読む度にたたみ直す。計画には、計算に使った最後の通し番号、アプリの版、計算した時刻を付けて返す。測って遅いと分かった時だけ、家庭・通し番号・家族の情報の版・アプリの版・時刻を含むキーで控えを足す。
- RLS（行の決まり）は、今週は使わない。全ての表に household_id を持たせ、使える形にしておく。使う時は、サーバーのつなぐ役に、決まりを迂回できる権限を与えない。

### 6.2 敏感な中身を、事象と分ける

01-model §2 の「分けた保管場所」を、保存の層で行う。

- 書く時に、保存の層が事象から敏感な欄を取り出して payloads に置き、事象には中身の ID だけを残す（乾かす）。読む時に戻す（戻す）。
- core のエンジンと試験は、今と同じ「中身の入った事象」を扱う。保存の分け方を、エンジンは知らない。
- 事象に残してよい欄を、事象の種類ごとに決める（許す一覧）。一覧に無い欄は、すべて payloads に置く。

| 事象 | 事象に残す欄 | payloads に置く物 |
|---|---|---|
| householdSet | なし | 家族の情報の全体 |
| noticeReceived | 出典の ID・版・届いた時刻・送り手の種類・送り手の場所の ID・言葉・届いた形・訂正元 | 題・文・写真の参照 |
| modelOutputRecorded | 呼び出しの種類・モデル・プロンプトの版・出典の ID と版 | 出力・入力のハッシュ |
| transcriptionCorrected | 出典の ID | 直した行 |
| answered | 未定の値の ID | 値 |
| itemConfirmed・itemDismissed | 事項の ID・理由の種類 | — |
| itemCorrected | 事項の ID | 直した解釈 |
| optionChosen・optionDropped・assignmentProposed | キーと成員の ID・役割 | — |
| commitmentChanged | 作業のキー・成員の ID・操作 | 提案の控え |
| externalRequestSent | 作業のキー・依頼の ID・相手の ID・種類・根拠のキーと事項の ID | 文の控え |
| externalReplyRecorded・cancellationSent・requestRecordCorrected | 依頼の ID・返事 | — |
| notified | 知らせのキー・成員の ID・経路・結果・種類 | 中身の控え |
| sourceWithdrawn・sourceContentPurged | 出典の ID・範囲 | — |
| clockAdvanced | 時刻（デモだけ） | — |

- 事象に残す ID は、どれもサーバーが作る中身を含まない ID と、決まった種類の符号だけにする（§4）。許す一覧だけでは、ID に名前が紛れ込むのを防げないため。
- それでも、ID・時刻・相手の ID は結び付けられる付随情報である。出典ごとに消した後も、事象の骨（種類・ID・時刻）は残り、中身は無い。家庭ごとに消す時は、骨も消す。
- 捨てた案：
  - 事象の中に置いたまま、消す時に書き換える。分ける欄を数える手間は同じで、追記だけの決まりを日常的に破る。
  - 鍵を捨てて読めなくする（暗号の消去）。今週の規模に重く、確かめていない方法で完全な削除を約束できない。

### 6.3 消された中身をたたむ

- 戻す時に中身が消えていたら、事象は「消した」印付きで core に渡る。
- 写真だけ消した：書き起こしと事項は残るので、計画は変わらない。
- お知らせごと消した：その出典の事項・未定の値・作用は使えない。それに頼っていた依頼と引き受けは「根拠を消したので要確認」（§5.1）。
- 家族の情報の古い版を消した：今の版があれば計画は作れる。古い時点の説明は「再現できない」と示す。

### 6.4 消す

| 求め | すること |
|---|---|
| 写真だけ | R2 と blobs を消し、sourceContentPurged（写真）を記録 |
| お知らせごと | その出典の payloads（文・書き起こし・読み取りの出力・依頼の文の控え）と写真を消し、sourceContentPurged（全部）を記録 |
| 家庭ごと | 止めて、全部の表から消す。事象そのものも消す |
| 写真の保持の期限 | 決めた日数で写真だけを消す（日数は作り手が決める。§15） |

- 消すことは、削除の仕事にして、状態を持たせ、段ごとに試し直せるようにする。終えるまで「消しました」と言わない。
- 出典を消す求めが来たら、その時点で「消している」の印を付け、その出典の読み取り・モデルへの送り出し・知らせ・新しい取り出しを止める。
  - 途中の読み取りの結果は、書く前に、消していないことと出典の版が変わっていないことを確かめ直す。消した後に、遅れて届いた結果で中身が戻らないようにする。
  - 外の事業者に既に送った物は、こちらで取り消せない。
- 中身から作った物（文の題、要約、ハッシュ、ログ、仕事の記録）も、個人の情報を含み得る物として一緒に消す。
- 控え（Railway の Backups）には、控えが入れ替わるまで残る。控えの中の削除の記録は、控えを取った時より後の削除を含まない。そこで：
  - 削除の記録を、DB の控えの外（R2 の別の置き場）にも書く。中身は ID だけで、権限を絞り、控えの保持期間より長く残してから消す。
  - 順番：削除の求めを受け付けたと答える前に、外の記録を書き、読めることを確かめる。書けなければ「消している」のままにし、終えたとは言わない。DB だけ処理して外の記録が無いまま止まると、古い控えから戻した時に、その削除が分からなくなるため。
  - 控えから戻す時は、隔離した所で、この外の記録に従って消し直してから、外に出す。外の記録がそろっていると確かめられない時は、戻すのをやめる。
  - これを隔離した合成のデータで確かめるまで、「全ての写しを消した」と言わない。
- 控えから戻すと、控えを取った時より後の事（家族の操作、送った依頼、知らせ、操作の記録）は失われる。
  - 戻した時は、戻した時点を家族に示し、自動の送り出しを止める。
  - その時点より後の依頼・引き受けを、家族に確かめてもらってから再開する。
  - 戻した控えより後の操作について、送り直しの冪等は保てない。そう言う。
- 外の事業者（Claude の API、地図）に送った物の保持は、それぞれの条件に従う。使う人には、実際に送る先と保持を説明する。

## 7. 書き込みの道

### 7.1 計算する場所

**サーバーを正本にする。画面ではエンジンを動かさない。**

- 画面は、サーバーが作った見せる物（その大人の「きょう」、よてい、手配の詳細、元の文）を受け取って出す。
- 理由：
  - 知らせと書き込みの検査には、どのみちサーバーで計算が要る。
  - 画面とサーバーで版がずれると、見えた物と記録した物が食い違う。
- 「もしも」：サーバーの試算の口で答える。仮の事象を足して計算し、保存しない。
- デモも同じ道を通す。サーバーの中に、メモリに保存するデモの家庭を作り、時計はデモの時計にする。
- 電波が無い時は、確定したか分からない操作を成功と見せない。同じ操作 ID で、状態を問い合わせるか送り直す。
- 捨てた案：画面でも同じ core で計算して先に見せる。速く見えるが、二か所の版の管理と、ずれた時の扱いが要る。電波の無い所で使う要望が出たら、「下書き」と示した手元の試算として考える。

### 7.2 命令

画面は事象を直接書かない。命令を送り、サーバーが権限と前提を確かめて、事象に展開する。

| 命令 | 書ける人 | 出る事象 |
|---|---|---|
| 家族の情報を変える | 有効な大人。見た版の後に家族の情報が変わっていたら断る | householdSet（成員を止める時は members の表も） |
| お知らせを入れる（文字・写真・家族の一言） | 有効な大人 | noticeReceived（と読み取りの仕事） |
| 書き起こしを直す | 有効な大人 | transcriptionCorrected（と読み直しの仕事） |
| 事項を確かめる・直す・関係ないとする | 有効な大人。今の読み取りにあり、取り下げていない出典の事項だけ | itemConfirmed・itemCorrected・itemDismissed |
| 読み直しの対応に答える | 有効な大人 | 同じ物か、どれとも違うかの事象（§4.1） |
| お知らせを取り下げる | 有効な大人。届いていて消していない出典（取り下げ済みなら何も足さない） | sourceWithdrawn |
| 写真だけ・お知らせごと消す | 有効な大人 | 削除の仕事（終えた時に sourceContentPurged） |
| 答える | 有効な大人。今の読み取りにある未定の値（宣言した値の中から）か、計画の問いの値だけ。取り下げた・消した出典の未定の値は断る | answered |
| 案を選ぶ（本命・予備、担当） | 有効な大人。決め時を過ぎて始めていない案は断る。一つの案は本命か予備のどちらか（予備を本命にすると予備から外れる。本命を予備には選べない） | optionChosen、assignmentProposed。自分が担当なら、画面が作業ごとに付けた提案の控えが今の提案と同じ作業だけ accept（控えの無い作業は提案のまま。違えば断る） |
| 案をやめる | 有効な大人。今選んでいる案（本命か予備）だけ | optionDropped |
| 担当を提案する | 有効な大人 | assignmentProposed |
| 引き受ける・断る・済んだ・できなくなった | 担当の本人だけ | commitmentChanged（引き受けは提案の控えを持つ） |
| 依頼を送ったと記録する | 担当の本人だけ | externalRequestSent |
| 「送った」の押し間違いを直す | 押した本人だけ（§5.6 の条件） | requestRecordCorrected |
| 返事を記録する | 有効な大人 | externalReplyRecorded |
| 取り消しの連絡を送ったと記録する | 有効な大人 | cancellationSent |
| 時計を進める | デモの家庭だけ。進めるだけで戻せない。進めた後の命令は、家庭を押さえた中で、その時刻で記録する | clockAdvanced |

- modelOutputRecorded、notified、sourceContentPurged は、仕組みだけが書く。
- 新しく決める命令（案を選ぶ・担当を提案する・引き受ける）は、今も要る（生きている）手配・作業にだけ受け付ける。古い画面からの操作で、要らなくなった計画の意図を書かないため。起きた事の記録（済んだ・送った・返事・取り消しを送った）は、要らなくなった後でも受け付ける。
- 今のたたみ方は、本人でない引き受けの操作と、有効な大人でない人の家族の言明（事項の確かめ・直し・関係ない、取り下げ、書き起こしの直し、「送った」の直し）を、記録した上で無視している。書き込みの時点で断る方を正にし、たたみ方の無視は守りの二重として残す。
- 押し間違いの取り消しには、全ての事象に効く「取り消し」を作らない。
  - 過去の事象を飛ばすと、その後の済み・返事・知らせの事実と食い違うからである。
  - 意味のある後の操作で直す：答え直す、案をやめる・選び替える、できなくなった、記録の誤り（§5.6）。
  - 最初は、何でも戻すボタンを置かない。

### 7.3 一つの命令の処理

一つのトランザクションで行う。

1. 身元を確かめる（トランザクションの前）。
   - Cloudflare Access の署名付きトークン（署名・発行元・対象・期限）を確かめる。
   - 全ての入口で確かめ、トークンが無いか正しくない要求は、Railway に直接来た物も含めて断る。
   - Cloudflare を通った要求だけに絞る仕組み（源の側の制限）が Railway で使えるかは、実機の尖峰で確かめる。確かめるまで「直接の要求は全部届かない」とは言わない。
   - Cookie で書き込む要求は、Origin を確かめる。
2. households の行を、書き込みのために押さえる。同じ家庭の書き込みは、一列に並ぶ。
3. 押さえた後に、その身元の成員が今も有効か、その家庭の権限があるかを、トランザクションの中で確かめ直す（押さえる前に止められた時のため）。
   - 確かめるのは、成員が有効な大人であること、確かめた身元が今もその成員に結ばれていること、身元を外していないこと。読むだけの要求（見せる物）も、押さえた中で同じく確かめ、通らなければ家庭の物を何も返さない。
   - これが撤権と互いに排他になるのは、撤権（成員を止める・身元を外す・結びを外す）の書き込みも、先に同じ家庭の行を押さえる時だけである。撤権の操作を作る時は、同じ順で押さえる（関わる家庭を全て押さえてから表を変える）。本物の Postgres での並びの試験と合わせて、門②の条件にする。
4. operations で操作 ID を引く。
   - あって、元の操作をした人が同じで、要約も同じなら、何も足さずに今の見せる物を返す。
   - 人か要約が違えば、衝突として断る。
5. 事象を読み、たたみ、今の計画を作る。
6. 権限（§7.2）と前提を確かめる。
   - 例：引き受けは、その作業が今あり、本人に提案されていて、提案の控えが今の提案と同じ時だけ。
   - 押した人が見た版の後に、対象が消えたか、提案・決め時が変わっていたら、409 と新しい見せる物を返し、本人に見直してもらう。
7. 事象に通し番号を付けて足し、operations に一行足す。何も起きなかった操作も一行足す。
   - 理由：「A を選ぶ」が既に A で何も起きず、後で別の人が B にした後、同じ操作の送り直しで A に戻すのを防ぐ。
8. 終える。新しい計画から見せる物を返す。知らせの判定をすぐ一度する（§9）。

- モデル・地図・Push への通信の間は、DB の押さえを持たない。地図の結果が古ければ、押さえの外で引き直し、押さえた後に版と調べた時刻を確かめてから使う。

## 8. 読み取りの道

1. 受け取る。
   - 文字か写真。出典の ID を作り、写真は R2 へ仮に置く。
   - noticeReceived を記録し、読み取りの仕事を待ちに入れる。
   - 写真の大きさ、文の数、条件の節点の数（今は64）に上限を置く。
   - 「あした」「きょう」の基準の日は、お知らせが書かれた日（連絡帳の日付）であり、写真を撮った・入れた時刻ではない。前の日の連絡帳を後で撮った時や、夜中を越えて入れた時に、入れた日を基準にしない。書かれた日が分からなければ、家族に確かめる。モデルが返した日付と、コードが「あした」から決めた日付が違えば、食い違いにする。
     - 今のコードは、受け取った時（receivedAt）の家庭の時区の暦日を基準にしている。これで合うのは、受け取った日が元の文の書かれた日と同じ時だけである。前の日の連絡帳を後で撮った写真、LINE の古い連絡を次の日に転送した物、連絡帳の文を後で打ち込んだ物では合わない。取り込みを作る時に、書かれた日を出典の欄に持たせ、分からなければ家族に確かめる（写真も文も同じ決まり。それまでは設計）。食い違いの検査は実装済み。
   - 写真は、置く前にサーバーで付随情報（EXIF の撮った場所・時刻など）を外す。置く物と Claude に送る物は、外した後の同じ画像にする。外れたことを試験で確かめ、使う人への説明も実際の処理に合わせる。確かめるまで「外した」と言わない。
2. 写真なら書き起こす：modelOutputRecorded（transcribe）。
   - 行ごとの読みにくさを持たせ、画面で写真と並べて、読みにくい行を目立たせる。
   - 全行の確認は求めない。
   - モデルが言う確かさは危うさの目印にすぎず、確かさが高くても正しいとは限らない。
3. 読む。
   - 関係する出典の今の事項を ID 付きで渡す。
   - 出力をコードで検査する：型、文 ID、日付と曜日、条件、作用の ID、出典の版。
   - 通れば modelOutputRecorded（extract）。読んでいる間に出典の版が上がっていたら、その出力は当てない。
4. 失敗する。
   - 拒否・打ち切り・型の誤りは、有効なデータとして扱わない。
   - 試し直しは回数と待ちに上限を置き、試しごとに model_calls を分ける。
   - TypeScript の SDK は既定で自分で2回試し直すので、`maxRetries: 0` にして、試し直しはこちらで行い、一回ずつ記録する（SDK の中の試し直しで、記録に出ない呼び出しを作らない）。
   - だめなら仕事を失敗にし、画面に「読めませんでした」と、もう一度・手で書くを出す。
   - デモの録った応答で、本番の失敗を埋めない。
5. 代償の大きい作業の前に見せる。
   - 買い物・休み・人に頼むの前には、要の日付・対象と、元の文（写真のその所）を家族に見せる。
   - 確かさの高さにかかわらず、決める画面で見せる。
   - 自動で進めてよい境界は、実際の写真で測ってから決める。
6. 費用：呼び出しごとに model_calls（§6.1）。

## 9. 時間と定時の仕事、知らせ

- 時計：
  - 本番はサーバーの時計。試験とデモだけ時計を差し込む。
  - 日付だけの物はその地の日付、時刻のある物は時区付きで持つ。
- 繰り返し：
  - サーバーのプロセスの中で、5分ごとと起動の時に回す。外の cron や別のキューは足さない。
  - 仕事と知らせの意図は DB にあるので、落ちても続きから再開する。
- 知らせの判定：
  - 書き込みの後にすぐ一度と、繰り返しの度に行う。
  - 本番の家庭ごとに今の計画を作り、知らせの決まり（core の純粋な関数）で、出すべき知らせを出す。
- 送り出し：
  - 意図を冪等のキーで入れ、期限付きで引き受けてから送る。
  - 送る直前に、もう一度作り直し、取り消し・担当・期限を確かめる。
  - 事業者が受け付けたら notified を記録する。
  - 失敗や結果不明は運用の表に置き、限られた回数だけ試し直す。
  - 送り出しは、一つのプロセスから始める。増やす時は、仕事の引き受けにだけ `SKIP LOCKED` を使う。
- 止まっていた間の分：
  - 起動の時に、まだ役に立つ物（決め時・問いの期限の前）だけ送る。
  - 役に立たなくなった物は送らず、画面に「過ぎた決め時」として出す。
- 時機：
  - 決め時の知らせには、5分の間隔より十分前の余裕を持たせる。
  - 新しく出た物で残りが5分も無い時は「すぐ扱う」とだけ言い、時刻ちょうどを約束しない。
- 文：
  - ロック画面の文には、子・学校・人の名前を入れない。
  - Service Worker は家族の API の応答を保存しない。
  - iPhone のホーム画面の PWA と Access と知らせの組み合わせは、実機で確かめる。成り立たない間は画面の中の表示を使い、送れたと装わない。
  - 一台の iPhone で二人の大人を切り替える時（デモと、作り手の確かめ方）：同じ Push の登録先で使う人が替わったら、前の人との結び付きを外す。知らせから開いた時は、今の身元で権限を確かめる。実機で確かめるまで、本人に届いたとは言わない。デモの画面の中の切り替えは、Access の身元の切り替えや、本人ごとの知らせの証明にならない。
  - 一人が複数の端末を使う時は、一つの意図について、登録先ごとに試しを記録する。今週は複数の端末の流れを作らない。

#### 9.1 知らせの決まりと送り出し（2026-11-02 に作った形）

- 出すべき物（core の `notificationIntents`。有効な大人ごとの「きょう」の上の札から）：
  - 取り消し・要確認：札が出たら。頼んだ時間の終わりまで（始まった後も残りがある）。夜に待つかは、頼んだ時間の始まりで決める。
  - 予備：札が出たら（札は次の案の決め時の26時間前から出る）。
  - 決める事：最初に選べなくなる案（選んだが使えなくなった案を除く）の決め時の26時間前から。札を見る大人の全員に。
  - 頼まれた事：もう一人の大人が頼んだ物は、すぐ。自分で自分に頼んだ物は出さない。仕組みの提案（提案の事象が無いか、system が書いた物）は、決め時の26時間前から。引き受けた後に中身が変わった物は、誰が頼んだ物でも出す。
  - 問い：聞く期限の26時間前から。
  - 期限を過ぎた物は出さない（止まっていた間の分も）。
- キーは「何についての知らせか」（計画の ID と決まった符号と成員の ID）だけで、時刻・品物などの中身を入れない。検証器が照らせるよう、意図は元の物（作業・依頼・手配と案・問い）を構造で持つ。
- 回（何回目か）：
  - 書き込みのまとまり（一度の家庭の押さえの中で足した事象。events の batch に最初の通し番号）ごとに、前に見た所から事象を再生し、無かったキーが出たら回を一つ進める。同じキーが出ている間は一回で、消えてまた出れば次の回（見回りの合間でも、同じ分の書き込みでも落とさない）。
  - 最後に今の時刻で作り直す（時刻だけで出る・消える物は、5分ごとの見回りで拾う）。初めて見る家庭は、再生せず今の形を一回目とする。
  - 見た位置（households の notified_through_seq）・意図の表の読み・再生・書き戻しは、家庭の行を押さえた一つのトランザクションで行う（命令とも、別のプロセスとも重ならない）。
  - notified には「キー#回」を残す。
- 夜（家庭の時区で22時〜7時）は、朝まで待てる物を7時まで待つ。7時に送ると、本人が動く時（無ければ期限）まで2時間の余裕が無い物は、夜でも送る。
- 同じ大人に同時にいくつも出れば、件数の文で一通にまとめ、意図ごとに notified を残す。
- 送る前の確かめ：
  - 家庭を押さえて作り直し、まだ出すべきか・身元が今も結ばれているかを見る。回を数えた後に家族の書き込みがあれば（その間に消えてまた出て、次の回になったかもしれない）、今は送らず、次のまわしで数え直してから送る。
  - 検証器：計画の違反があれば、その家庭の知らせを全部止める（どれに響くか絞れない）。知らせの検証の違反は、そのキーだけ止める（$all なら全部）。実際に送る文も、決まった文かを確かめる。未判定は止めない（文は事実を言い切らず、開いて確かめてもらうだけ）。回の数え方は検証器では未判定で、サーバーの試験で確かめる。記録には違反の種類だけを残す。
  - 事業者に持たせる時間（TTL）は、期限までの残り（最長24時間）。残りが無ければ送らない。
  - 引き受けるごとに札（乱数）を付け、送った後の状態は自分の札の行だけを替える（期限の切れた古い引き受けが、後から引き受けた物の結果を上書きしない）。送る前に、その回が notified に記録済みなら送らない（記録の後・状態の更新の前に止まった時に、送り直さない）。事業者が受け付けた後・記録の前に止まった時の二度送りは、防げない。
- 登録先：
  - 大人ごとに一つ。知っている Push の事業者（Apple・Google・Mozilla・Microsoft）の https の宛先だけを受ける（サーバーから任意の住所へ送らない）。
  - 同じ宛先で別の大人が登録すれば、前の人との結び付きを外す。登録ごとの版（乱数）を持ち、送る直前に同じ大人・身元・版かを確かめる。無くなった（404・410）宛先と、結びの外れた身元の登録は、読んだ時と同じ版の物だけを消す（その間に登録し直された物は消さない）。
  - 登録する・外すは、家庭の行を押さえた中で結びを確かめ直し、同じ取引の中で書く（命令と同じ。撤権と互いに排他になる条件も同じで、§7.3 の 3）。
  - 登録には、端末が頼んだ時（その端末の時計）を添える。同じ登録先で、後から頼まれた登録が先に済んでいれば、遅れて届いた前の登録は断る（一台の端末で使う人が替わった時）。同じ時なら、別の人の登録は先に済んだ方を残す。違う端末の時計とは比べない。
  - 残る隙：新しい人が知らせを止めて登録を消した後に、前の人の遅れた登録が届くと、比べる時刻が無いので受けてしまう。止めた時は端末の購読も外すので、その宛先には、ふつう事業者が「無い」と返し、最初に送る時に消える（実機では未確認。購読を外せなかった時は、前の人の知らせがその端末に出得る。文に名前は無く、開けば今の身元で確かめる）。実際の家族が一台の端末を分けて使うなら、消した後も時刻を残す形にする（門②で見直す）。
  - 送る事と記録は一つにできないので、確かめた後・送る前の替わりまでは防げない。ロック画面の文に名前を入れず、開いた時に今の身元で確かめる。
- 画面：家族の家庭だけ。iPhone はホーム画面に追加した時だけ受け取れる（追加を案内する）。許可は押した時だけ求める。Service Worker は知らせを出すだけで、API の応答を控えない。
  - 止める時は、サーバーが外したと答えた時だけ、端末の購読を外す。使う人が替わった・画面を閉じた後は、前の人の操作の続き（購読を作る・外す）をしない（端末の購読は、次の人の物かもしれない）。
  - 知らせを押して、前から開いていた画面に戻った時も、身元を確かめ直す（確かめる間、前の人の画面は出さない）。
- まだ確かめていない：iPhone の実機でのホーム画面の PWA・Access・知らせの組み合わせ（11/4）、大人ごとの静かな時間、複数の端末。

## 10. 版と「なぜそう言ったか」

| 物 | 決まり |
|---|---|
| 事象の形 | 事象の種類ごとに版を持つ。古い版を今の形に読み替える関数を core に置き、互換の試験を付ける。保存した事象は書き換えない（例外は §6.4 の削除）。知らない新しい版は、無理に読まずに止める |
| 計画のキーの形 | 事象が指す契約。変える時は、読み替えの関数で古い事象のキーも写す |
| プロンプト | 版を modelOutputRecorded に残す。新しい版は新しい出典にだけ使う。古い出典は、明示して読み直す時だけ（§4.1） |
| 家族の情報 | householdSet ごとの版。計画は、その時の最新の版で、先の事を計算する |
| エンジン | 計画は保存しないので、版が変われば計画も変わり得る（それでよい） |
| 説明 | 「あの時なぜ」は、人が見た物（提案の控え、依頼の控え、知らせの中身）で示す。notified と model_calls にアプリの版（Git のコミット）を残す |

- 保存した事象が一つも無い間（門②の前）は、事象の形を版を上げずに変えてよい。デモと試験の事象はコードから作り直す。実在の家族の事象を最初に保存した時に v1 を固め、以後の変更は版を上げて読み替える。
  - 2026-11-02：提案の控え（shown）を全部の欄に広げ、notified に経路・結果・種類・中身の控え・アプリの版を足した。この規則による変更で、前の形は読まない。
- 完全に再現できるのは、要る中身、その時のコードと依存、時間のデータ、許された外のデータがそろう時だけである。
- 消した原文、保存できない地図の結果、失われた古い版があれば「再現できない」と示す。今の地図や新しいモデルで埋めない。

## 11. 秘密と個人情報

- 鍵：手元は `.env`、本番は置き場所の秘密の設定。ブラウザ・Git・ふだんのログに出さない。
- 家庭の分離：
  - 全ての API・DB の検索・仕事・写真の取り出しを、確かめた身元から引いた household_id で絞る。
  - 二つの試験用の家庭で、互いに読めず書けないことを、実際の Postgres で確かめる。
- Claude に送る物：
  - 出典（文字・写真）と、関係する出典の今の事項だけ。家族の情報の名前・住所・ふだんの週は送らない。
  - 原文そのものに個人の情報が含まれ得る（連絡帳の写真の名前など）。どの文字・写真を送るかは、作り手が許した範囲に限る（§15）。
- ログ：
  - ID・数・時間・終わり方だけ。本文・文・名前・入力の要約を出さない。
  - 送ってよい項目の一覧で、送り出しとログを絞る。
- 写真の URL・R2 のキー・Push の登録・文の要約も、漏れ得る物として扱う。
- 公開のデモは架空の家族だけで、本番と読み書きの先を分ける。
- 処理と保存の場所：
  - Railway はシンガポール（作り手が了承）。
  - R2 の場所の指定は、保存の国の保証ではない。
  - Claude と地図の処理・保持の条件は別に確かめ、使う人に説明する。
  - 地図のデータは条款に従い、place ID 以外の営業時間・道のり・写真を、自由に保存してよいとはみなさない。

## 13. 段階と、今のコードから直す順

### 13.1 段階

1. **架空のデモ**：今の純粋なエンジンで通す。サーバーの道（メモリの保存）に載せ替える。
2. **実在の家族のデータの前の門**：次をそろえ、架空のデータで実際の環境（Railway・Cloudflare・iPhone）で確かめる。
   - 身元
   - members と identities
   - 家庭の分離
   - 事象と payloads の分け方（許す一覧）
   - 命令と operations
   - 家庭の行の押さえと 409。撤権（成員を止める・身元や結びを外す）の書き込みも同じ家庭の行を先に押さえ、読む・書くと互いに排他になることを、本物の Postgres の並びの試験で確かめる（§7.3 の 3）
   - 書き込みの Origin と JSON の確かめ、家族の家庭の返事を控えに残さない（no-store）
   - 送った依頼の控え（必須にし、控えの無い送ったの事象は受け付けない。§5.6 の残る穴）
   - 引き受けの提案の控え（accept の命令に必須。控えの無い引き受けは、今の作業を確かめたことにしない）
   - 読み取りの仕事は、実際に読んだ出典の文の版（sourceVersion）を必ず記録し、書く前に今の版と照らす
   - 消す（家庭ごと・取り下げ・写真・お知らせごと）、消している間の止め方、DB の控えの外の削除の記録（先に書いて読めることを確かめる）と、控えからの戻し（戻した後は送り出しを止め、家族が確かめてから再開）
   - 写真の付随情報を外す
   - 知らせの意図と結果
   - model_calls（SDK の試し直しを止める）と上限
   - 源の側の制限が Railway で使えるかの尖峰
   - 一台の iPhone で二人の大人を切り替えた時の、Push の登録と身元の結び付き（§9）。登録の順は端末の時刻で決めるが、新しい人が止めて登録を消した後の、前の人の遅れた登録は断れない（§9.1 の残る隙）。実際の家族が一台を分けて使うなら、消した後も時刻を残す形に直すか、一台を一人で使う決まりにして、実機で確かめる
   - 家族の情報の ID を、中身を含まない ID にそろえる（家族が書いた成員・場所・取れる手・手順の ID は、事象の actorId・taskKey・知らせのキーにそのまま残るため。入口で付け替え、配列の参照・組み合わせた ID・控えも含めて試験する。§5.8）
   - **この門を通るまで、実在の家族のデータを入れない。**
3. **後で**：繰り返しの決まりの広げ方、地図、性能の手当て、パスキー。要る時に足す。

## 14. 捨てた案

| 案 | 捨てた理由 |
|---|---|
| 正本を事象の列だけにする | 個別の削除と、今の権限の即時の遮断ができない |
| 全部を今の値の表だけにする | 「誰がいつ何に同意したか」と、取り消しの根拠が残らない |
| 画面でもエンジンを動かして先に見せる | 二か所の版の管理と、ずれた時の扱いが要る。§7.1 |
| モデルに事項の同じを決めさせる | 読み落としや分割で、引き受けを別の物に付け替える。§4.1 |
| 読み直しで見つからない事項を消す | 読み落としで、明日の持ち物が黙って消える。§4.1 |
| 全ての事象に効く「取り消し」 | 後の済み・返事・知らせと食い違う。§7.2 |
| 操作の記録を事象だけで済ませる | 何も起きなかった操作の送り直しが、後の他の人の選択を戻す。§7.3 |
| 外の cron・別のキュー・複数の送り手 | 今の規模に要らない。DB の意図と期限付きの引き受けで、後で移せる |
| 端末に一度だけ届くことの約束 | 外の受け付けと DB の記録を一つにできない。§5.7 |
| 中身を事象に置いたまま、消す時に書き換える | §6.2 |
| 汎用の繰り返しの言葉、通販のアカウント接続、医療の助言 | 今の範囲の外。危うさが大きい |

## 15. 作り手が決める点

1. **実在の家族の材料のうち、どの写真・文を Claude と置き場所に送ってよいか**：既定は架空の材料だけ。実在の物は、物ごとに作り手が許す。連絡帳の写真には、子や他の子の名前が写り得る。
   - 決めた（2026-11-02、作り手）：作り手の実例（学校のお知らせ・紙のお知らせ等）は `~/dev/maniau-private/` に置く。物ごとに個人情報（子・先生・家族の名前、学校・組の名、住所、電話、顔、手書きの署名）を確かめ、作り手が確かめた一覧で分ける。
     - 個人情報の無い物：Claude に送って、読み取りの確かめと評価に使ってよい。公開のリポジトリには入れない（学校の名や地名も居場所を示すため）。
     - 個人情報のある物：参考にするだけ。Claude にも、絵を作る道具にも送らない。版の形・文の調子・よくある書き方を、名前を含まない文で書き留め、そこから架空の名前と場所で合成する。
     - 公開のデモと評価の材料は、合成した物だけを使う。合成の材料も、開発用と、提出まで取っておく物に分ける。
