# Claude と Claude Code の使い方の記録

開発は Claude Code を中心に進める。機能は目的ごとに選び、選んだ理由と、効いたこと・効かなかったことをここに残す。製品の中での Claude の受け持ちは [../design/01-model.md](../design/01-model.md) §1・§10。

書き方：日付、目的、選んだ物、理由、結果（効果と失敗）。結果は、確かめた事だけを書く。

## 2026-11-02

### 前期調査を、分野ごとに並行して調べる（サブエージェント）

- 目的：ビルド開始の前（11/2の0時〜1時台）に、価値・新しさ・素のAIとの差を、6つの分野（社会学、心理学、先行事例、アルゴリズム、LLMの計画の能力、日本の学校・園の負担）から確かめる。
- 選んだ物：分野ごとのサブエージェント。統合と、設計の判断への落とし込みは本体で行った。
- 理由：分野ごとに読む資料が多く、互いに独立している。本体の文脈を、資料の読み込みで埋めないため。
- 結果：[../research/](../research/) の01〜06と、まとめ [00-synthesis.md](../research/00-synthesis.md)。Web検索の回数の上限で、日本のアプリの横断など一部を調べられなかった（各調査の§5・§6）。

### 守りの仕組み（フック）

- 目的：公開のリポジトリに、鍵・手元だけの物・実在の家族の材料を入れない。エージェントが、このリポジトリの外を読み書きしない。
- 選んだ物：
  - Claude Code の PreToolUse フック（`.claude/hooks/guard-paths.py`）：ホームの下で、このリポジトリの外を指すパスへの道具の使用を止める。
  - Git のフック（`scripts/git-hooks/`）：コミットの前に、作者のメール・鍵の形・置き場所・材料の写しを検査する。Claude Code の中で作ったコミットに、Claude の共同作者の行を付ける。
- 理由：決まりを文書に書くだけでは、複数のエージェントが並行して動く時に守りきれない。機械で止められる所は止める。
- 結果：
  - 試験は `tests/hooks/` にある（止める物・通す物・壊れた入力・共同作者の行）。
  - 実際のセッション（権限の確認を省く起動）でも、リポジトリの外への Bash と Read を止め、中の操作を通した。

### 公開の前の見直し（サブエージェント）

- 目的：最初の push の前に、公開してよい物か、主張が行き過ぎていないか、文書が食い違っていないか、検査に穴がないかを確かめる。
- 選んだ物：書いた本人の判断を渡さない、独立したサブエージェントによる見直しと、出典を原典で確かめるサブエージェント。指摘は、一つずつ確かめてから直した。
- 理由：書いた本人は、自分の前提の誤りに気づきにくい。
- 結果：
  - 鍵の検査が、パイプの途中で grep が先に終わると、大きな差分の後ろの鍵を見逃す不具合を見つけた。直して、試験を足した。
  - パスのフックが、サブディレクトリで起動すると誤る所と、文字列の中の `..` や `~` で誤って止める所を直した。確かめられない入力は、通さないようにした。
  - 出典の誤り（研究の対象、数値の範囲）を直した（[../research/00-synthesis.md](../research/00-synthesis.md) の冒頭）。

### 画面の考えを、作り手と見ながら決める（Artifact の画布）

- 目的：主な画面を、会話ではなく「今週・全体・詳細」の形にする判断を、作り手と画面を見ながら決める。G1 の製品の門で、作り手が自分の家の出来事を当てはめる試作にもする。
- 選んだ物：Claude の Artifact（デザインの画布）。携帯の幅の画面を11枚、筋（届いた → 返事待ち → 変更）ごとの行に並べた。
- 理由：文で説明するより、作り手が数分で判断できる。コードを書く前に、流れの欠けを見つけられる。
- 結果：作り手の指摘（使える助言には場所の情報が要る、主な画面は予定と作業の形）を受けて、設定・全体・今週・どこで買うかの4枚を足した。例の日付と場所を改めた時に、画面も11月の学習発表会の筋に直した（[../plan/02-product.md](../plan/02-product.md) §2・§5）。

### 後で替えにくい選択を、独立に考えてから突き合わせる

- 目的：言葉・保存・身元・置き場所のように後で替えにくい選択を、一人の思い込みで決めない。
- 選んだ物：二つのエージェントが、同じ問いに互いの結論を見ずに答え、その後に突き合わせた。評価の場面と正解を作る担当と、製品のプロンプトを直す担当も分けた。
- 結果：保存を SQLite から Postgres に、今週のログインを Cloudflare Access に改めた。作業の置き方を15分刻みにすると、実際にある10分の窓（17:20〜17:30）を落とすことを見つけ、分の精度に直した。家族の誰が引き受けたかと、外の相手に頼んだ事を、別の状態に分けた（[../design/01-model.md](../design/01-model.md) §7・§8・§11）。

### Claude API の仕様を、記憶でなく資料で確かめる（claude-api の Skill）

- 目的：Opus 5.5 の思考と effort、構造化出力の制限を、正しく扱う。
- 選んだ物：Claude Code の claude-api の Skill の資料。
- 結果：Opus 5.5 は思考を切れず、思考が max_tokens に含まれ、effort の初期値が medium であることを確かめた。比べる相手（強い Claude）の出力の上限を 4096 から 16384 に上げ、effort を明示した。元の上限のままなら、比べる相手を不当に弱くしていた。

### 画面をやさしくする（作り手の指摘で、画布を作り直す）

- 目的：子育て中の親や祖父母が、5〜10分で使い始められる画面にする。作り手から「専門の道具のように見える」と指摘を受けた。
- 選んだ物：同じ Artifact の画布を作り直した（版15）。
- 結果：一画面のやる事を三つまでにし、カードのボタンを一つにした（二択の問いだけ二つ）。「決め時」「引き受け」などの言葉を画面から外した。連絡帳を撮る入口と、習い事（サッカーの練習試合）の例を足した。

### 検証器の見直しを、独立のサブエージェントに任せる

- 目的：検証器を書いた担当とも、計画のエンジンを書いた担当とも違う目で、誤報と見逃しを探す。
- 選んだ物：Claude Code のサブエージェント（汎用）。設計の文書と型、試験の動かし方だけを渡し、見つけた物は一時的な試験で再現させた。
- 結果：見逃し7件と誤報3件を、再現つきで見つけた。エンジン側の漏れも分かった（断られた本命を開き直さない、頼んだ後に取り下げた案に取り消しの連絡を作らない、決め時を過ぎて始めていない本命をそのままにする）。エンジンは直して試験を足し、検証器は担当が直す。

### Managed Agents を今週は使わないと決める（資料をサブエージェントに読ませる）

- 目的：作り手から、Claude の新しい仕組み（Managed Agents）が、クラウドに置いた後の製品の力を広げるかを聞かれた。設計に「毎朝の見直しを Managed Agents に置くか（11/3に判断）」が残っていた。
- 選んだ物：Claude Code のサブエージェントに、claude-api の Skill の資料（Managed Agents の各章）を読ませ、製品の必要と照らした表を、出典の章付きで返させた。料金・ジッター・反復の上限などの要の数字は、資料で突き合わせた。
- 結果：今週の製品には入れない。毎朝の見直しは、サーバーの定時の回しと、コードの決まりで行い、文が要る時だけ Messages API を一度呼んで記録する。理由：ベータであること、会話の記録が消すまで残り、実在の家族のデータの消し先が一つ増えること、定時の起動に最大9分の遅れがあり、知らせの判断はもともとコードで行うこと、評価の繰り返しは費用と遅れを何倍にもし、一度の読み取りはコードの検査で足りること、API なしの試験と呼び出しの記録が崩れること。期間の後には、学校や区の公開のページの変化を定時に見る用途（変化は新しい出典として、読み取りと家族の確認を通す）を候補に残す。

## 2026-11-03

### 家の人がすることを読み分ける（構造化出力の欄を一つ足し、プロンプトを extract.v3 に）

- 目的：宿題と当番のうち、家の人がすること（音読カードのサイン、丸つけ、お茶当番、配車）だけを家族の作業にする（作り手の選択：毎日のお知らせを作業にする）。子どもだけでする宿題や子の当番は作業にしない。
- 選んだ物：読み取りの構造化出力に familyAction（はい・いいえ）を足し、プロンプトを extract.v3 にした。誰がするかの読み分けは読み取りの仕事なので、モデルに型のある欄で返させる。作業にするか（うちの番か、書かれた時刻に入るか）はコードが決める。v2 で録った応答は書き換えず、無い欄を false として読む。
- 理由：コードで言葉を当てはめる（「サイン」を含むか等）より、原文の言い回しの違いに強い。欄を一つ足すだけで、ほかの読み取りの形は変えない。
- 結果：架空の事項で、エンジン・検証器・画面の試験を通した。開発用の架空の場面 4 つ（既存の 3 つと、サイン・子の宿題・当番を混ぜた 1 つ）を、v3 で各 1 回、実際の Claude（Opus 5.5、思考の強さ medium）に読ませた：4 回の呼び出し、入力 23,125・出力 5,824 トークン、約 0.21 ドル。混ぜた場面の 6 行では、家の人がすることの読み分けがこの 1 回では合った（1 回だけで、正答率とは言えない。v2 との比べもしていない）。
- 見つかった事と直し：「12月4日まで」から、書かれていない 8:00 を締切に付けた。モデルに頼まず、コードが指した文に書かれた時刻だけを使うようにした（午前・午後と範囲の書き方を見る。落とした始まり・終わりは、その文を家族に確かめてもらう）。習い事の場面では、条件の一部（空きのある級、受付の確認）を落とし、欠席の連絡と振替を締切として読んだ。これは習い事の作業を作る時に扱う。
- 同じ日に、ほかの担当が、決める・追う場面の比べ（開発用の架空の場面 2 つを足して 8 つ）を回した：6 回、12 回の呼び出し、入力 21,275・出力 16,696 トークン、約 0.42 ドル。二つを合わせて約 0.63 ドル。

### 家族が入れた文を、その場で Claude に読ませる（Messages API・構造化出力）

- 目的：用意したお知らせだけでなく、家族が貼った文・キーボードの音声入力で話した文を、その場で読んで計画に入れる（作り手の指摘：今のデモは決まった筋しか見られない）。
- 選んだ物：前から使う読み取り（Claude Opus 5.5、構造化出力、プロンプト extract.v2、effort は medium）を、デモのサーバーから呼ぶ。SDK の自動の再試行は止め（一回の読み取りは一回の呼び出し）、110 秒で諦める。数と同時に読む数に上限を置く。
- 理由：読み取りの形と検査は、録った応答と試験で既にある。新しい呼び方を足さず、同じ道を家族の入力にもつなぐのが最も小さい。
- 結果：
  - 架空の文で 2 回確かめた（延期のお知らせ：入力 6117・出力 1007 tokens、13 秒。架空の学級だより：入力 6111・出力 1408 tokens、14 秒。合わせて約 0.10 ドル）。どちらも、録った応答と同じ形で計画に入った。
  - モデルが、二つの文にまたがる事項の文 ID を逆の順に挙げた。引用の検査は、原文の順につないで探すようにした。
  - モデルが「8日(火)までに」を二通りに読めると示し、その文を「要確認」として家族に見せた。
  - 試用の下見（架空の連絡帳を製品と同じ道で読み、二人の「きょう」に何が出るかを見た。手元だけの道具で行い、リポジトリには入れていない）：1 回、入力 6,138・出力 1,451 tokens、約 0.054 ドル。
  - 独立の見直しで、読む間に家族が事項を直した時に古い読み取りがそれを消す等の穴が見つかった。前提が変わった読み取りは足さない、引用と日付を原文と照らす等の検査を足した（コードで行い、モデルの出力で置き換えない）。

### 家族の一言を、記録の案にする（ひとこと。Messages API・構造化出力・Sonnet 5.5）

- 目的：「おばあちゃん、12/7は大丈夫だって」「申込書、書いたよ」のような一言から、どの頼み事・作業のことかを探し、押すだけで記録できるようにする（作り手の希望：声で使えること。札を探して押す手間を減らす）。
- 選んだ物：一言と、今の作業・頼み事・未定の値・事項を渡し、構造化出力で「記録の種類と対象の ID」「問いなら参照する ID」「受け付けられない理由」だけを返させる（プロンプト utterance.v1、effort は low）。対象があるか、話した人が担当か、今の状態で効くかはコードが確かめ、家族に見せる文は画面が計画から作る。押すまで何も書かない。
- モデル：Sonnet 5.5（01-model §10 の表のとおり）。同じ七つの一言で Opus 5.5 と同じ答えを返し、待つ時間が短かった（1.4〜4.6 秒と 1.7〜5.6 秒）。
- 呼び出し（11/3、すべて架空のデモの家族）：
  - 確かめの六つの一言（Opus 5.5）：6 回、入力 24,638・出力 525 tokens、約 0.109 ドル。
  - 同じ六つ（Sonnet 5.5）：6 回、入力 25,016・出力 525 tokens、約 0.055 ドル。どのモデルが答えたかの確かめ：2 回（Sonnet 1・Opus 1）、約 0.028 ドル。
  - 開発用の場面（eval/cases/spoken-updates の 7 つ。Opus 5.5）：7 回、入力 19,252・出力 701 tokens、約 0.091 ドル。7 つとも分類が合い、変更の 4 つは対象の命令も合った。この後にプロンプトと前提の形を直したので、今の版の成績ではない。
  - 直した後、同じ開発用の場面（Sonnet 5.5、プロンプトと前提を凍結した版）：7 回、入力 19,689・出力 701 tokens、約 0.046 ドル。7 つとも分類が合い、変更の 4 つは対象の命令も合った（画面の文と、押した前後の動きは、この数に入らない）。
  - サーバーを通した確かめ：Opus 5.5 で 1 回（入力 4,174・出力 102 tokens、約 0.019 ドル）、Sonnet 5.5 で 2 回（入力 8,330・出力 174 tokens、約 0.018 ドル。1.4〜1.6 秒）。
  - 携帯の幅（390px）の画面から、実際に問い・ふだんの週の変更・返事を伝えた確かめ（独立の見直し、Sonnet 5.5）：5 回、入力 20,850・出力 358 tokens。うち 3 回は約 0.027 ドル。前の 2 回は推論の地域と速さの記録が無く、費用は不明。
  - まだだれも持っていない作業（提出物）への一言の確かめ（独立の見直し、Sonnet 5.5）：1 回、入力 3,439・出力 59 tokens、約 0.0075 ドル。今のプロンプトは、話した人が持つ作業だけを対象にするので、受け付けない（other）と返した。一言では記録しないと README に書き、コードは対象が担当の無い作業なら「きょう」で担当を決めるよう返す。
  - 持ち物の「家にあるか」への一言（今の計画から作った架空の 7 つの場面：ある・ない・あると答えた後の言い直し・祖母の返事・品物の問い・店の分からない品物・同じ品物が別の日に要る。独立の見直し、Sonnet 5.5）：7 回、入力 23,694・出力 881 tokens、約 0.056 ドル。7 つとも対象と分類が合った。同じ品物が別の日に要る場面は、前提に要る日が無いまま一回選び当てただけで、見分けられる証拠ではない（その後、前提と候補に要る日を添えた）。
  - 同じ 7 つを、前提に要る日を添えた後に（Sonnet 5.5）：7 回、入力 23,802・出力 698 tokens、約 0.055 ドル。7 つとも対象と分類が合った。二回とも開発用の一組で、全体の正しさや実機での効き目は言えない。
  - 買った後の言い直し（「家にあった」「見つからない」）と、祖母の返事の場面を、買った後の今の答えを空にした前提で（独立の見直し、Sonnet 5.5）：3 回、入力 10,303・出力 317 tokens、約 0.024 ドル。3 つとも対象が合い、押した後の状態も合った（画面の文は、この数に入らない）。開発用の場面で、全体の正しさは言えない。
  - 合わせて 54 回、約 0.53 ドル（費用の分からない 2 回を除く）。
- 独立の見直しで見つかった穴（直して試験を足した）：別の大人の作業を一緒に言った時に黙って落とす、見せた後に日や用件が替わっても古い案を記録できる、頼み事の日を送った時の日でなく今の手配の日で示す、取り消しを伝える頼み事が前提から抜ける、読む間や送り直しまでに計画が変わっても古い答えを今の事実として見せる、届いたか分からない前の操作より先に記録を送れる（逆に、記録が届いたか分からない間に、ほかの命令を送れる）、共有する子の多い条件の式を展開しきって入力が膨らむ、答えを見せた後に計画が進んでも古い答えが残る、同じ相手への同じ日の頼み事を候補の文で見分けられない、比べるための候補の作業を前提に入れ、引き受け待ちのように答える。

### お知らせの写真・PDF を書き起こす（Messages API・画像と PDF・構造化出力・Opus 5.5）

- 目的：学校のプリントや連絡帳は紙で届く。写真を撮るだけで入れられるようにし、作り手の家のおたよりで試せるようにする（02-product §5.2）。
- 選んだ物：写真は画面で長い辺 2576px までに縮めて JPEG にし、PDF はそのまま、Claude（Opus 5.5、effort low）に書き起こさせる（プロンプト transcribe.v1。書かれた文字を読む順にそのまま行ごとに、要約も訂正もせず、読めない字は〓）。書き起こした文は、家族が写真と見比べて直してから、今の読み取り（extract.v2）で読む。写真は残さない。
- 理由：読み取りに画像を直接渡すより、文を確かめる一段を挟む方が、家族が読み違いを直せ、読み取りの文 ID も確かめた文に付く。手書き・小さい字・表のために Opus 5.5 を選び、考えることは少ないので effort は low にした。
- 費用の上限：ファイルの大きさ（PDF 4MB）では、PDF のページ数を抑えられない（ページごとに画像の分がかかる）。書き起こしを呼ぶ前に、同じ要求（構造化出力の形を含む）で入力の tokens を数え（count_tokens。費用は掛からないが、写真・PDF も Anthropic に送る）、12,000 を超える物は書き起こしを呼ばずに断る。数は見積もりで、実際の入力と少し違うことがある。大きすぎた物も一回と数える（選び直し続けて、外への要求が上限なく増えないように）。独立の見直しで、数 KB の 40 ページの PDF が通ると指摘されたため。
- 呼び出し（11/3）：合成した印刷の連絡帳の写真（開発用の場面 01 の文を画像にし、傾け・ぼかし・ざらつきを加えた物）で 1 回。入力 3,657・出力 158 tokens、6.3 秒、約 0.018 ドル。6 行とも元の文と一字も違わなかった。手書きや実際のプリントの写真では、まだ確かめていない。

  - 取っておく 5 場面：まにあうは 1 場面で調べを呼び（家の地域があり、調べの頼みは入口が扱う種類を使った）、頁を読んだ後の候補は 0 件だった。固めた頁だけでは、その頁が頼んだ種類に当たると示せないので、見落としとは決めない。3 場面は家の地域が無く、決めておいた規則のとおり、情報が足りないとして呼ばなかった。1 場面は店の調べで、入口が扱わないので呼ばなかった（この 4 場面を、モデルの失敗には数えない）。比べる相手は 5 場面とも答えを終え、次の一手を示した。22 回、入力 29,688・出力 6,492 tokens（Opus 5.5・標準の速さ）、約 0.249 ドル。
