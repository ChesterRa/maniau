# 通用の「すること」を含む読み取り：開発用場面

架空の開発用材料であり、製品の成績ではない。`source`・`schoolYear`・過去の事項と未定値だけをモデルに渡す。`expected` の確認点は採点者だけが使う。提出まで残す別の場面は `.local/eval-holdout/reading-v4/` に置き、提示文を調整する担当には見せない。保留場面の結果を使って調整したら、その場面は開発用となる。

| 場面 | 主な確認 |
| --- | --- |
| dev-01 | 行事・提出物・持ち物・家の人と子の当番・署名を保ち、同じ義務を need に重ねない |
| dev-02 | 同じ文にある行事の事実と家族の出席依頼を分ける |
| dev-03 | 同じ文にある締切と条件付きの家族の申込みを分ける |
| dev-04 | 終わりのない時間窓を、書かれていない時刻や別の締切に変えない |
| dev-05 | 送り手の予定や子の当番を家族の仕事にしない |

## 採点

`eval/reading-v4-score.mjs` は、文 ID・引用・種類・指定された欄・条件の参照・重複 need の一部だけを機械的に照らす。引用は、指した文を原文順に連結してから NFKC と空白で正規化し、製品と同じ方法で確かめる。複数の文をまたぐ引用や別の文脈として参照している場合は、どの用件が重複かを決めず `undetermined` とする。参照不能な条件・出典、書かれていない家族の成員 ID は失敗。拒否・打ち切り・壊れた応答は `unscorable` であり、成功に数えない。

機械の判定がすべて `pass` でも、結果の `state` は `partial`、各 `manual` は `pending` のままである。採点者は原文と出力を見て、用件・対象者・日付・場所・同一義務の重複・条件の真偽を、各場面の `expected.manual` に従って「満たす／満たさない／判定不能」で記録する。特に日だけの締切は、変換後に書かれていない時刻が確定扱いされていないかも見る。重要項目の失敗と判定不能を別に残し、平均に埋めない。

`undetermined` が出た時は、事項自体が無かったのか、事項はあったが欄が欠けたのかを、保存した応答を見て人の記録に分ける。

人の判断をプログラムで記録する時は `reviewReadingV4(result, decisions)` を使う。`decisions` は確認点 ID を鍵とし、各値に `status`（`pass`・`fail`・`undetermined`）と空でない `evidence` を入れる。重要な確認点が一つでも失敗なら `fail`、未採点が残れば `pending`、判定不能なら `undetermined` とし、すべて確かめた時だけ `pass` にする。根拠を含む結果も `eval/runs/` に置き、保留場面の内容は提示文を調整する人に渡さない。

保存済みの応答を照らす時は、応答を Git 対象外の `eval/runs/` に置く。通信や鍵の読み込みはしない。

```sh
node --test eval/test/reading-v4-score.test.mjs
node eval/score-reading-v4.mjs --case eval/cases/reading-v4/dev-01.json --response eval/runs/RESPONSE.json
```

`inputForModel` が作る入力の SHA-256 を採点結果に含める。実際に製品の `extractNotice` を呼ぶ時は、その `inputHash`、提示文と変換器の版・ハッシュ、モデル、停止理由、各試行と再試行の回数、使用量と費用を別に記録する。実行前後に実装が変わった試行は比較に使わない。架空の手書き応答で採点器を試した結果は、モデルや製品が読み取れた証拠ではない。
