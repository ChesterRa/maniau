# 読み取りの開発用場面

架空の連絡帳の書き起こし、サッカーの連絡、水泳の決まりを使う。実在の家庭・学校・団体の材料ではない。連絡帳は文字への書き起こしであり、写真の文字認識の評価ではない。

各 JSON の `source` と `context` を入力にし、`expected` はモデルに渡さず採点者が使う。`expected.referenceOutput` は `ExtractionOutput` の形をした正しい読み方の一例である。ID、事項の分け方、意味が同じ条件式は固定しない。`checks` の各項目を○・×・？で判定し、重要な項目の失敗と判定不能を別に残す。

- 書かれたこと、推定、実際に家族や相手が確認したことを分ける。
- 一つの文に複数の用件がある時は、全てを残す。文IDの網羅だけでは、抽出漏れがない証明にならない。
- 条件つきの予定を確定させず、中止となる条件の「かつ／または」も確かめる。
- 日付だけの期限を、根拠のない時刻つきの期限に変えない。現行の型で表しにくい点は各場面の `limits` に書く。
- 参照は書き起こしの文だけに基づく。写真を読めた、実際の場所や契約を確認できた、という根拠にはならない。

整合性の検査は `node --test eval/test/reading-cases.test.mjs`。検査が通っても、モデルの読み取りや計画の正しさを示すものではない。提出まで見せない場面は、このディレクトリや試験に入れない。
