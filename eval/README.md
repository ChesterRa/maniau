# 境界の場面で比べる

G1 の技術の門に向けた、架空の材料による開発用の評価である。日付・店・時間を固定した小さな場面で、外部サービスなしに境界を確かめる。実在の地理を使うデモや実使用は別に検証する。製品の門は [product-gate.md](product-gate.md) で別に確かめる。ここに結果を先に書かない。実行前の評価材料は、製品の性能を示す証拠ではない。

## 何を比べるか

| 場面 | 失敗させたくないこと |
|---|---|
| `cases/01-expired.json` | 期限切れの案を実行可能と勧めない |
| `cases/02-waiting.json` | 返事待ちと引き受け前を確定扱いせず、予備の決め時を逃さない |
| `cases/03-change.json` | 要らない準備を外し、残す準備と外部への連絡を分ける |
| `cases/04-questions.json` | 段取りが変わる問いを必要な時に聞き、答えを勝手に埋めない |
| `cases/05-joint-care.json` | 二日分の申込みを重ねず、先に引き受けた時刻を保つ |
| `cases/06-joint-conflict.json` | 登録された時間では本命と予備の両方を置けない時に、重なりをごまかさない |
| `cases/07-declined-task.json` | 引き受けた後に一つの作業だけを辞退しても、別の引き受けを消さない |
| `cases/08-moved-request.json` | 日が変われば前の日への返事を新しい日の承諾とせず、予備を残す |

各ファイルの `raw` は元の連絡、`facts` は同じ情報を整えた入力、`interview` は質問に答える係だけが読む答え、`expected` は採点者だけが読む確認点である。どちらの入力にも現在時刻を付ける。正解と質問への答えは、質問される前にモデルへ渡さない。実在の家族の材料を、この仕組みや API に入れない。

05 は、書く・提出する作業と使える時間を限定した開発用場面である。同じ架空の事象と時刻を製品の正式な命令にも通し、四つの作業の時間・順序・引き受けの状態を比較する。比較相手には、G1 の別の四場面で選定済みの提示文 2 を事前に固定して使う。製品には整理済みの事実を渡すため、この比較は `facts` 同士とし、読み取りを含む成績とは扱わない。分単位の独立した列挙は、この限定した範囲で候補があることと、元の引き受けを保てることを確かめる。読み取りの正しさ、実家庭での実現可能性、すべての案の最適性を示す物ではない。

06 も同じ設定と範囲で、登録された時間だけでは両方の案の準備を置けない例を扱う。「この時間に置けない」ことと、家族が現実に取れるすべての手を調べ尽くしたことは分けて採点する。

07 と 08 は、辞退と日付の訂正について、作業・依頼の状態を正式な命令で再生する。比較相手には G1 で選んだ提示文 2 を固定し、整えた事実を渡す。読み取り・画面・実機への通知は、この二つの再生には含まない。製品側にはデモ家庭の他の登録情報もあるため、場面に共通して明記された確認点だけを比べ、それ以外の配置の優劣には使わない。結果は [開発用比較](results/lifecycle-development.md) に残す。

05 と 06 の製品側の再生は `eval/test/joint-product.test.ts` に置く。場面ファイルのハッシュが変わると止まり、手で組んだ製品側の前提と場面が今も一致するか見直す。架空の事象を正式な命令に通し、有限列挙、引き受けの状態、検証結果と通知 gate を別々に確かめる。これは読み取り・実機への通知・すべての置き方の検証ではない。モデルへの実呼び出しとは分け、外部通信なしで実行できる。

製品と強い Claude に、同じ場面・時刻・情報・必要な質問への答えを与える。両者とも、初回に元の連絡を読む試行と、整えた事実を受け取る試行を分ける。後者だけの成績を、読み取りを含む成績として扱わない。日付計算の道具と質問を両者に許す。製品にその入力方法がまだ無ければ、未実施と記録する。

この比較で見る「知らせ」「連絡」は、その時点で誰に何を知らせるべきかの出力である。文章で提案したことを、実機へ通知が届いたことや、外部の相手に連絡が済んだこととは扱わない。製品の自動追跡、事象の保存、実機への配送は別の操作・時刻・実機試験で確かめる。単発のチャットとの比較から自動追跡の実績は主張しない。

比較相手には `prompts/` の三通り以上を開発用の各場面・各入力で一回ずつ試す。最良の選択基準は、順に「重要な確認点の失敗が少ない」「重要な確認点の判定不能が少ない」「不要な質問が少ない」とし、同数なら番号の小さい方にする。その後、選んだ版で各場面・各入力を 3〜5 回ずつ実行し、選定時の試行とは別に記録する。同じ開発用場面を選定と評価に使うことによる偏りを結果に添える。保留場面の成績を選択に使わない。時間が足りなければ実際の回数を書く。評価担当が各試行の記録を見て、各確認点を「満たす／満たさない／判定不能」で採点する。重要な確認点の失敗をまとめて平均に埋めない。文面が曖昧なら、正解に寄せて解釈せず判定不能にし、場面を直して改めて両者を試す。

記録する指標：外し漏れ・誤った取消し、期限切れの案を勧めた数、未確定を確定と扱った数、聞いた問いの数と段取りが変わる問いの数、制約違反、判断不能を正直に示したか。製品・比較相手の両方が成功した場面と、比較相手が勝った場面も残す。少数の開発用場面から一般的な優劣を主張しない。

## 質問に答える係

対話端末でモデルが `ask_family` を呼ぶと質問が出る。係はその場面の `interview` に該当する答えだけを返す。書いていないことは「分かりません」と返す。非対話の実行では、場面ごとの `match` に記した語の組合せで答えを一つだけ選ぶ。ゼロ件・複数件、または `exclude` の語が含まれる場合は「分かりません」と返す。答えをまとめて先に教えない。

機械的な語の一致は、質問の意味の理解を保証しない。質問・一致した項目・答えは `runs/` の各試行の `interview_audit` に残る。採点者がすべて見直し、答え過ぎた、取り違えた、答えるべき質問に答えられなかった場合は、その試行を比較不能とし、モデルの失敗には数えない。適切な回答に直して別の試行を行い、両方の記録を残す。質問の数は会話記録から数え、採点基準を使って有用性を人が判断する。製品側の質問にも同じ答えを使う。

## 実行

Node.js 24 を使う。依存の追加は不要。最初は通信も鍵の読み込みもしない準備確認を行う。

```sh
node --test eval/test/*.test.mjs
pnpm --filter @maniau/server exec tsx --test ../../eval/test/joint-product.test.ts
node eval/run-baseline.mjs --case eval/cases/01-expired.json --input raw --prompt 1 --model MODEL_ID --effort high --max-tokens 16384
```

実際に呼ぶ時は `.env` に `ANTHROPIC_API_KEY` を置き、上のコマンドに `--execute` を付ける。モデル名は実行時に指定し、比較相手として強いモデルを選んだ根拠を結果に残す。`--effort` はモデルが対応する場合に指定する。モデルによって既定値は異なるので、強い比較相手として使う設定とその選択理由を結果に記録する。`--max-tokens` は一回の応答ごとの上限で、思考にも使われる。上限で打ち切られた試行は未完了とし、必要なら上限を増やして別試行にする。端末から質問に答える。`--execute` なしでは API を呼ばず、正解や質問の答えも表示しない。

トークン使用量から費用を見積もるには、実行時に公式料金を確かめ、`--input-usd-per-million`、`--output-usd-per-million`、`--pricing-url`、`--pricing-checked`（`YYYY-MM-DD`）をすべて指定する。指定しなければ費用は不明と記録する。通常の global / standard の単価を指定し、応答の推論地域が global と確認できない時、高速料金やキャッシュ料金が必要な時は不明扱いにする。概算は請求額の証明ではなく、後で実際の明細と照合する。

`runs/ledger.jsonl` にリクエスト開始と結果、モデル、日時、入出力トークン、料金の根拠と概算を残す。429・500・529 は最大2回再試行し、それぞれ独立したリクエストとして記録する。`Retry-After` がある場合はそれ以上待つが、30秒を超える時は勝手に早めず中止する。通信が途切れた場合は自動再試行せず、課金の有無を不明とし、失敗を 0 円と扱わない。各試行の対話記録は `runs/` に保存する。どちらも Git の対象外。引用する結果だけを `results/` に、実行条件・試行回数・費用・失敗例とともに置く。

提出まで残す別の場面は、`.local/eval-holdout/` に置き、製品のプロンプトを調整する担当には提出まで見せない。版を固定した後、評価担当が独立に試し、結果の公開可否を確認する。結果を見てプロンプトや製品を調整した場合、その場面は開発用となる。次の独立した評価には未使用の別の場面が必要である。

## G1 の判断

技術の門は製品を続けるか否かを決めない。比較相手がほぼ正しく扱えるなら、求解を小さく保ち、状態と追跡を優先する。崩れるなら、観察された失敗と、それを求解・検証のどこで防ぐかを記す。モデルの読み取りが落とした事実を、制約の検証だけで完全に見つけられるとは言わない。
